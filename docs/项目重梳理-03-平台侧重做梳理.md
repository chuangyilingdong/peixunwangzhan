## 0. 三条结论（先看这个）

**结论一：「每节课算力预算」目前事实上不存在，是从零实现，不是接线。**
`class_sessions` 有 `session_credit_cap`、`consumed_credits_total` 两个字段，也有机构端「积分上限」按钮，
但 `consumed_credits_total` **只在**一个孤立端点里累加（`apps/server/src/routes/ai.js:170`），
真实生成走的两条路（`aiGeneration.js` 异步 worker、`vibecoding.js` 对话）**都不累加** → 恒为 0 → 永远拦不住。
另外 `org_ai_budgets` 表是摆设（`assertOrgAiBudget()` 是空函数，`billingConfig.js:137-138`）。
所以「填了 50 元就能真拦住」这件事，必须新建预算闸（课时 / 机构 / 学生三级），并把它挂到**唯一的上游出口**上。

**结论二：积分不能先删，必须先建算力账。**
现在「积分」不只是账务，它同时是三处**刹车**：①课堂用量上限（`aiControls.js:34-35`，虽不生效）、
②成员个人上限（`ai_credit_limit`，**在 3 处重复实现**：`ai.js:143-146`、`aiGeneration.js:381-382`、
`vibecoding.js:169-170`）、③周期额度（`monthly_credit_allowance`，同样 3 处重复）。
另外 `billing_packages` 一张表同时扛着**席位 + 能力开关 + 月度额度**三件事，
删它会把 `PACKAGE_CAPABILITY_DISABLED` 这个能力闸一起删掉。
👉 顺序必须是：先做算力总控（能用新机制接住这三处刹车）→ 再删积分。

**结论三：new-api 值得接，但要接受它的许可证与「自定义上游」的边界；必须先做一个 PoC。**
new-api 正好是我们要做的东西（多渠道 / 多 key / 模型映射 / **按令牌限额** / 用量日志 / 重试与负载均衡），
拿它当「上游渠道池 + 按 key 的额度闸 + 用量日志」比自研省几周。三处必须提前知道的事：

- **许可证是 AGPL-3.0**（不是网上常说的 MIT/Apache-2.0，已用 GitHub API 核实：`spdx_id = AGPL-3.0`）。
  含义：① 原样部署、当成独立服务用 → 可以，但按 AGPL §13 要对使用者提供对应源码（未修改的上游版本指向官方仓库即可）；
  ② **只要改了它**（例如为我们的视频/音乐写一个任务插件），那部分改动必须按 AGPL-3.0 开源；
  ③ 我们的平台通过 HTTP 调用它，是独立程序、不算衍生作品（我们的代码不必开源）—— 但这是法律判断，正式商用前请法务过一眼。
- **我们的「自定义请求模板」有对应机制但不完全等价**：new-api 有**参数覆盖（param_override）**，
  支持按条件（可匹配模型，内置 `original_model`/`upstream_model` 字段）把 JSON 合并/覆盖进下游请求体 ——
  这能覆盖我们「同渠道不同模型不同请求体」的大部分需求；但**提交/查询路径**（MiniMax V2 那种 submit + poll）
  它走的是「任务式 provider」，自定义厂商要写**任务插件（Task Plugin）**（社区已有通用协议插件，如 `generic-rest`）。
- **额度单位是它自己的 quota**（按模型价格表折算），要把「这节课 50 元」翻译成令牌额度，需要先把模型价格表配准。

## 1. 目标与交互原则

**要解决的问题**（用户原话）：平台端/机构端/老师端后台「逻辑混乱、操作逻辑混乱、重复且不清晰」。

**原则（写下来当验收标准）**：
1. **一个概念只在一个地方管**。例：机构额度只在「机构管理」里管，不再同时在「机构管理 / 计费与用量 / 概览」三处出现。
2. **列表页 + 详情页各是一个路由**（可深链、可刷新、可后退）。现状是 `CourseManagement.jsx:826` 用 `useState` 在一个路由里切列表/详情，深链和后退都失效。
3. **术语统一**：现在「积分 / 魔法石 / 额度 / 配额」四种叫法混用（`Dashboard.jsx:51` 用「魔法石」、`:52` 用「积分」），三套「素材」同名不同物（宣传物料 / 画布素材 / 教学素材）。重做时每个概念只留一个词。
4. **危险动作显式确认**：发布、更新发布、下架、重置密码、撤销授权，都要有「影响谁」的确认文案。
5. **状态机统一**：同一种生命周期用同一套状态名（现在画布作品 4 态、VibeCoding 作品 3 态 + 一个 `is_public` 布尔，见第 5 节）。

## 3. 板块一：创建课包

### 3.1 课包字段（用户口径：只要这 7 个）

| 字段 | 现状 | 目标 | 备注 |
|---|---|---|---|
| 封面 | `course_series.cover_image_url` ✅已有 | 上传/裁切预览 | 需要图片上传 + 尺寸提示 |
| 名称 | `title` ✅ | 必填，平台课包唯一 | 现有唯一索引 `schema.js:250` |
| 简介 | `description` ✅ | 必填 | — |
| 版本 | `version` ✅但语义错 | **见 3.4** | 现在是「改一次自动 +0.1」的展示计数器 |
| 价格 | `price_fen` ✅ | 保留（对外报价） | 与「算力」无关，别混 |
| 可见范围 | `visibility` ✅但名字误导 | **改名**：`公开上架课程广场` / `仅授权机构可见` / `私有草稿` | 现在 `ALL_ORGS` 的真实含义是「上架官网课程广场」，**与机构能不能用无关**；机构能不能用只由 `course_assignments` 决定（`lib.js:469-472`）。这是最容易误读的字段 |
| 难度 | `difficulty_level` ✅ | 1–5 星 | 已有 |
| ~~其他~~ | 现有还有 `validity_days`（**零消费方**，实际有效期在授权单上）、`grade_range`、`estimated_credits_per_person`、`marketplace_reward_credits`（积分） | **删除或隐藏** | `validity_days`/`estimated_credits_per_person` 是死字段；积分字段随积分一起删 |

### 3.2 课时（用户口径：名字 + 时长 + 上课类型 + 能力 + 素材 + 算力上限）

**① 上课类型改成「按课时、可多选」** —— 这是与现状最大的结构差异：

- 现状：`course_lessons.delivery_mode` 是**单值** `CHECK IN ('CANVAS','VIBECODING')`（`schema.js:264`），
  且课包层也有一份（`:249`）作为新课时默认值。学生端按「课时优先、单值互斥」判定可用性
  （`studentContext.js:305-306`：`canUseNow` 只认 CANVAS、`canUseVibeCodingNow` 只认 VIBECODING）。
- 目标：一个课时可**同时**勾选「画布」「VibeCoding」，学生进课时后自选一种。
- 改法（推荐，改动最小）：新增 `course_lessons.delivery_modes`（JSON 数组，如 `["CANVAS","VIBECODING"]`），
  读取侧先读新字段、缺失时回退旧 `delivery_mode`；学生端的两个 `canUse*Now` 改成读数组。
  **课包层的 `delivery_mode` 删掉**（语义模糊，只当默认值用）。
- ⚠️ 待拍板：同课时两种都开时，学生端是「进来先选」还是「两套入口并列」；以及作品归属（画布作品走 `works`、VibeCoding 走 `vibecoding_submissions`，两条链路的作品展示是否要在同一课时下并列，见第 5 节）。

**② AI 能力**：沿用 `course_lesson_capabilities(lesson_id, capability)`（白名单 `text/image/video/music`，`helpers.js:119`）。
改造点：把 `video` 与「音乐」的表达对齐到现在的实际模态（现有 `music`，播客/配音已下线），并把「按类型默认勾选」做出向导
（勾了 VibeCoding → 默认 `text`；勾了画布 → 提示是否要图片/视频）。

**③ 教学素材**：沿用 `course_lesson_materials`（画布素材/生成框体）+ `course_lesson_teaching_assets`（教师备课）。
改造点：`material_type` / `asset_type` **服务端现在零校验**（`helpers.js:125`、`:172` 只是 `toUpperCase().slice(0,30)`），
前后端还是两份枚举（`CourseManagement.jsx:25`、`:32`）→ 统一到服务端一份白名单并返回给前端。

**④ 算力上限（填钱，且实际生效）** —— 新增字段 + 新机制：

- 新字段：`course_lessons.compute_budget_fen INTEGER`（这节课的算力预算，单位分）。
- 生效位置：**网关侧**（不是应用侧）。每次上游调用前，网关按「这节课时 token 的剩余额度」判断，
  超了直接拒绝（返回统一的「本节课算力预算已用完」错误码）。见第 7 节的三级预算闸。
- 额外要求（用户明确）：**能监控到所有机构每节课的实际消耗** → 需要按「课时 / 课堂 / 机构」三个维度归集实际花费，
  见 7.4。现状 `usage_records` 有 `class_session_id` 但没有真实金额/token（`input_tokens/output_tokens` 明确未采集），
  所以**必须扩采集**。

### 3.3 发布（创建完成后提示是否发布）

- 现状：`POST /course-series/:id/status` 只有 `publish` / `archive`（`courses.js:283`），发布前 `validateSeriesForPublishing` 校验
  「未归档课时必须全部 PUBLISHED / VibeCoding 课时必须开放 text / 生成框体模态必须在已开放能力内」。
- 目标：课时保存后弹「是否发布这节课？」；发布后课时即对学生生效；未发布的课时在课包详情里灰显。
- 保留现有校验（那三条校验都是踩坑得来的），但**错误提示要指到具体课时**（现在只返回一个错误码）。

### 3.4 编辑与版本（用户口径：每次修改填最新版本号 + 是否更新发布）

- 现状：`version` 是纯展示计数器，`bumpSeriesVersion`（`helpers.js:535-539`）在**任何**内容改动时自动 +0.1
  （改个标题也会 +0.1）→ 版本号快速膨胀且无区分度；**没有版本历史、没有快照、没有发布隔离**
  （已发布课包一改，已授权机构立刻看到新内容，`studentContext.js:141` 只看 `status='PUBLISHED'`）。
- 目标：
  1. 版本号**由人填写**（不再自动 bump），修改时必填「新版本号 + 变更说明」。
  2. 「是否更新发布」= 一次显式动作：不发布 → 只存草稿（对已授权机构**不生效**）；发布 → 生效并推给已授权机构。
  3. 「授权的机构以及外显层面都要全部更新」→ 发布后：机构端课时内容更新；官网课程广场（若上架）同步；在学班级不受影响（见下）。
- 需要的新东西：**版本快照**。推荐 `course_series_versions(series_id, version, snapshot JSON, note, created_by, created_at)`
  + 课时内容一并存入快照；学生/机构读到的是「当前已发布版本」，平台看到的是「草稿」。
- ⚠️ 待拍板：**正在上课的班级**要不要钉在旧版本（推荐钉：班级开课时记录 `series_version`，避免上课中途内容变化）。
  这是现有代码完全没有的能力，做与不做差别很大。

## 4. 板块二：机构账号（创建 / 管理 / 授权）

### 4.1 创建机构

| 字段 | 现状 | 目标 |
|---|---|---|
| 机构名称 | `organizations.name` ✅ | 必填 |
| 登录账号 + 密码 | 创建机构时可同时建首个机构管理员（`admin/organizations.js:143`） | 保留，但①必填密码由平台填（**不再默认 `org123`**）②可选「首次登录强制改密」 |
| 签约信息 | `contract_start_at/contract_expires_at` + `organizations` 其他字段 ✅ | 收敛成一张「签约信息」卡片（起止、状态、备注、附件可选） |
| 可创建老师数 / 学生数 | 老师：`base_teacher_seats + purchased_teacher_seats`（`admin/organizations.js:167-169`）；学生：**挂在套餐上**（`billing_packages.student_seats`，`admin/helpers.js:328`） | **统一到机构层级**：`student_seats` 从套餐搬到机构（与老师席位同一处管） |

⚠️ 现状的坑：老师席位与学员席位是**两套模型、两个页面**（机构页 vs 套餐页）。学生数目不在机构上，
而在被删掉「积分套餐」页面留下的套餐表里 —— 这正是要一起理顺的地方。

### 4.2 管理机构

平台可改：机构名称、重置密码、签约信息、可创建老师数 / 可创建学生数。
接口沿用 `PUT /organizations/:id`、`POST /organizations/:id/admins/:...`（改密）、`seat-adjustments`，
但**合并成一个「机构详情」页的四个区块**（基本信息 / 签约 / 席位 / 管理员账号），不再散在两个页面。

### 4.3 课包授权（新增「数量/库存」维度）

这是用户新增的核心诉求，现状**完全没有**：`course_assignments` 只有
`(series_id, org_id, status, assigned_at, expires_at)`，**没有数量概念**。

设计（两条轴，分开算）：

```
算力轴（钱） ：平台 ──算力池──▶ 机构 ──课时预算──▶ 课堂/学生 的实际消耗
许可轴（次） ：平台课包库存(10000 次) ──授权 N 次──▶ 机构 ──分给学生 M 次──▶ 学生获得使用许可
```

- 平台侧：`course_series.stock_total`（库存，如 10000 次）、授权时填 `quota_total`（授权多少次数）。
- 表：`course_assignments` 增加 `quota_total INTEGER`、`quota_used INTEGER DEFAULT 0`。
- 机构侧：机构把课包的「可用次数」分给学生 → 新增 `student_course_grants(id, org_id, student_id, series_id, lesson_id?, quota_total, quota_used, source_assignment_id, created_at, revoked_at)`。
- **门禁**：机构必须 `quota_used < quota_total` 才能把课包授权给学生（否则拒绝，错误码 `COURSE_QUOTA_EXHAUSTED`）。
  学生侧判定「能不能上这节课」= 原有班级课单链路 **AND** 该学生有剩余次数。
- ⚠️ 待拍板（重要）：**一次 = 什么？** 我建议「一个学生获得该课包（或课时）的一次使用许可」（消耗在授权那一刻，撤销可退回），
  因为它和「库存/授权」的语义一致；另一种口径是「一次 = 一次 AI 调用」，那就与算力轴重复了。**这条定了才能动表**。

- 现状链路要说清（避免做重）：今天机构把课包给学生，是靠**班级课单**：
  `course_assignments`（课包→机构）→ 机构把**课时**加进班级 `class_curriculum_items`（`orgAdmin.js:486-490`，
  写入时用 `accessibleLesson()` 校验授权）→ 学生通过 `class_members` 在班里 → 学生可用性 = 班课单 + 课包授权有效
  （`studentContext.js:241-251`）。**没有「课包→学生」的直连表**，也没有「学生换班后失去课」的痕迹。
  新的 `student_course_grants` 要么替代它、要么叠加在它上面 —— ⚠️ 待拍板（我倾向叠加：班级课单管「教什么」，grant 管「许可还剩几次」）。

## 5. 板块三：学生作品发布管理

**现状是两条并行链路，状态机还不一样**：

| | 画布作品 `works` | VibeCoding 作品 `vibecoding_submissions` |
|---|---|---|
| 状态 | `PENDING / APPROVED / REJECTED / PUBLISHED`（`schema.js:531`） | `PENDING / APPROVED / REJECTED` + `is_public` 布尔（`schema.js:1627`） |
| 发布广场 | `PUT /works/:id/plaza` 写 `status='PUBLISHED',is_public=1`（`admin/works.js:173`） | `PUT /vibecoding-works/:id/plaza` 只写 `is_public=1`（`admin/works.js:348`） |
| 下架 | `status` 改回 `REJECTED`（语义是「被拒」，不是「已下架」，`admin/works.js:144`） | `is_public=0` |
| 审核方 | 平台端（机构端审批入口也还在，`orgAdmin.js:674-693` → **双写冲突面**） | 平台端 |
| 提交入口 | 学生提交 → 机构审批申请 `work_publish_requests` | 学生提交即交给平台 |

**目标（合并成一套）**：
1. 统一状态：`已提交 / 已发布到广场 / 已下架（含原因）/ 精选`，其中「下架」**独立于审核状态**（不再复用 `REJECTED`）。
2. 平台端一页看两条链路，字段一致：**哪个机构、哪个学生账号、哪个课时、什么时候提交、当前状态、操作**（筛选：机构 / 课时 / 状态 / 时间）。
3. 去掉机构端审批（平台已是唯一审核方，`PlatformWorks.jsx:50` 明写「不再需要机构先审核」），
   `work_publish_requests` 表保留历史但不再产生新数据。

## 7. 板块五：算力总控（含 new-api 评估）

### 7.1 用户要的形态

> 平台配置好渠道、key 和使用的模型 → 做个网关 → 创建机构账号就分发一个 key → 机构创建学生账号再分发下面的 key
> → 能看到机构消耗、每个学生账号的消耗，也能算出每个课堂的总消耗，与「课时总预算」对应起来。

### 7.2 new-api 是什么、能不能接（结论：能接一半，要先 PoC）

**它是什么**：`QuantumNous/new-api`（原 `Calcium-Ion/new-api`，2026-09-11 访问 GitHub 时已转到 QuantumNous），
one-api 的二次开发，「大模型网关 + AI 资产管理系统」，GitHub 约 25k stars，
**许可证 AGPL-3.0**（GitHub API 实测 `spdx_id=AGPL-3.0`），Docker 部署（也发 Windows/macOS/Linux 单文件二进制），
SQLite/MySQL/PG 三选一，可选 Redis。最新版 `v1.0.0-rc.37`（还在 rc 阶段）。

**它已经有的（正好是我们要做的）**：

| 我们的需求 | new-api 的能力 |
|---|---|
| 配置渠道 / key / 模型 | 渠道管理：多渠道、多 key、**加权随机负载均衡**、失败重试、**模型重定向**、**自定义渠道可填完整调用地址** |
| 给机构/学生分发 key | **令牌（token）**：每个令牌独立配置**额度上限**、无限额度、**可用模型**、分组（含跨分组重试）、过期时间、IP 白名单、批量创建；额度耗尽后拒绝使用（状态机含「已耗尽」） |
| 看到机构/学生消耗 | **用量日志**（每次请求的令牌/渠道/模型/token 数/耗时/额度消耗）+ 数据看板 |
| 按预算拦停 | **令牌额度用尽即拒绝**（内置闸），另有「模型按次数收费」模式 |
| 我们那种自定义请求体 | **参数覆盖（param_override）**：按条件（可匹配模型）合并/覆盖下游 JSON，内置 `original_model` / `upstream_model` 字段 |
| 自定义异步上游 | **任务插件（Task Plugin）**：任务式 provider 体系（内置 MJ / Suno / 视频类若干），自定义厂商写插件（社区已有 `generic-rest` 通用协议插件） |

**它不适合直接接管的部分（风险点）**：

1. **自定义请求模板只「部分」能表达**。我们的上游是「同渠道不同模型不同请求体 + 不同提交/查询路径」
   （`billingConfig.js` 的 `modelRequestTemplates / requestTemplates / requestPaths / pollPaths`，为 MiniMax V2 / Mureka 摸索出来的）。
   请求体部分可以用**参数覆盖**表达；但**异步提交/查询路径**要靠任务插件（= 要写代码，且写了就受 AGPL 约束）。
2. **非 chat 模态的适配**。new-api 任务式（异步）provider 覆盖 Midjourney / Suno / 视频类（Kling、海螺、即梦、Vidu、Sora 等），
   我们用的是 MiniMax（视频/图）、Mureka（音乐）—— 是否在列表里、请求体是否对得上，**必须实测**。
3. **额度单位是它自己的 quota（按模型价格表折算）**，我们的诉求是「元」。
   把「这节课 50 元」翻译成令牌额度，需要先把模型价格表配准；按次计费好算，按 token 计费则要价格表可信。
4. **多一个服务 + 多一个数据库**。生产是 1.6GB 内存的 ECS（现在 available ~1.29GB），Go 网关本身很轻，但要评估；
   跑起来后我们的用量日志与它的日志是**两份数据**，要定谁为准。
5. **许可证是 AGPL-3.0**（见结论三），改它就要开源那部分；不改、只当独立服务用则只需提供其源码指向。
6. **合规与免责**：README 有「仅供个人学习使用/不提供技术支持」的免责声明，并提示不得向境内公众提供未备案的生成式 AI 服务。
   这是**你（产品方）要判断的**，不是技术问题，但必须写明。

**推荐路线（分三步，先 PoC 再定）**：

- **第 0 步（约半天，不碰生产）**：本地起 new-api（Docker 或单文件二进制），做四件事的 PoC：
  ① 建一个「自定义渠道」指向我们现用的上游，用我们的模型名，打一次 chat、一次生图、一次视频任务，
     看请求体（参数覆盖够不够）与异步路径（要不要写任务插件）能不能对上；
  ② 建一个令牌，设 1 元额度，把它打爆，看拒绝行为与日志里的消耗数字是否精确；
  ③ 用它的管理接口（或直接读库）拉一份用量日志，看能不能带上我们要的维度（令牌名 → 机构/学生/课时）；
  ④ 估一下内存与运维成本（要不要 Redis、数据库选哪个）。
  ⚠️ 本次**没能跑成 PoC**：本机 Docker CLI 有、但 Docker Desktop 守护进程没起（不想擅自在你的机器上拉起 Docker VM），
  且 Windows 侧出网被拦（连 GitHub release 超时）；只从 WSL 里读到了 GitHub API（所以许可证与资产清单是实测的）。
  真跑 PoC 需要：起 Docker Desktop，或在服务器上找个维护窗口用单文件二进制起一次（不占生产库）。
- **第 1 步（按 PoC 结论）**：若 chat/图能对上、视频/音乐要写插件 → **chat + 图片先接 new-api**，
  视频/音乐继续走我们自己的 `getGenerationProvider()`；两者都记到我们自己的用量表（保证「按课时归集」口径一致）。
- **第 2 步**：预算闸与归集落在 new-api（令牌额度）+ 我们自己的 `usage_records`（业务维度）双写，
  然后才动「删积分」。

### 7.3 key 分发模型（无论自研还是 new-api，都是这个形状）

```
平台（渠道/key 池）
  └─ 机构 key（机构级，额度 = 机构算力池）
       └─ 学生 key（学生级，额度 = 该学生可用算力）
            └─ （可选）课堂/课时 token（额度 = 课时算力预算）
```
- 现状的 key 存在**数据库之外的文件**里（`services/providerSecret.js`，AES-256-GCM，
  主密钥用 `AUTH_PEPPER` 派生；文件读失败会**静默降级为「没有 key」**），渠道元数据在 DB 的
  `platform_settings.ai_provider_policy` JSON 里 → 两个数据源靠 `channel.id` 关联。
  新设计要么把 key 也入库（加密列），要么把「读密钥失败」变成显式告警（现在是静默的）。
- ⚠️ 待拍板：**给机构/学生的 key 是「我们自己发的中转 key」还是「new-api 的令牌」**。
  两者都能实现，前者要求我们自己写校验与限额中间件（工作量大），后者白拿 new-api 的额度闸（推荐）。

### 7.4 三级预算闸 + 消耗归集（与 3.2④ 对应）

| 级别 | 预算来源 | 拦截位置 | 现状 |
|---|---|---|---|
| 课时 | `course_lessons.compute_budget_fen`（新） | 网关（按课时 token 剩余额度） | **从零做**（`session_credit_cap` 不生效） |
| 机构 | 机构算力池（新，替代 `org_billing_accounts.credit_balance`） | 网关（按机构 key 额度） | 现状是「积分余额」，扣费固定 1 分/次、与真实成本无关 |
| 学生 | 学生可用算力（新，替代 `users.ai_credit_limit / monthly_credit_allowance`） | 网关 + 应用侧（现行 3 处重复实现要收敛成 1 处） | 3 处重复 |

**归集维度**（用户明确要「所有机构每节课的实际消耗」）：
- 每次调用要能回答：**哪个机构 / 哪个学生 / 哪节课 / 哪个课时 / 哪个作品 / 花了多少钱**。
- 现状：`usage_records` 有 `org_id,user_id,class_session_id,project_id,generation_job_id,modality,model,status`
  → 前三项 ✅；**`work_id` 无人写入** ❌；**金额/token 没采集**（`input_tokens/output_tokens` 明确是空列）❌；
  VibeCoding 插画完全无记录 ❌。
- 所以要扩：①`usage_records` 增加真实成本列（上游返回的 token/次数 → 折算金额）②补 `work_id` 与 `lesson_id` 的写入
  ③插画也记一条。**这三处补完，「每节课花了多少」才有数据可看。**
