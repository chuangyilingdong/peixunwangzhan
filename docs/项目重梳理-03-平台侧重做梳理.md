## 0. 三条结论（先看这个）

**结论一：「每节课算力预算」目前事实上不存在，是从零实现，不是接线。**
`class_sessions` 有 `session_credit_cap`、`consumed_credits_total` 两个字段，也有机构端「积分上限」按钮，
但 `consumed_credits_total` **只在**一个孤立端点里累加（`apps/server/src/routes/ai.js:170`），
真实生成走的两条路（`aiGeneration.js` 异步 worker、`vibecoding.js` 对话）**都不累加** → 恒为 0 → 永远拦不住。
另外 `org_ai_budgets` 表是摆设（`assertOrgAiBudget()` 是空函数，`billingConfig.js:137-138`）。
所以「填了 50 元就能真拦住」这件事，必须新建预算闸（课时 / 机构 / 学生三级），并把它挂到**唯一的上游出口**上。

**结论二：积分不能先删，必须先建算力账。**
现在「积分」不只是账务，它同时是三处**刹车**：①课堂用量上限（`aiControls.js:34-35`，虽不生效）、
②成员个人上限（`ai_credit_limit`，**在 3 处重复实现**：`ai.js:143-146`、`aiGeneration.js:381-382`、
`vibecoding.js:169-170`）、③周期额度（`monthly_credit_allowance`，同样 3 处重复）。
另外 `billing_packages` 一张表同时扛着**席位 + 能力开关 + 月度额度**三件事，
删它会把 `PACKAGE_CAPABILITY_DISABLED` 这个能力闸一起删掉。
👉 顺序必须是：先做算力总控（能用新机制接住这三处刹车）→ 再删积分。

**结论三：new-api 值得接，但要接受它的许可证与「自定义上游」的边界；必须先做一个 PoC。**
new-api 正好是我们要做的东西（多渠道 / 多 key / 模型映射 / **按令牌限额** / 用量日志 / 重试与负载均衡），
拿它当「上游渠道池 + 按 key 的额度闸 + 用量日志」比自研省几周。三处必须提前知道的事：

- **许可证是 AGPL-3.0**（不是网上常说的 MIT/Apache-2.0，已用 GitHub API 核实：`spdx_id = AGPL-3.0`）。
  含义：① 原样部署、当成独立服务用 → 可以，但按 AGPL §13 要对使用者提供对应源码（未修改的上游版本指向官方仓库即可）；
  ② **只要改了它**（例如为我们的视频/音乐写一个任务插件），那部分改动必须按 AGPL-3.0 开源；
  ③ 我们的平台通过 HTTP 调用它，是独立程序、不算衍生作品（我们的代码不必开源）—— 但这是法律判断，正式商用前请法务过一眼。
- **我们的「自定义请求模板」有对应机制但不完全等价**：new-api 有**参数覆盖（param_override）**，
  支持按条件（可匹配模型，内置 `original_model`/`upstream_model` 字段）把 JSON 合并/覆盖进下游请求体 ——
  这能覆盖我们「同渠道不同模型不同请求体」的大部分需求；但**提交/查询路径**（MiniMax V2 那种 submit + poll）
  它走的是「任务式 provider」，自定义厂商要写**任务插件（Task Plugin）**（社区已有通用协议插件，如 `generic-rest`）。
- **额度单位是它自己的 quota**（按模型价格表折算），要把「这节课 50 元」翻译成令牌额度，需要先把模型价格表配准。

## 1. 目标与交互原则

**要解决的问题**（用户原话）：平台端/机构端/老师端后台「逻辑混乱、操作逻辑混乱、重复且不清晰」。

**原则（写下来当验收标准）**：
1. **一个概念只在一个地方管**。例：机构额度只在「机构管理」里管，不再同时在「机构管理 / 计费与用量 / 概览」三处出现。
2. **列表页 + 详情页各是一个路由**（可深链、可刷新、可后退）。现状是 `CourseManagement.jsx:826` 用 `useState` 在一个路由里切列表/详情，深链和后退都失效。
3. **术语统一**：现在「积分 / 魔法石 / 额度 / 配额」四种叫法混用（`Dashboard.jsx:51` 用「魔法石」、`:52` 用「积分」），三套「素材」同名不同物（宣传物料 / 画布素材 / 教学素材）。重做时每个概念只留一个词。
4. **危险动作显式确认**：发布、更新发布、下架、重置密码、撤销授权，都要有「影响谁」的确认文案。
5. **状态机统一**：同一种生命周期用同一套状态名（现在画布作品 4 态、VibeCoding 作品 3 态 + 一个 `is_public` 布尔，见第 5 节）。

### 3.2 课时（用户口径：名字 + 时长 + 上课类型 + 能力 + 素材 + 算力上限）

**① 上课类型改成「按课时、可多选」** —— 这是与现状最大的结构差异：

- 现状：`course_lessons.delivery_mode` 是**单值** `CHECK IN ('CANVAS','VIBECODING')`（`schema.js:264`），
  且课包层也有一份（`:249`）作为新课时默认值。学生端按「课时优先、单值互斥」判定可用性
  （`studentContext.js:305-306`：`canUseNow` 只认 CANVAS、`canUseVibeCodingNow` 只认 VIBECODING）。
- 目标：一个课时可**同时**勾选「画布」「VibeCoding」，学生进课时后自选一种。
- 改法（推荐，改动最小）：新增 `course_lessons.delivery_modes`（JSON 数组，如 `["CANVAS","VIBECODING"]`），
  读取侧先读新字段、缺失时回退旧 `delivery_mode`；学生端的两个 `canUse*Now` 改成读数组。
  **课包层的 `delivery_mode` 删掉**（语义模糊，只当默认值用）。
- ⚠️ 待拍板：同课时两种都开时，学生端是「进来先选」还是「两套入口并列」；以及作品归属（画布作品走 `works`、VibeCoding 走 `vibecoding_submissions`，两条链路的作品展示是否要在同一课时下并列，见第 5 节）。

**② AI 能力**：沿用 `course_lesson_capabilities(lesson_id, capability)`（白名单 `text/image/video/music`，`helpers.js:119`）。
改造点：把 `video` 与「音乐」的表达对齐到现在的实际模态（现有 `music`，播客/配音已下线），并把「按类型默认勾选」做出向导
（勾了 VibeCoding → 默认 `text`；勾了画布 → 提示是否要图片/视频）。

**③ 教学素材**：沿用 `course_lesson_materials`（画布素材/生成框体）+ `course_lesson_teaching_assets`（教师备课）。
改造点：`material_type` / `asset_type` **服务端现在零校验**（`helpers.js:125`、`:172` 只是 `toUpperCase().slice(0,30)`），
前后端还是两份枚举（`CourseManagement.jsx:25`、`:32`）→ 统一到服务端一份白名单并返回给前端。

**④ 算力上限（填钱，且实际生效）** —— 新增字段 + 新机制（口径已定：**按学生算**）：

- 新字段：`course_lessons.per_student_budget_fen INTEGER`（**每个学生**在这节课上的算力上限，如 5000 分 = 50 元）。
- 这节课的**总额度 = 单价 × 参与学生数**（机构加 5 个学生 → 250 元），用于看板与超支告警。
- 生效位置：**网关侧**（不是应用侧）。每个学生的调用走他自己的令牌额度，用完即拒；
  这样「一个学生 50 元」是硬闸，而课时合计只做汇总。见第 7 节。
- 额外要求（用户明确）：**能监控到所有机构每节课的实际消耗** → 需要按「课时 / 课堂 / 机构」三个维度归集实际花费，
  见 7.4。现状 `usage_records` 有 `class_session_id` 但没有真实金额/token（`input_tokens/output_tokens` 明确未采集），
  所以**必须扩采集**。

### 3.3 发布（创建完成后提示是否发布）

- 现状：`POST /course-series/:id/status` 只有 `publish` / `archive`（`courses.js:283`），发布前 `validateSeriesForPublishing` 校验
  「未归档课时必须全部 PUBLISHED / VibeCoding 课时必须开放 text / 生成框体模态必须在已开放能力内」。
- 目标：课时保存后弹「是否发布这节课？」；发布后课时即对学生生效；未发布的课时在课包详情里灰显。
- 保留现有校验（那三条校验都是踩坑得来的），但**错误提示要指到具体课时**（现在只返回一个错误码）。

### 3.4 编辑与版本（用户口径：每次修改填最新版本号 + 是否更新发布）

- 现状：`version` 是纯展示计数器，`bumpSeriesVersion`（`helpers.js:535-539`）在**任何**内容改动时自动 +0.1
  （改个标题也会 +0.1）→ 版本号快速膨胀且无区分度；**没有版本历史、没有快照、没有发布隔离**
  （已发布课包一改，已授权机构立刻看到新内容，`studentContext.js:141` 只看 `status='PUBLISHED'`）。
- 目标：
  1. 版本号**由人填写**（不再自动 bump），修改时必填「新版本号 + 变更说明」。
  2. 「是否更新发布」= 一次显式动作：不发布 → 只存草稿（对已授权机构**不生效**）；发布 → 生效并推给已授权机构。
  3. 「授权的机构以及外显层面都要全部更新」→ 发布后：机构端课时内容更新；官网课程广场（若上架）同步；在学班级不受影响（见下）。
- 需要的新东西：**版本快照**。推荐 `course_series_versions(series_id, version, snapshot JSON, note, created_by, created_at)`
  + 课时内容一并存入快照；学生/机构读到的是「当前已发布版本」，平台看到的是「草稿」。
- ⚠️ 待拍板：**正在上课的班级**要不要钉在旧版本（推荐钉：班级开课时记录 `series_version`，避免上课中途内容变化）。
  这是现有代码完全没有的能力，做与不做差别很大。

### 3.5 草稿隔离（「不点更新发布就看不到」）：做到哪儿了 / 卡在哪

**状态：已完成并发布（release `20260912T055309Z` / `8a5d2ab`）。** 下面保留设计与踩坑记录，便于以后改动时对照。

**目标**：平台端编辑的是**实时数据**；机构端 / 学生端 / 官网读的是**最近一次「更新发布」定格的快照**。
不点更新发布，他们看不到改动；点了立刻全端可见。

**设计（已在本地实现并大体验证过）**：
1. 两张表各加一列 `published_content TEXT`（课包与课时）。
2. `capturePublishedContent(seriesId)`（写在 `routes/admin/helpers.js`）：把课包字段 + 每个课时的
   内容（标题/简介/时长/正文/类型/算力预算/能力/素材/框体）序列化进这一列。
   调用点：**首次发布课包时**、以及**「更新发布」时**（都必须放在端点自己的 `transaction` **之外** ——
   里面再开事务会抛错，这个坑我踩了）。
3. `lib.js`：`normalizeLesson(row, { asPublished })` 与 `normalizeSeries(row, { asPublished })`
   支持用快照覆盖实时值（无快照 → 回退实时，老数据不受影响）；`lessonCanvasConfig(lessonId, override)`
   支持用快照里的能力/素材。
4. 读取侧只在三个地方传 `asPublished: true`：`studentContext`（课时上下文）、
   `communication/public.js`（官网课包详情）、`orgAdmin`（机构端课包列表与详情）；
   **平台端一律不传**（否则编辑界面会「改不动」）。
5. 学生端那条**逐列 SELECT**（`resolveStudentLessonContext`）必须把 `lesson.published_content`
   一起查出来 —— 这是第 6 次「字段丢在读取路径」了（我确实又漏了一次，被 p54 逮住）。
6. 列表类 SQL 里展示用的课时标题有 15 处，统一改成 `COALESCE(lesson.published_title, lesson.title)`
   （加了一列 `published_title`，避免在 SQL 串里塞 `json_extract` 的引号 —— 那会把 JS 字符串写坏，我踩过）。

**当时卡住、后来定位到的两个点（都很有代表性）**：
- `POST /course-series/:id/versions` 一度 500：真因是 **`capturePublishedContent` 没被 `courses.js` 导入**（ReferenceError），
  跟事务无关 —— 「模块导入测试 + 看服务端日志」两步就能定位，别靠猜。
- 课包资料层的隔离曾不生效：① `normalizeSeries` 把课时交给 `normalizeLesson` 时**没把 `asPublished` 传下去**
  （课时层就不隔离了）；② 脚本替换 `snapPick` 时**误伤了 `normalizePackage` 的 `priceFen`**（→ `/org/billing/packages` 500）。
  两处都靠守卫脚本照出来。

**验收（下次做完直接用这份清单）**：
1. 改课时但不发布 → 机构端与学生端读到**旧**标题；平台端读到**新**标题。
2. 点更新发布 → 机构端与学生端立刻读到**新**内容，「有未发布的改动」归零。
3. 改课包标题/价格但不发布 → 机构端读到**旧**值；发布后读到**新**值。
4. 老数据（没有快照）行为不变。

而在被删掉「积分套餐」页面留下的套餐表里 —— 这正是要一起理顺的地方。

### 4.2 管理机构

平台可改：机构名称、重置密码、签约信息、可创建老师数 / 可创建学生数。
接口沿用 `PUT /organizations/:id`、`POST /organizations/:id/admins/:...`（改密）、`seat-adjustments`，
但**合并成一个「机构详情」页的四个区块**（基本信息 / 签约 / 席位 / 管理员账号），不再散在两个页面。

### 4.3 课包授权（数量/库存 + 排课联动）

**你的口径（2026-09-11 补充，最终版）**：
1. 机构把课包分给一个学生 = **用掉 1 次**（机构次数 -1）。
2. **同一个课包不能对同一个学生授权多次**（去重）。
3. **每一节课，学生只能上一次**。
4. 老师排课时**只能挑「拥有该课包许可」的学生**；**已经上过这节课的学生不能再被添加**，
   判定依据 = **该学生提交过这节课的作品**。

两条轴（互不换算）：
```
许可轴（次）：平台课包库存 10000 次 ──授权 500 次──▶ 机构 ──分给学生（每次 -1，同一学生只一次）──▶ 学生持有许可
算力轴（钱）：课时「每学生算力上限」50 元 ──机构加 5 个学生──▶ 这节课 250 元 ──按调用归集实际消耗──▶ 看板与告警
```

**表设计**：
- `course_series.stock_total`：平台侧库存（如 10000 次）。
- `course_assignments` 增 `quota_total`（授权给机构多少次数）、`quota_used`（已分给学生多少）。
  **门禁**：`quota_used >= quota_total` 时机构不能再分给学生 → 错误码 `COURSE_QUOTA_EXHAUSTED`。
- **`student_course_grants`（新）**：`(id, org_id, student_id, series_id, source_assignment_id, granted_at, granted_by, revoked_at)`，
  **唯一约束 `(org_id, student_id, series_id)`** —— 呼应「不能授权多次」；撤销后重新授权沿用同一条、只清 `revoked_at`，
  这样「谁什么时候被授权过」有迹可循。
- **`class_lesson_students`（新）**：`(class_id, lesson_id, student_id, added_at, added_by)`，
  **唯一约束 `(class_id, lesson_id, student_id)`** —— 这就是「排课时挑学生」的那一层。
  ⚠️ 现状**没有**这层：学生进班（`class_members`）就自动算能上课，课堂 `class_sessions` 是**班级级**的
  （`schema.js:389`，没有 session↔student 关系表）。所以要新增，老师排课的界面要能筛人。

**排课候选学生的规则**（界面上直接显示「可选 / 不可选 + 原因」）：
```
可选 = 该学生在本机构持有该课时所属课包的许可（student_course_grants 有效）
     且 该学生没有提交过这节课的作品（works.course_lesson_id 或 vibecoding_submissions.lesson_id 任一有记录）
不可选原因写清楚：① 尚未被授权该课包   ② 已经上过这节课（已提交作品）
```
- 「已上过」跨班级、跨课堂判定：只要该学生在**任何**班级/课堂提交过这节课的作品，就不出现在候选里。
- ⚠️ 小口径待确认：学生提交后又撤回、或作品被下架，还算「已上过」吗？（我建议**算**：有记录即视为上过，
  否则老师侧名单会自己变。）

**撤销规则（2026-09-12 你的口径，最终版）**：
1. **机构侧不能撤销**：授权给学生 = 次数已经消耗，**不可逆**，机构界面不提供撤销入口。
2. **平台留兜底撤销**：平台管理员可以撤销某次授权（必填原因、写审计）。
   我的补充建议：撤销时若该学生**还没提交过**该课包任何一节课的作品 → **退回 1 次给机构**；
   已上过课 → **不退**（资源已消耗）。撤销后该学生从后续排课候选里消失，作品保留。
3. **换班**不影响课包许可（许可挂在「机构-学生-课包」上，不挂班级）。
4. **一节课只上一次**：`class_lesson_students` 的唯一约束 + 「提交过作品就不进候选」双重保证；
   同一节课在别的班级也不能再把这个学生加进去。

## 7. 板块五：算力总控（含 new-api 评估）

### 7.1 用户要的形态

> 平台配置好渠道、key 和使用的模型 → 做个网关 → 创建机构账号就分发一个 key → 机构创建学生账号再分发下面的 key
> → 能看到机构消耗、每个学生账号的消耗，也能算出每个课堂的总消耗，与「课时总预算」对应起来。

### 7.2 new-api 是什么、能不能接（结论：能接一半，要先 PoC）

**它是什么**：`QuantumNous/new-api`（原 `Calcium-Ion/new-api`，2026-09-11 访问 GitHub 时已转到 QuantumNous），
one-api 的二次开发，「大模型网关 + AI 资产管理系统」，GitHub 约 25k stars，
**许可证 AGPL-3.0**（GitHub API 实测 `spdx_id=AGPL-3.0`），Docker 部署（也发 Windows/macOS/Linux 单文件二进制），
SQLite/MySQL/PG 三选一，可选 Redis。最新版 `v1.0.0-rc.37`（还在 rc 阶段）。

**它已经有的（正好是我们要做的）**：

| 我们的需求 | new-api 的能力 |
|---|---|
| 配置渠道 / key / 模型 | 渠道管理：多渠道、多 key、**加权随机负载均衡**、失败重试、**模型重定向**、**自定义渠道可填完整调用地址** |
| 给机构/学生分发 key | **令牌（token）**：每个令牌独立配置**额度上限**、无限额度、**可用模型**、分组（含跨分组重试）、过期时间、IP 白名单、批量创建；额度耗尽后拒绝使用（状态机含「已耗尽」） |
| 看到机构/学生消耗 | **用量日志**（每次请求的令牌/渠道/模型/token 数/耗时/额度消耗）+ 数据看板 |
| 按预算拦停 | **令牌额度用尽即拒绝**（内置闸），另有「模型按次数收费」模式 |
| 我们那种自定义请求体 | **参数覆盖（param_override）**：按条件（可匹配模型）合并/覆盖下游 JSON，内置 `original_model` / `upstream_model` 字段 |
| 自定义异步上游 | **任务插件（Task Plugin）**：任务式 provider 体系（内置 MJ / Suno / 视频类若干），自定义厂商写插件（社区已有 `generic-rest` 通用协议插件） |

**它不适合直接接管的部分（风险点）**：

1. **自定义请求模板只「部分」能表达**。我们的上游是「同渠道不同模型不同请求体 + 不同提交/查询路径」
   （`billingConfig.js` 的 `modelRequestTemplates / requestTemplates / requestPaths / pollPaths`，为 MiniMax V2 / Mureka 摸索出来的）。
   请求体部分可以用**参数覆盖**表达；但**异步提交/查询路径**要靠任务插件（= 要写代码，且写了就受 AGPL 约束）。
2. **非 chat 模态的适配**。new-api 任务式（异步）provider 覆盖 Midjourney / Suno / 视频类（Kling、海螺、即梦、Vidu、Sora 等），
   我们用的是 MiniMax（视频/图）、Mureka（音乐）—— 是否在列表里、请求体是否对得上，**必须实测**。
3. **额度单位是它自己的 quota（按模型价格表折算）**，我们的诉求是「元」。
   把「这节课 50 元」翻译成令牌额度，需要先把模型价格表配准；按次计费好算，按 token 计费则要价格表可信。
4. **多一个服务 + 多一个数据库**。生产是 1.6GB 内存的 ECS（现在 available ~1.29GB），Go 网关本身很轻，但要评估；
   跑起来后我们的用量日志与它的日志是**两份数据**，要定谁为准。
5. **许可证是 AGPL-3.0**（见结论三），改它就要开源那部分；不改、只当独立服务用则只需提供其源码指向。
6. **合规与免责**：README 有「仅供个人学习使用/不提供技术支持」的免责声明，并提示不得向境内公众提供未备案的生成式 AI 服务。
   这是**你（产品方）要判断的**，不是技术问题，但必须写明。

**推荐路线（已按 2026-09-11 的 PoC 结论定案）**：

### 7.2.1 PoC 实测结论（2026-09-11，本地 Docker，未碰生产）

在本地起了 `calciumion/new-api:latest`（v1.0.0-rc.37），配一个**自定义 base_url 的渠道**指向我写的假上游，
建了带额度与模型限制的令牌，跑通「调用 → 消耗 → 耗尽拦截 → 日志」全链。14 项断言全过，
脚本留在 `E:\学习平台正常\.tmp\newapi-poc2.mjs`（不入库）。结论：

| 你要的事 | PoC 结果 | 证据 |
|---|---|---|
| 能配渠道 / key / 模型 | ✅ | 建了指向**我们自建地址**的渠道（非官方 OpenAI），渠道测连打到我们的假上游；模型名可自定义（`gpt-mock`） |
| 能给机构/学生分发 key | ✅ | 令牌可设**额度上限**、**可用模型**、分组、过期时间；48 位明文 key 可取出，上游收到的是**渠道里配的 key**（用户令牌不出网） |
| 额度用尽会拦住 | ✅ | 令牌额度 3000、每次消耗 1500 → 第 3 次直接被拒；令牌的「已用额度」同步增长 |
| 能看到谁花了多少 | ✅ | 用量日志带 `token_name`（→ 我们映射机构/学生/课时）、`model_name`、`quota`、`prompt_tokens/completion_tokens`、`channel_name` |
| 渠道出意外能切备用 | ✅（机制在） | 多渠道 + 加权随机 + 失败重试 + 一键禁用渠道；下游用的是同一个 base_url，**切渠道对机构/学生无感** |
| 按模型改请求体 | ✅（无条件）/ ⚠️（带条件） | **参数覆盖**真的改写进了上游请求体（实测 `temperature: 0.3` 出现在上游收到的 body 里）；但**带条件的写法**我按直觉写的 `mode:'eq'` 被拒（`unsupported comparison mode: eq`），正确 mode 待查官方文档 |
| 把「元」翻译成额度 | ⚠️ 有前提 | 模型**必须配价格**（`ModelRatio`），不配就 `model_price_error` **直接拒绝服务**；额度换算单位 `QuotaPerUnit` 可查；另有 `billing_setting.billing_expr`（计费表达式）与「按次收费」模式 |

**两条对设计有直接影响的发现**：
1. **「没配价格的模型一律不放行」** —— 这其实是好事：它逼我们把每个模型的单价配准，
   「这节课 50 元」才能换算成令牌额度并被真实拦截；但上线前**必须把价格表配全**，否则学生一调用就是错误。
2. **日志的归集维度靠「令牌名」** —— 所以令牌命名要有规范（例如 `orgA/stu-1024/lesson-7`），
   我们的看板按令牌名解析出机构/学生/课时；这也意味着**归集不依赖改 new-api 的代码**（AGPL 风险可控）。

**仍要做的事（PoC 没覆盖）**：
- 视频/音乐这类**异步任务**（提交 + 轮询）在我们的上游是自定义路径 → 要么用它的任务插件机制（要写插件 = 受 AGPL 约束），
  要么这部分继续走我们自己的 `getGenerationProvider()` 直连，只把用量记进我们自己的表。
- 令牌的**带条件参数覆盖**正确写法（查官方文档）。
- 生产部署形态（SQLite 还是 MySQL、要不要 Redis、内存占用）与故障切换演练（禁用主渠道看下游是否无感）。

- **图片路径**：走网关必须用 new-api 的 **`/v1/images/generations`（复数）**，我们自己的默认是单数
  `/image/generations` → 不覆盖就是 404，看起来还像「网关不支持图片」。
- **面向学生的错误文案**：额度耗尽在 HTTP 上是 403，直接透原始错误会显示
  「AI渠道认证失败…请在管理后台重新填写并保存该渠道 API Key」——真因（钱花完了）被完全盖住。
  所以归一化里把额度耗尽**排在认证失败之前**判、且**不拼上游原文**；VibeCoding 的 SSE 出错分支
  原来没归一化，也一起改了。

**上线前必须做的三件事**（代码已上线，但生产上的**网关开关是关**的 → 这条闸门在线上还没生效）：
1. 部署 new-api，配好渠道 + **模型价格**（不配价格它会直接拒服务，PoC 实测）。
2. 平台端「算力 → 算力网关」填地址/账号/密码并**启用**（启用后 TEXT/IMAGE 立刻全部走网关）。
3. 给要开课的课时填「每学生算力上限」（不填就不发令牌 → 走直连、不受额度约束）。

**仍未做**：视频/音乐不设闸（见上）；网关用量日志与我们 `usage_records` 的**对账**；
学生端看不到「我在这节课还剩多少」（网关上那张令牌的剩余额度，接口已有）；机构算力池的汇总页。

**「与课时总预算对应起来」这一步已经做了**（用户 2026-09-11 的原话就是「能算出每个课堂的总消耗，
与课时总预算对应起来」）：平台端用量面板里有一张「课时预算对照」表 ——
**总预算 = 每学生上限 × 参与学生数**（排课名单去重人数，机构加人预算自动放大），
**实际消耗**取网关日志按课时维度（`…/课时:<id>` 令牌）的合计，两者相除就是**使用率**。
⚠️ 两个要留意的边界：① 实际消耗那一列只含**走网关的模态**（对话/图片），
视频/音乐不在里面（所以使用率会**偏低**）；② 没排学生的课时不给百分比（避免出现 ∞%）。


### 7.3 key 分发模型（无论自研还是 new-api，都是这个形状）

```
平台（渠道/key 池）
  └─ 机构 key（机构级，额度 = 机构算力池）
       └─ 学生 key（学生级，额度 = 该学生可用算力）
            └─ （可选）课堂/课时 token（额度 = 课时算力预算）
```
- 现状的 key 存在**数据库之外的文件**里（`services/providerSecret.js`，AES-256-GCM，
  主密钥用 `AUTH_PEPPER` 派生；文件读失败会**静默降级为「没有 key」**），渠道元数据在 DB 的
  `platform_settings.ai_provider_policy` JSON 里 → 两个数据源靠 `channel.id` 关联。
  新设计要么把 key 也入库（加密列），要么把「读密钥失败」变成显式告警（现在是静默的）。
- ⚠️ 待拍板：**给机构/学生的 key 是「我们自己发的中转 key」还是「new-api 的令牌」**。
  两者都能实现，前者要求我们自己写校验与限额中间件（工作量大），后者白拿 new-api 的额度闸（推荐）。

### 7.4 三级预算闸 + 消耗归集（与 3.2④ 对应）

| 级别 | 预算来源 | 拦截位置 | 现状 |
|---|---|---|---|
| 学生 × 课时 | 课时上填的是**每个学生的算力上限**（新字段 `per_student_budget_fen`，如 50 元） | 网关（该学生的令牌额度） | **从零做**（`session_credit_cap` 不生效） |
| 课时合计 | = 单价 × 参与学生数（机构加 5 个学生 → 这节课 250 元），用于**看板与超支告警** | 汇总计算，不单独拦 | 无 |
| 机构 | 机构算力池（新，替代 `org_billing_accounts.credit_balance`），= 名下学生的预算之和与已消耗 | 网关（机构级 key 额度）+ 看板 | 现状是「积分余额」，扣费固定 1 分/次、与真实成本无关 |

（口径来自 2026-09-11 你的答复：**预算按学生算，机构加人则课时总额度自动放大**。
机构级不做独立闸，避免「机构池满了但某个学生还有预算」这种自相矛盾的状态；机构级只做汇总与告警。）

**✅ 2026-09-12 用户拍板（本节结论即为施工口径，已实现）：**
1. **池子按「学生 × 课包」** —— 一个学生在一个课包上就**一个**池子（不是一课一池）。
2. **四种模态都算进这一个上限**：对话 / 图片 / 视频 / 音乐共用。

**为什么闸门从网关搬到了应用侧**（这是这次拍板的必然结果，不是回头路）：
用户要「四种模态共用一个池子」，但**视频与音乐走不了网关**（异步任务要写 new-api 任务插件，
写了那部分受 AGPL-3.0 约束，见 7.2.3）→ **只有应用侧能同时看见四种模态**。
所以：**池子的权威账本在应用侧**（`usage_records.cost_fen` / `series_id`），
`services/computePool.js` 是唯一的闸门函数；**网关的令牌额度退化成宽松兜底**
（它只认得对话与图片，正常情况是应用侧先拦住）。

**记账口径（预扣 + 结算）**：
- 调用前 `assertComputePoolBudget()`：单价 × 本次次数（文档插画一次 3 张就是 3）与「已用 + 本次 > 上限」比较，
  超了就拦（`COMPUTE_POOL_EXHAUSTED`，文案给学生看：上限 X 元、已用 Y 元）；
- 调用后：成功按同一套单价记 `cost_fen`，**失败记 0**（不花学生的钱，但留一条记录）；
- **拦的时候与记的时候用同一个函数取价**，所以两边必然一致；
- 单价在平台端「算力网关」页配（`platform_settings.compute_pricing`，按**每次调用**估，
  四个模态各一个默认值，模型级可覆盖）—— ⚠️ 默认值只是让池子一上线就有数可算，**必须按实际渠道价改**；
  它是**预估**，与网关的精确账单口径不同（对账还没做，见下）。
- 课包没填「每学生算力上限」→ **不拦、只记账**；没有课包上下文的调用（如平台侧代写歌词）→ 不拦不记。

**「这节课的总预算」怎么算**：预算挂在课包上，所以「这节课」不再单独设预算；
面板里仍保留「课时预算对照」表，但口径要说清 —— 总预算 = 每学生上限 × 该课时排课名单人数。

**归集维度**（用户明确要「所有机构每节课的实际消耗」）：
- 每次调用要能回答：**哪个机构 / 哪个学生 / 哪节课 / 哪个课时 / 哪个作品 / 花了多少钱**。
- 现状：`usage_records` 有 `org_id,user_id,class_session_id,project_id,generation_job_id,modality,model,status`
  → 前三项 ✅；**`work_id` 无人写入** ❌；**金额/token 没采集**（`input_tokens/output_tokens` 明确是空列）❌；
  VibeCoding 插画完全无记录 ❌。
- 所以要扩：①`usage_records` 增加真实成本列（上游返回的 token/次数 → 折算金额）②补 `work_id` 与 `lesson_id` 的写入
  ③插画也记一条。**这三处补完，「每节课花了多少」才有数据可看。**

### 名词解释 A：「一次」是问什么

课包要设「库存 10000 次」，授权给机构 N 次，机构再分给学生。问题是**消耗掉一次「次」的动作是什么**：

- **口径一（许可次数，我推荐）**：机构把课包分给一个学生 = 用掉 1 次。学生拿到的是一份「可以用这个课包」的许可，
  之后这节课他上几遍、调多少次 AI，都**不再另扣次数**（AI 花的钱走算力轴，见下）。
  好处：与「库存/授权」的字面意思一致，机构一看就懂「我还有多少次能卖给学生」。
- **口径二（调用次数）**：学生每调一次 AI 用掉 1 次。这样「次」其实就是算力，会和算力轴重复，
  而且机构没法预估「一个学生要用掉多少次」。

**两条轴一起看**（这也是整套算力设计的关键）：
```
许可轴（次）  ：平台库存 10000 次 ──授权 500 次──▶ 机构 ──分给学生 1 次──▶ 学生获得该课包许可
算力轴（钱）  ：课时单价 50 元/学生 ──机构加 5 个学生──▶ 这节课上限 250 元 ──实际消耗按调用归集──▶ 看板与超支告警
```
👉 你要的「1 个学生 50 元、5 个学生 250 元」属于**算力轴**；「库存 10000 次、授权 500 次」属于**许可轴**。
两者独立记账、互不换算。

### 名词解释 B：「替代 vs 叠加」是问什么

现在学生能上某节课，是因为**机构把那节课加进了班级课单**（`class_curriculum_items`），学生进班就有。
新需求是「机构必须有可用次数才能把课包给学生」。这两件事的关系有两种做法：

- **叠加（我推荐）**：班级课单继续决定「这个班教哪些课时」（老师排课用），
  新的许可表决定「这个学生还有几次该课包的许可」。学生要上课 → 两条都得满足。
  好处：不动老师现有的排课习惯，许可只是多一道闸。
- **替代**：把班级课单整个换成「按学生发许可」，老师不再排课。
  风险：老师侧的操作方式全变，且现有 `class_curriculum_items` 的排课能力（顺序、来源课包）要重做。
