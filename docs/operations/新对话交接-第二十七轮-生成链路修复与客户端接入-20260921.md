## 二、这一轮做了什么

### A. 报错是怎么触发的（生产数据实锤）

一句话：**同一节课的"框体列表"，画布读实时、判定读快照。**

```text
学生画布上画出来的框体 + 右侧「课堂素材」
  ← normalizeProject() → lessonCanvasConfig(lessonId)        = 实时素材表（course_lesson_materials）
点「生成」时服务端校验 boxId
  ← studentContext → normalizeLesson(asPublished: true)      = 已发布快照 published_content
两边指向两批不同的 id → 学生「看得见新框体，点一下说不属于本课」
```

生产上到底几节课会报（只读诊断 `.tmp/diag-normalize.mjs`，**直接调用生产代码** `normalizeLesson`）：

| 课时 | 快照里有 `generationBoxes` 键？ | 实时框体 | 学生读面拿到 | 结果 |
|---|---|---|---|---|
| **1-1 AI 初识：召唤哪吒** | 有（11 个） | 11 个（**全新 id**） | 快照那 11 个旧 id | 0/11 相交 → 点哪个都报 |
| 其余 16 节（1-2、1-4…2-10） | **没有这一键** | 各有 2~13 个 | **0 个** | 判定侧拿到空数组 → 点哪个都报 |

⚠️ 这里有个**我上一轮（第二十五轮文档）没说准的地方**，记下来免得下次又踩：
`normalizeLesson` 对缺键的默认是**空数组**，不是"回退实时"——
`merged = snapshot ? { ...snapshot, generationBoxes: Array.isArray(...) ? ... : [] } : null`
所以"快照存在但缺这一键"的课，判定侧一个框体都不认。**一眼看不出**，只有让真代码跑一遍才知道。

**时间线**（1-1）：`course_lessons.updated_at` 与它全部素材/素材组的 `created_at` 都停在
**2026-09-20T08:53:23.968Z** —— 那一刻这节的素材被**整体重建**成一批新 id（服务端
`replaceLessonCanvasConfig` 本来是**保留 id** 的，注释写着"每次保存换新 id 会让学生端节点认不出来"，
前提是调用方把 id 传回来），重建之后**没有人对课包点「更新发布」**，快照还停在重建前那批 id 上。
当天 9:06–15:43 还有一串"单节课整体重建"（1-2、2-1、2-2、2-5…2-9 各一次）。

### B. 修法：读面与判定**共用同一个函数**

```text
lib.js 新增 mergedLessonCanvas(lessonRow, liveCanvas)
  · 快照里**有哪一档用哪一档**（capabilities / materialGroups / generationBoxes），缺的档回退实时；
  · normalizeLesson（判定侧）与 normalizeProject（画布侧）都改用它 —— 再也不各写一遍；
```

为什么缺键必须**回退实时**而不是给空数组：那 16 节课的快照是"发布早于生成框体这个功能"时定格的，
给空数组等于**把学生手里的框体全没收**（它们现在能正常用，正是因为两边都回退到同一份）。
这与第二十四轮「教学素材可见性」那条判据是同一个形状（逐键回退）。

### G. 客户端更新清单：按客户端那份《接入要求》逐条核 + 补的两处

客户端项目给了一份契约（`GET /downloads/manifest.json?t=` 免鉴权返回**合并后**的 JSON；后台只改策略字段、
文件身份字段由发布脚本生成；并列了「必须验证」十条）。实现提交 `d1d44a7` 已在分支上，
**现在完全归平台维护**（对方原话：「后续完全交给平台项目处理」）。逐条核对结果：

```text
① 公开清单     未登录 /downloads/manifest.json?t=… → 200 · application/json · 可解析         ✓
② 清单↔真包     size 308138555 与磁盘一致；sha256 e83a1cb5…1008 与磁盘一致；HEAD 200 可下      ✓
③ 写入原子性    另起进程猛读：写 300 次、读 299578 次，**一次半截 JSON 都没有**                 ✓（本轮补）
④ 后台生效      临时实例 PUT /api/admin/client-update → 清单文件立刻反映策略，
                且身份字段（版本/文件名/size/sha256）原样不动                                  ✓
⑤ 启动复写      清单被发布脚本整体覆盖后，策略能被复写回来（mandatory/minVersion 不丢）         ✓（本轮补）
```

**本轮补的两处（契约明确要求、原实现缺）**：

1. **原子写**（契约：「清单更新过程中不能出现半截 JSON」）：原来直接 `writeFileSync`，而客户端随时在
   带 `?t=` 读 → 改成**同目录**临时文件 → `fsync` → `rename` 覆盖（同目录是必须的：跨设备 rename
   会退化成拷贝，就不原子了）。
2. **策略另存 + 启动复写**：客户端发布脚本是**整体覆盖** manifest.json 的（只写身份字段），
   覆盖之后后台配的 `enabled/mandatory/minVersion/note/channel` 就没了 —— 即「每发一次客户端版本，
   后台策略被静默重置」。现在后台保存时把策略另存一份（清单旁边的 `manifest.json.policy.json`），
   **服务启动时只补差异复写回清单**（失败只记一行，绝不影响启动；身份字段永远由发布脚本说了算）。
   ⚠️ **仍有一个窗口**：发布脚本覆盖之后、平台下次重启（或后台点一次保存）之前，清单里是发布脚本那套
   默认值。要彻底对称，客户端那条发布流水线应改成**合并写入**（或发布后调一次后台保存）—— 已同步给对方。

**运维**（契约 3.4：服务进程用户要有权限改清单）：生产那份清单原来是 `root:root`（服务跑在
`ai-kids-prod`）→ 已 `chown ai-kids-prod:ai-kids-prod` 目录与清单，并**以服务用户身份实测**
（建临时文件 + rename + touch 都通过）。客户端发布脚本里本来就有 `chown ai-kids-prod` 那一行 ✓。

**守卫**：`p120-client-update-config` 从 4 条扩到 8 条（原子写机制 + 契约字段落盘 + 策略复写 +
并发读不断 JSON）。⚠️ 并发那条在 **Windows 上跳过并说明**：rename 覆盖一个正被别的进程打开的文件
在 Windows 会 EPERM，而生产是 Linux（POSIX 下 rename 原子、读的人拿旧 inode）——**这条证据只能在
Linux 上跑**，别在 Windows 上看到"跳过"就以为它没做事。
逐条跑生产的那份验收脚本：`.tmp/verify-client-manifest.mjs`（只读生产清单 + 临时实例指向清单副本）。

### H. 客户端运行时只认"这节课声明了 VibeCoding"（客户端项目报的门禁缺口）

客户端报的**属实**：平台建课时就定了上课类型，但 `apps/server/src/routes/studentRuntime.js` 的三个解析器
**什么都没筛** → 画布课也被当成"你现在能进的课"下发：`client-context.classroom` 有值、
**网关密钥照发**，客户端看到 `classroom != null` 就打开 VibeCoding 环境
（它拿不到类型字段，自己判断不了）。**这道门禁必须在服务端**：客户端只执行"平台下发的可进入结论"。

⭐ **判据用课时声明的类型，不用课堂那个单值** —— 这一条差点做错，记下来：

```
平台建课时：勾选框，可多选 → course_lessons.delivery_modes（只画布 / 只 VibeCoding / 两种同时）
老师建课堂：**只读展示**，跟着课时走（9-16 口径「老师不再选课堂模式」）——
           存进 class_sessions.delivery_mode 的是 publishedModes(课时)[0]，也就是"第一个"
⇒ 两者只在"两种同时开"时分叉：课堂那个单值是 CANVAS，而课时其实两种都开
```

第一版按客户端的字面要求筛 `class_sessions.delivery_mode = 'VIBECODING'`：单类型课时行为正确，
但**双开课时会被误挡**（网页两个入口都亮、客户端却回"当前是画布课堂"）。
改成 `deliveryModesOf(课时两列).includes('VIBECODING')`（与网页侧 `lessonAvailability` **同源**，口径 61）：

| 课时声明的类型 | 网页 | 客户端 |
|---|---|---|
| 只画布 | 只亮画布入口 | **不发密钥**（回 `CLASSROOM_MODE_MISMATCH`） |
| 只 VibeCoding | 只亮"去客户端" | 正常下发 |
| **两种同时** | 两个入口都亮 | **也放行**（这一版修掉的误挡） |

### I. 单文件上传上限 25MB → 200MB（用户要传 100MB+ 的课件 PPT）

用户问「创建课包上传素材最大多少，我有 100 多 MB 的 PPT 能传吗」→ 当时是 **25MB**（`FILE_UPLOAD_MAX_BYTES=26214400`），
传不了。按三层一起改：

| 层 | 改前 | 改后 | 说明 |
|---|---|---|---|
| **应用** `FILE_UPLOAD_MAX_BYTES` | 25 MiB | **200 MiB** | 代码里还有一层硬顶，同步 100MB → **200MB**（`MAX_UPLOAD_CEILING_BYTES`；env 只能往下调） |
| **nginx** `client_max_body_size` | 30m | **300m** | 必须 > 应用上限，否则轮不到我们说中文、只给一句裸 413（sites-enabled 与 sites-available **两份都改了**） |
| **Cloudflare** | — | 不参与 | 域名现在是 **DNS-only**（公网解析直给源站 IP、nginx 没配 real_ip、日志无 cf-ray）→ 它那层 100MB 上限今天不适用 |

**真正的约束不是读 body，而是病毒扫描**（这次量出来的，也是新加两道保护的原因）：

```text
clamscan 每次调用都要把病毒库读进内存：扫 150MB 文件 峰值 RSS ≈990MB / 9.4s
⇒ 一次 200MB 上传的峰值 ≈ app 400MB + 扫描 1GB ≈ 1.4GB，而机器只有 1.6GB（可用 ~1.1GB）
```

所以同期补了两条**守卫机器**的机制（不是可选项，是 200MB 的前提）：

1. **读 body 之前的内存闸**（`services/uploadBodyGate.js`）：默认「同时 2 份 / 合计 256MB」——
   一份 200MB 天然互斥；超了当场 429 `UPLOAD_BUSY`（中文），**不走到分配内存那一步**；
   名额在请求结束（finish/close）归还，release 幂等。
2. **扫描器包一层内存上限**：`/usr/local/bin/clamscan-limited`（`ulimit -v 1.3GB` + exec clamscan）；
   内存真不够时让**这次扫描失败**（应用回「文件安全扫描失败，上传已拒绝」），而不是让内核 OOM 去挑受害者
   —— 这台机器上 OOM 挑走过学生的创作环境。`FILE_UPLOAD_SCANNER` 指向它。
   另把扫描超时 120s → **240s**（150MB 实测 53s，机器忙时要留余量）。

**实测（新配置下，端到端）**：

```text
① 穿过 nginx 发 120MB 请求体      → 返回**应用自己的 400**（不是 nginx 413）✓ nginx 那道已抬上去
② 生产 env 值起临时实例、真传 150MB → HTTP 200 / 60s，落盘字节 157286404 与源文件一致 ✓
③ 并发两份 150MB                   → 第一份 200 ✓，第二份 429 UPLOAD_BUSY（不是 OOM）✓
   过程中可用内存最低 ~90–125MB（峰值几乎全是 clamscan 的 ~990MB）
```

**守卫**：`p10-file-upload-security` 补三组（硬顶 200MB 且 env 越不过去、超限文案用配置值、
内存闸「2 份/256MB」的四条边界 + release 幂等 + 归零）。

⚠️ **两条遗留（都记进 §五）**：
1. **机器内存薄**：一次 200MB 上传的峰值把可用内存压到 ~90MB。要么**扩容**（这台机器上面还挂着
   「学生环境被 OOM 杀掉」那段事故），要么把上限往回收 —— 现在能跑，但没有余量。
2. **ClamAV 病毒库 16 天没更新**（`/var/lib/clamav/main.cvd` 是 9-05 的，扫描时 ClamAV 自己会警告
   「database is older than 7 days」），而且**没有 freshclam 定时任务** —— 等于拿两周前的库在扫。

### J. 视频「参考」的语义修好了 + 四类框体的数字进度条（用户同一天提的两条）

**① 「视频生成出来跟参考也不一样啊。完全是两种东西啊」** —— 学生把《清明上河图》连到视频框体、
写「图片动起来」，出来的是一段毫不相干的画面（另一个人物场景）。

排查结论（**先排掉了两个看起来很像的假设**，别重复走）：

```text
✗ "参考没发出去" —— 生产那个模型级模板里 `{{referenceItems}}` 是**在的**
  （content: [ {text:{{prompt}}}, {{frameItems}}, {{referenceItems}} ]），图确实发出去了
✓ 真正的根因是**语义错了**：MiniMax-H3 在生产上声明了四种输入方式（含 OMNI_REFERENCE），
  而客户端只要看到"支持全能参考"就一律把连过来的图当**参考**发 ——
  可"参考"在上游是"启发素材"（画一段像它的），不是"这张图动起来"（**首帧**）。
  学生那句「图片动起来」要的是后者。
```

改法（判定收成**一处** `videoInputPlan`，生成 payload 与面板那行提示都读它 —— 口径 61 同源）：
**能当帧就当帧** —— 连过来的全是图片、1~2 张、模型也支持帧 → 走**首帧**（+尾帧）；
够不着的（多张图 / 视频 / 音频混合参考）才走全能参考。
顺带修一个真 bug：尾帧判定原来写的是 `LAST_FRAME`，而模态值是 **`FIRST_LAST_FRAME`**
（服务端 `acceptsLastFrame` 看的是后者）→ 尾帧永远不亮，客户端与服务端口径又不一致。

同时把视频这条的两处静默补齐（与图片那条 9-17 的口径对齐）：
· 默认模板新增 **`VIDEO_OMNI`**（带 `{{referenceItems}}`）—— 原来**没有任何默认模板**能承载全能参考；
· `generationOptionsFor` 的视频分支加「模板带不了参考就**当场拒绝**」（原来只有图片分支有）。

**② 「能否增加个数字进度条：小灵施展魔法中 1%」** —— 四类框体（文本/图片/视频/音乐）都加上了：
底部一条细进度条 + 「小灵施展魔法中 N%」（`.learning-node__progress`）。
⚠️ **这不是上游的真实进度**：上游只回状态、我们也没存过原始响应（只有 request/payload id），
所以百分比是按**实测中位耗时**估的 —— 生产 `generation_jobs` 实测：图片中位 45s（最长 82s）、
文本 2s、视频 132s，音乐取 90s 量级；**封顶 95%**，最后 5% 留给真正的完成事件，
不出现"进度满了还在等"的假完成。要真进度得让上游回 progress 并加列存（见 §五 遗留）。

**守卫**：p109 补 5 条（默认模板带得动参考、参考真进请求体、没参考时形状不变、显式模板带不了就拒绝、
以及客户端四条：能当帧当帧 / 尾帧用 `FIRST_LAST_FRAME` / 面板与 payload 同源）。
截图验过：夹具把视频框体置成「40 秒前开始生成」，画布上显示「小灵施展魔法中40%」+ 进度条 ✓。

### L. 事故：发布重启打断了在途生成（用户报「上游已经扣钱了，但是这边不返回了」）

用户原话：「现在生视频你修改后，等了一会，上游已经扣钱了，但是这边不返回了。下面的报错之前是：
视频正在生成xxx，但是一直不显示出来，再点击再次生成，也不行了」。

**现场（生产库实查，时间线对得上）**：

```text
07:00:38Z  学生点了「生成短片」→ 任务入队、worker 认领、上游受理（会计费）
07:02:12Z  **发布重启了服务** ← 就是这一轮我自己的那次发布
之后       任务永远停在 RUNNING：没人再接它 → 结果拿不回来；
           而 assertBoxNotGenerated 把"在途任务"也算占用 → 框体被判「该生成框体已经生成过了」
           → 学生**再也点不动**（他说的"再点击再次生成也不行"就是这个）
```

**为什么兜底没接住**：`initializeAsyncGenerationQueue` 当时只回收**租约过期（>5.5 分钟）**的 RUNNING，
而重启那一刻这条任务才 **94 秒** → 被跳过 → 之后再也没有任何东西看它。

**改法（按 worker 判，不按时间猜）**：`worker_id` 里带进程号（`ai-worker-<pid>-<rand>`），
所以**本进程刚起来时，任何 RUNNING 都属于已经没了的那个 worker**：
· 启动时 `interruptOrphanedJobs()` 一律收成 FAILED（码 `GENERATION_INTERRUPTED`，文案给学生看：
  「生成过程中服务重启了，这次的结果没拿到（上游可能已受理）；请重新点一次生成」）
  → 框体随之解封（FAILED 不算占用 ✓ 学生可以重试）；
· **关服钩子**（SIGTERM/SIGINT）也收一次自己的在途任务 → 重启后立刻是"可重试"状态，不必等下次启动；
· 旧的租约判据保留，作为**崩溃**（没走关服钩子）的兜底。

**本次事故的收尾**：那条任务用同一个码/文案标成 FAILED，框体的在途数归零 ✓（学生已可重新生成）。
⚠️ **账上注意**：`usage_records` 里**没有**这笔成本（我们的账本没记到），而上游可能已经计费 ——
这类"上游扣了、我们没记"的差额只能靠官方账单对账找回来（见 `docs/operations/真实三账对照-20260914.md`）。

**守卫** p4-o12 加一条**带反向自检**的用例：造一条"别的 worker 认领、才开始 10 秒"的 RUNNING
（旧判据不会管它）→ 服务启动后必须 FAILED/`GENERATION_INTERRUPTED`、且该框体在途数归零。
摘掉回收调用时这条会红（实测：孤儿仍 RUNNING、在途=1 —— 正是用户看到的现象）。

## 三、不许破的口径（承接 1–60；**本文新增 61–70**）

61. ⭐⭐ **同一份东西的"读面"与"判定"必须同源**：学生画布画的框体、与点生成时服务端校验 boxId 用的
    列表，**必须是同一个函数的输出**（`mergedLessonCanvas`）。这一条与口径 34/54 是同一族
    （「界面看得到、点开说无权」/「预检与真正那一步不同口径」）——**写两处迟早会漂**，这次漂的代价是
    17 节课的框体点不动。
62. ⭐ **"缺键给空数组"与"缺键回退实时"是两个语义，选错就是静默事故**：快照缺某键时，
    **给空数组 = 把用户手里的东西全没收**（那 16 节课的框体），**回退实时 = 老数据行为不变**。
    老数据（发布早于该功能）要的是后者；「已定格的课包不允许回退」只适用于**可见性判据**
    （第二十三轮），**展示/可用性**一律逐键回退。
63. ⭐ **"要人知道的状态"必须放在**看得见的那一层**上**（用户 2026-09-21：「有修改未发布的应该在
    版本发布这里有明显的提示，而不是点进去才看得到」）。判据与它所指的那处**共用同一个值**
    （`hasUnpublishedChanges`），别各算一遍；角标要能在**选中态**下也看得清（紫底上换半透明白）。
64. ⭐ **画布左侧「生成框体」一眼可辨：四周一圈金色**（border + box-shadow 各一圈，四边完整；
    悬停换色不吃掉它）。**只区分"是不是生成框体"**，模态色（生图/生视频/生音乐）照旧
    —— 那是 2026-09-17 的口径，两条都要在。
66. ⭐⭐ **"能不能进"这类结论必须在服务端定，并按对象类型限死**：客户端运行时（dsh / VibeCoding）
    **只认"这节课声明了 VibeCoding"**（课时类型**可多选**）—— 画布课不下发 `classroom`、
    不下发网关密钥、也不许交作品；**两种同时开时客户端这一侧也放行**。
    ⚠️ **别拿 `class_sessions.delivery_mode` 判**：那只是"跟着课时带的第一个"（老师不再选课堂模式，
    只作历史兼容），用它判会把双开课时误挡（网页两个入口都亮、客户端却回"当前是画布课堂"）。
    客户端拿不到的字段（如 `deliveryMode`）绝不能成为它的判断依据；它只执行平台下发的结论。
    多课堂时**先按类型过滤候选**，点名了不对类型的那节要**明说**（`CLASSROOM_MODE_MISMATCH`），
    绝不静默换成另一节。
65. ⭐⭐ **静态清单是客户端的唯一真相源，两个写方各写一半、谁都不许覆盖对方那半**：
    后台只写**策略**（enabled/mandatory/minVersion/note/channel），发布脚本只写**身份**
    （version/files.name/size/sha256/publishedAt）。当前实现靠"策略另存 + 启动复写"兜住发布脚本的
    整体覆盖；**写这份清单必须原子**（同目录 temp → fsync → rename），因为客户端随时在读它。

67. ⭐⭐ **上传上限有三层，且真正的约束常常不是"读 body"**：应用（`FILE_UPLOAD_MAX_BYTES`，硬顶 200MB）
    **必须小于** nginx 的 `client_max_body_size`（300m）—— 这样"文件太大"这句中文才轮得到我们说；
    Cloudflare 代理时它还有一层 100MB（今天域名是 DNS-only，不参与）。
    ⚠️ 而这个规模下最吃内存的是**病毒扫描**（clamscan 每次加载病毒库 ≈1GB）：
    抬上限必须同时看机器 RAM，并保证有「**读 body 之前**的内存闸」（`uploadBodyGate.js`）——
    否则两份大请求叠起来就是 OOM，而被 OOM 挑走的不止这个进程。
68. ⭐⭐ **"连过来的素材怎么用"是语义问题，不是传输问题**：视频框体上连一张图，
    学生说「图片动起来」= **首帧**（i2v）；只有多素材/视频/音频混合才叫**参考**（启发素材）。
    模型"支持全能参考"不等于"该走参考"——**能当帧就当帧**（`videoInputPlan`）。
    同类提醒：模态值是 `FIRST_LAST_FRAME`（不是 `LAST_FRAME`），客户端与服务端必须用同一串。
69. ⭐ **同一个上游的不同代模型，请求体形状可能不一样 —— 内置模板要按模型名给**：
    2.5 系图片模型把 `output_format`/`resolution` 放**顶层**，2.0 收的是 `metadata` 里那套
    （2026-09-21 用户报「2.5 报错、2.0 正常」）。`requestTemplateFor` 的优先级固定为
    **渠道/模型上配过的 > 内置按模型 > 内置按模态** —— 管理员配过的永远赢，内置只兜底。
70. ⭐⭐ **在途任务必须在"进程边界"上收尾**：启动时收**孤儿**（`worker_id` 不是本进程的一律收掉）、
    关服时收**自己的**。只按"租约过期"回收会漏掉**年轻孤儿** —— 而年轻孤儿的表现最坏：
    上游的钱花了、结果拿不到、**入口还锁着**（框体被判"已经生成过了"，学生点不动）。
    收尾要给**学生看得懂**的码与文案（`GENERATION_INTERRUPTED`「服务重启了…请重新点一次生成」），
    别写"请核查后人工处理"那种给自己看的话。

## 四、这一轮踩过的坑（承接 1–75；**本文新增 76–86**）

76. ⭐⭐ **诊断要直接调用生产代码，别拿自己的 JSON 判断去推**：我第一版诊断脚本用
    `JSON.parse` 自己判"快照缺这一键时读面是不是回退实时"，推断成"回退实时 → 那 15 节没事"，
    于是只报了 1 节课；后来改成**在副本上真的 import `lib.js` 调 `normalizeLesson`**，
    才看清是**17 节全中**（缺键给的是空数组）。**差一点就按错的范围去修**。
77. ⭐ **发布按 HEAD 走，会把别人"还没打算部署"的提交一起带上线**：这次就带上了另一个会话的
    客户端更新后台配置（他文档里写着"尚未部署"）。发布前扫一眼
    `git log --oneline origin/<branch> -3`，看清 HEAD 里都有谁的东西；影响评估与处置见 §二.F。
78. ⭐ **平台差异会伪装成"测试通过"**：原子写的并发证据在 **Windows 上根本跑不了**
    （rename 覆盖一个正被别的进程打开的文件会 EPERM），只能跳过 —— 而生产是 Linux。
    同一条还有反例：同一份 `setInterval` 读取在同步写循环里**一次都不会跑到**（事件循环被占死），
    于是"没读到半截 JSON"其实是**空转通过**。**写这种并发证据时一定要断言"读的人真的读到了"**
    （本轮两处都是这么发现的）。

79. ⭐ **给一条路上了闸之后，守卫的夹具也要跟着改**：p118/p119 的夹具原来只把**课时**改成
    VIBECODING，**没改课堂**（课堂是夹具按当时还是画布课的课时建的）—— 门禁一上，它们就被自己的
    门禁挡住（红在"client-context 没给出课堂"）。**先认出这是夹具不真实，别去松门禁**：
    真实的开课流程里课堂类型是跟着课时走的（`orgAdmin` 建课堂时按课时的 `deliveryMode` 取）。

80. ⭐ **nginx 的 `include sites-enabled/*` 是通配的 —— 备份文件不能放在那个目录里**：我给
    `sites-enabled/iicili.cyou` 做备份时顺手 `cp` 成 `iicili.cyou.bak-…`，于是它**也成了一块启用的
    server 块**（`nginx -t` 立刻报 `conflicting server name`）。这次靠"真文件按字典序排在前面"没出事，
    但下次顺序一变就是"改了配置不生效"。**备份一律放 `/etc/nginx/backups/`**（历次都放那儿）。
81. ⭐ **用 curl 量"到底谁挡的"要看穿透结果，别看 `%{http_code}` 一个数**：`--data-binary @-`
    会先把 stdin 整个读进内存再发（120MB × 1 次 = curl RSS 139MB、耗时 2 分钟），
    而 `%{http_code}` 遇上 `Expect: 100-continue` 会报 **100**（我第一版就把它当成了"返回 100"）；
    真正可信的是 **nginx access.log 里的那一行**（400 = 应用回话 / 413 = nginx 挡住），
    顺便还能看出是谁挡的。
82. ⭐⭐ **别把"看起来最像的那个假设"当根因**：这次用户报「视频跟参考完全不一样」，
    我第一反应是"参考没发出去"，也真的找到了一个成立的机制（默认视频模板里没有 `{{referenceItems}}`）
    —— 正准备按它修时，把**生产策略 dump 全**（第一次的输出被 `head` 截断了 12 行）才发现：
    那个渠道配了**模型级模板**、里面 `{{referenceItems}}` 好好地在，图确实发出去了 ✗。
    真因是语义（当参考发而不是当首帧发）。**教训：先把配置/数据 dump 全、看到全貌再下结论**；
    截断的输出会替你造一个通顺但错误的因果。
83. ⭐ **上游的报错原文就是线索，别急着猜**：`output_format is not supported by this model` 一句话
    就把字段名点出来了（我们把它塞在 `metadata` 里，2.5 只认顶层）。同一条也提醒：
    **别把参数一股脑塞进 `metadata`** —— 那看着"稳妥"，其实每换一代模型都可能踩雷。
84. ⭐ **窄屏下 flex 行里的按钮会被压到只剩一列字宽，中文按字折行 = "按钮变形"**：
    按钮要 `white-space: nowrap` + `flex: 0 0 auto`（同行的说明文字让它自己去换行）。
    （口径 57 那条"窄列要 nowrap"是同一个毛病的另一处；这次是按钮，不是表格列。）
85. ⭐⭐ **`set -o pipefail` 会让 `sed … | head -1` 静默中止整个脚本**：head 读完就关管道，
    sed 收到 SIGPIPE 退出非零 → 管道非零 → `set -e` 把脚本带走。表现是
    **"把该做的事都列出来了、然后什么都没做"**（本轮 `prune-releases.sh` 就是这个：
    列出了要删的 release、一条都没删）。给这种管道加 `|| true`，或者别用 head 截。
    **凡是"打印了计划却没执行"的脚本，先怀疑这一条。**
86. ⭐⭐ **在这台机器上「发布 = 重启服务 = 打断所有在途生成」**：本轮就真打断了用户的一条视频
    （上游已受理、会计费，结果拿不回来）。**发布前先看一眼在途任务**：
    `SELECT id,modality,status FROM generation_jobs WHERE status IN ('QUEUED','RUNNING')` ——
    有就等它跑完（视频 ~2 分钟）再发。兜底（口径 70）会让"被打断"变成"可重试"，
    但**钱已经花了**，而且 `usage_records` 里不会留下这笔成本（我们的账明明少了钱却看不出来，
    只能靠官方账单对账找回来）。
