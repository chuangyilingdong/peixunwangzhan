# 除了视频，其他模态/性质有没有同样问题（2026-10-30）

## 〇、结论

**有，而且生产上已经发生过。**

画布生成的 `TEXT / IMAGE / MUSIC / VIDEO` 四种模态**全部走同一个异步生成队列**
（`POST /api/ai/generations/async` → `asyncGenerationQueue` → 同一个 worker 池）。
所以视频把队列占满时，图片、文本、音乐一起排队。

生产实证（2026-10-30）：

| 图片任务 | 创建 | 实际开始 | 等待 |
| --- | --- | --- | --- |
| `generation_0ff86ed0...` | 08:47:14 | 09:48:15 | **61 分钟** |
| `generation_06519156...` | 09:04:59 | 09:48:56 | **44 分钟** |
| `generation_17043607...` | 09:05:22 | 09:49:31 | **44 分钟** |

这三条图片本身只跑了约 **50 秒**，前面全在等 H3 视频任务。

但不同“性质”的链路不一样，不能一概而论。下面按类型拆。

---

## 一、按模态/性质拆开

| 类型 | 走哪条链路 | 产物/耗时（生产实测或代码） | 是否有“同一个队列被视频拖住”的问题 | 额外瓶颈 |
| --- | --- | --- | --- | --- |
| **视频 MiniMax-H3** | 画布 async 队列 | 20–22MB / 7分50秒–9分25秒 | 源头；最重 | 20GB/1000 的结果回传；当前 1.3MB/s 入口要 4.3h |
| **图片 zhenzhen-image** | 画布 async 队列 | 约 2.9MB / 50 秒 | **有**，今天实测被 H3 拖 43–61 分钟 | 1000 张 2.9GB；按 1.3MB/s 收盘约 37 分钟；内容审核失败率高 |
| **音乐/音频（画布 MUSIC）** | 画布 async 队列 | 生产近一周无记录；按代码走同一队列与媒体归档 | 代码上**有**；视频会挤占 worker | 具体大小/耗时需用真实模型测；归档仍需流式 |
| **文本（画布 TEXT）** | 画布 async 队列 | 生产近一周无记录；无媒体归档 | 代码上**有**；文本会被视频挤占 | 无 20GB 归档问题；但队列公平性必须解决 |
| **VibeCoding（对话/写代码）** | `vibecoding.js` 的 `streamAssistantReply`（SSE） | 文本/文件；无 20MB 视频归档 | **不是**这条 8-worker 队列 | 1000 路并发 SSE/API/文本模型 QPS；提交产物走上传闸 |
| **PPT/Word/Excel 文档** | VibeCoding 产物 + 文件存储 | 文本/文档，通常远小于视频 | 不是这条队列 | 文档预览/LibreOffice 转换 CPU；上传闸 |
| **学生上传/提交作品** | `reserveUpload` + 文件存储 | 单文件上限较大 | 不是生成队列 | **同机构同时上传上限 3**（`FILE_UPLOAD_MAX_CONCURRENT=3`，用户和机构各算一份）；1000 人同机构同时传，绝大多数会收到 `UPLOAD_CONCURRENCY_LIMIT` |
| **画布自动保存/课堂轮询** | 普通 API + MySQL | 小请求 | 不是生成队列 | 1000 学生 × 5 秒轮询 = 200 RPS；单进程/连接池需压测 |
| **招生军师数字人/音频** | `junshiWorkbench` 的音频/视频任务 | 独立任务 | **不是**这条队列 | 自己的上游、轮询与并发；若 1000 路要单独评估 |

## 二、图片：同款队列问题 + 一个更严重的独立问题

### 2.1 队列被视频拖住（已有生产证据）

见上表：图片任务 08:47/09:04/09:05 创建，09:48/09:49 才开始；单条图片 50 秒。
原因就是 `asyncGenerationQueue` 不分模态，H3 视频每条 8–9 分钟，8 个视频就能把 8 个 worker 全占住。

**8 路并发只是把“视频串行”缓解了，没有做模态隔离**：只要有 8 条 H3 同时在跑，
新来的图片/文本仍可能等 8–9 分钟；1000 条视频排队时，图片会被无限往后推。

### 2.2 图片内容审核失败（与并发无关，但更常见）

最近一周 `zhenzhen-image-g-v2.5-lowprice`：

```text
SUCCEEDED 21 条，平均 51.5 秒
FAILED    19 条（约 47.5%）
```

今天 24 条图片：13 成功、11 失败（约 46%）。失败原因：

- 9 条 `GENERATION_PROVIDER_RATE_LIMITED`：上游提示“同一输入 24 小时内已有 2 次内容审核失败，进入 12 小时冷却期”；
- 2 条 `GENERATION_PROVIDER_UPSTREAM_ERROR`：生成结果未通过内容审核。

这不是队列/并发问题，是**上游内容审核 + 同输入冷却**。如果学生在做老照片/人脸类素材，尤其容易触发；
学生看到的是“没生成出来”，但实际是审核拒绝。需要：换模型/换提示词/换参考图，或者平台提供审核原因与重试引导。

## 三、其他性质的硬限制（容易被忽略）

### 3.1 学生上传/提交：同机构同时 3 路

`uploadLimits.js` 的 `FILE_UPLOAD_MAX_CONCURRENT` 默认 3，**按用户和机构各算一份**：

```text
同一个机构里，同时进行的上传最多 3 个
```

正常“一次传一个”不会撞到；但 1000 个同机构学生同时提交作品/上传素材，绝大多数会直接收到
`UPLOAD_CONCURRENCY_LIMIT`（429）。这不是生成队列，但同样会让“1000 人同时上课”失败。
要支持 1000 人同机构上传，需要改成队列/更高上限，并压测 OSS/nginx/DB，不能只把 3 改大。

### 3.2 VibeCoding：不是这条队列，但也有 1000 路问题

`vibecoding.js` 走 `streamAssistantReply`，不经过 `asyncGenerationQueue`；没有 20GB 视频归档。
但 1000 路同时对话意味着：

- 1000 条 SSE 长连接 + 文本模型 QPS；
- 单 Node 进程/4 vCPU 的 API 能力；
- 提交产物走上传闸（同机构 3 路）；
- 客户端/沙箱运行时的并发。

它需要单独的水平扩展与压测，但不是“视频把图片拖住”那个问题。

### 3.3 文档/PPT/Word/Excel

走 VibeCoding 产物与文件存储，通常没有 20MB 视频归档；但文档预览/转换（LibreOffice）是 CPU 密集，
1000 份同时转换会打满 4 vCPU，需要单独限流/队列。

## 四、建议的改法（按优先级）

1. **按模态拆队列**：视频一个池、图片一个池、文本/音乐一个池，或共享池 + 预留槽位/权重。
   最低要求：8 条视频不能把图片/文本全部饿死；1000 条视频排队时图片仍能走。
2. **媒体归档统一流式**：图片 2.9GB/1000、视频 20GB/1000；都不能再按“整段 Buffer”处理；
   优先上游直接写 OSS，其次高带宽归档层。
3. **图片审核单独治理**：换可用模型/提示词引导/参考图检查；把“审核失败/12h 冷却”明确展示给学生，
   不要让学生以为是平台卡住。
4. **上传闸改造**：同机构 3 路并发在 1000 人场景是硬失败；改成排队或按班级/用户配额，并压测。
5. **VibeCoding/文档/数字人分别压测**：它们不走这条队列，但各有 API/CPU/上传/上游瓶颈。

---

## 五、一句话回答

- **视频、图片、音乐、文本（画布）**：同一个 async 队列；视频会把其他模态拖住，今天图片已被拖 43–61 分钟。
- **图片**还叠加了上游内容审核失败/12 小时冷却（近一周约 47.5% 失败），这是另一个问题。
- **VibeCoding、文档、数字人**：不是这条队列，但各自有 1000 路时的 API/SSE/CPU/上游瓶颈。
- **上传/提交**：同机构同时只有 3 路，1000 人同时提交会大批 429；这是独立的上限。
