# 新对话交接 · 学生环境被内核 OOM 杀掉（2026-09-17）

> 现象：学生界面一直显示「深度求索中… **110 分 46 秒**」，最后一步工具调用报
> `The tool call was interrupted after it was recorded, but no result was durably recorded.`
> 排查结论：**不是模型在算，是那个学生的创作环境被内核 OOM 杀了**。
> 本文记下事实、可复用的排查手法、以及还没定的处置。

## 一、事实（都有证据，不是推测）

| 项 | 值 |
|---|---|
| 真实用时 | **24 分 02 秒**（界面重新进入后自己显示的「用时 24分02秒 · 17:03」） |
| 那 110 分钟是什么 | **客户端假象**：websocket 断了、界面「自动重连中」，计时器继续空转 |
| 被打断的动作 | `univer_compile_svg`（参数里是 `page-01.svg` / `*.univer` / `page:1`） |
| 内核日志 | `[Thu Sep 17 17:03:16 2026] Memory cgroup out of memory: Killed process … (MainThread)` |
| 被杀的是谁 | `oom_memcg=/system.slice/dsh-student-**dshs-2ed271402d**.service`（刘与那台） |
| systemd 记录 | `Failed with result 'oom-kill'` |

**关键对齐**：OOM 发生在 **17:03:16**，而那一轮结束、工具调用被打断也是 **17:03** —— 同一分钟。

## 二、排查手法（下次直接用，别重走）

1. **先判「真在算」还是「卡住了」**：查 `usage_records` 按分钟分桶。
   真在算 = 调用连绵不断；卡住 = 断崖式停止。
   这次是：16:39–16:42 一分钟十几条，然后 16:47、16:52、17:02 各一条，**17:03 之后彻底停**。
   ```sql
   SELECT substr(created_at,1,16) t, COUNT(*) n FROM usage_records
   WHERE created_at > datetime('now','-1 hours') GROUP BY t ORDER BY t;
   ```
   ⚠️ `created_at` 是 ISO（带 `T`/`Z`）而 `datetime()` 产出的是空格分隔格式，**字符串比较会串**，
   所以别依赖那个 WHERE 的边界，看整体形态就行。

2. **平台侧零错误不代表没事**：这次 journald 里 2 小时零错误、`usage_records` 每条都 `SUCCESS`。
   模型和网关是好的 —— 别再往那边查。

3. **查内核 OOM**（这是决定性的一步）：
   ```bash
   dmesg -T | grep -iE "out of memory|oom-kill|killed process" | tail
   journalctl --since "3 hours ago" | grep -iE "oom-kill|Failed with result"
   ```

4. **算清内存账**：`free -m`、`ps -eo rss,etime,pid,cmd --sort=-rss`、`swapon --show`。

**当前这台机器（39.106.183.200）的内存账**：

```
491,680 KB (480MB)  dsh-univer-office 的 artifact 进程   ← 单个最大
312,444 KB (305MB)  另一个学生的 dsh 运行时
 56,764 KB          平台服务
宿主 ~1.6GB；swap 2G 里已用 1.1G
```

`dsh-host-broker` 和两个 `dsh-student-*` 是独立 systemd 单元（`systemctl list-units | grep dsh`），
每个学生一个单元 —— **OOM 是按单元的内存 cgroup 触发的**。

## 三、根因与责任

**Univer 办公插件**（`d197ba3` 装的）常驻 **480MB**，和被杀的 dsh 运行时**在同一个内存 cgroup 里** ——
是它把这组推过线的。第十一轮交接文档里已经记过这个代价（「+290MB/学生」「这台 1.6GB 的机器
本来就只塞得下 1-2 个学生环境，装完余量更紧」），现在是它**真的把学生的会话杀掉了**。

严格说：被杀的进程本体是 dsh 运行时（247MB），所以「Univer 是主因」是**数字都指向它**，
但没法 100% 排除其它增长。

另外截图里 Univer 面板写着 **"Univer Office License Required"** —— 它是**没授权**的。
没授权还常驻 480MB 并把会话搞死，这笔账不划算。

## 四、还没定 / 下次要补

1. **留不留 Univer 没定**（用户本轮明确说先不动）。两条路：
   - 不留 → 摘掉插件（注意：**插件只在进程启动时加载，必须停 + 冷启，复用路径不生效**），
     然后冷启两个学生环境；
   - 留 → 必须给机器扩容，1.6GB 撑不住「2 个环境 + Univer」。
2. **dsh 自己的日志没有落点**：`/srv/ai-kids-platform` 下只有平台的日志，
   学生运行时的 stdout 找不到文件。所以这次只能说「卡在 `univer_compile_svg` 之后」，
   **没法证明是那一次调用不返回**。要补：把 dsh stdout 落到文件。
3. **平台侧该加兜底**：单元状态里有明确的 `oom-kill`，平台完全能检测到，
   应该直接告诉学生「环境内存不足已中断，请重试」，而不是让他对着一个空转的计时器等两小时。
4. 顺带欠着的（第十一轮就记了）：**重建镜像**、机器扩容。

## 五、一条可以直接记住的判断口径

> **客户端上的「深度求索中 + 计时器一直涨」不等于模型在算。**
> 连接断了之后它会继续空转。要判真伪，去查 `usage_records` 的调用曲线 ——
> 断崖式停止就是卡住了，连绵不断才是真在算。
