# 上游实扣接入（Seedance 直连）· 2026-09-15

配套阅读：`docs/operations/真实三账对照-20260914.md`（三账与金额口径总说明）。

## 一、为什么做

`compute_attempts` 在 2026-09-14 上线了三账机制，但生产里**一条记录都没有**，而且四个渠道
**全都没配上游合同单价**。也就是说：只要学生真生成一次，那笔的上游成本必然是 `UNKNOWN`。
根因不是配置漏了，而是代码读不到上游回传的实扣金额 —— 见第三节。

## 二、上游（api.seedance.nz）到底提供了什么

文档：网页版 `https://api.seedance.nz/docs/`；给 AI 工具用的是 `https://api.seedance.nz/docs/llms.txt`
（764KB Markdown，含完整价格表，比抓网页好用）。

**没有**按账期的账单 / 消费明细 / 发票接口 —— 不存在类似 OpenAI `GET /v1/organization/costs?start_time=…`
的东西。文档里「账单」二字只出现在「最终按上游实际账单换算结算」这类说明文字里。

**有**的是：

| 接口 | 给什么 | 性质 |
|---|---|---|
| 异步任务终态查询 | `usage.amount` + `currency` | **逐笔实扣**，文档保证「与本次实际从余额扣除的钱完全一致」，失败退款为 0 |
| `GET /api/usage/wallet/` | `amount`（余额）/ `used_amount`（累计已用）/ `quota` / `used_quota` | 点快照，可做总账校验 |
| `GET /api/usage/token/` | 令牌剩余额度（与钱包余额不是一回事） | 点快照 |
| `GET /v2/query/video_generation` | MiniMax-H3 近 7 天任务列表（可翻页、按 model/status 过滤） | 唯一带时间窗的列表，可补漏 |

逐笔实扣的**读取位置按协议不同**，这是接入的关键：

| 查询协议 | 位置 |
|---|---|
| 通用图片 / 视频 / 音频 / 3D 任务查询 | `data.usage` |
| `GET /v1/music/tasks/{id}` | `data.usage` |
| `GET /v1/videos/{id}` | `usage`（顶层） |
| `GET /v1/midjourney/tasks/{id}` | `usage`（顶层），另有 USD 的 `cost` |
| `GET /v2/query/video_generation/{id}` | `task.usage` |

### 实测与文档不一致的两处（2026-09-15 真机验证）

1. **币种**：文档示例写 `"currency": "CNY"`，**实测回的是 `"¥"`**：
   ```json
   {"code":true,"message":"ok","data":{"status":"SUCCESS","usage":{"amount":0.040112,"currency":"¥"}}}
   ```
   逐字比对 `CNY` 会让真实数据**一条都读不到**。
2. **钱包的 `display_type`**：文档示例写 `CNY`，**实测回的是 `"CUSTOM"`**。
   所以判断人民币只能靠 `usage.currency` 的写法，不能靠 `display_type`。

金额精度也值得注意：实测 `0.040112` 是 6 位小数（远细于「分」），乘 100 得 4.0112 —— 必须四舍五入。

## 三、代码改动（commit `35bf362` 起）

`reportedCost()`（`apps/server/src/services/openaiCompatibleProvider.js`）原来只认网关风格的
`payload.usage.cost.{amount,currency}`，而且要求 `currency === 'CNY'`。Seedance 直连的 payload
**少一层 `cost`** 且币种写 `¥`，于是被判成 `null`，成本只能落到 `COMPUTED`/`ESTIMATED`/`UNKNOWN`。

改了三件事：

1. **认三种信封**：`usage.cost`（网关）、`usage`（顶层）、`data.usage`、`task.usage`。
2. **认币种别名**：`CNY` / `RMB` / `¥` / `CN¥` / `人民币` 都算人民币；`USD` / `$` / `JPY` **一律不认**。
   跨币种不并账 —— 硬把 Midjourney / Suno 报的 USD 当人民币会把真实毛利算错，
   这类调用留在 `COMPUTED`/`UNKNOWN`，由账单侧单独核销。
3. **小数元四舍五入成整数分**：`Math.round(amount * 100)`。不改的话官方示例的 `¥20.40`
   会落成 `2039.9999999999998`、实测的 `¥0.040112` 会落成 `4.0112`（非整数分）。

另外补了 `reportedCostRuleSnapshot()`（`upstreamCost.js`）：REPORTED 也要留成本规则快照，
把上游**原样回传的币种写法**和**未取整的金额**存进 `cost_rule_snapshot`，这样「每一分是怎么来的」
事后查得清（`basis: 'UPSTREAM_REPORTED'`、`upstreamCurrency`、`upstreamAmount`、`reportedFen`）。

守卫：`p75` 钉形状矩阵（三种位置、`¥` 认 / `USD`·`JPY`·`$` 不认、缺 currency、token 用量、负数），
`p90` 加端到端用例（走真实轮询路径，含 MiniMax-H3 的 `task.usage` 与 `requestPaths`/`pollPaths` 拼接）。

## 四、合同单价：只填了有牌价的那个

牌价来自上游文档。**图片与音乐渠道故意不填** —— 上游对这两个是「按上游实际消耗结算」，
没有发布单价，填任何数字都是猜；现在逐笔实扣能读到，就不需要猜的兜底。

| 渠道 | 端点 | 模型 | 合同单价 | 依据 |
|---|---|---|---|---|
| 生视频 | `api.seedance.nz/v1` + `/v2/*` | `MiniMax-H3` | VIDEO `perSecondFen:30`，`byResolution: {480P:15, 768P:30}` | 文档「MiniMax-H3 → 价格」表：480P ¥0.15/秒、768P ¥0.30/秒；参考图/音频/视频不加收，驱动音频按同一每秒价，故不配 `audioExtraPerSecondFen` |
| 图片渠道 | `api.seedance.nz/v1` | `zhenzhen-image-g-v2-lowprice` | **不填** | 上游按实际消耗结算，无牌价 |
| 音乐 | `api.seedance.nz/v1` | `mureka-v9-song` | **不填** | 上游按实际消耗结算，无牌价；且文档「约 ¥0.004/秒」= 0.4 分/秒，**小于 1 分**，按「单位一律非整数分」表达不出来 |
| 文本主渠道 | `api.deepseek.com` | `deepseek-flash` | **不填** | 文本是同步接口，上游只回 token 用量、**没有 per-call 实扣**，本可走 COMPUTED，但直连 DeepSeek 无合同价可填 |

- `byResolution` 的档位键必须与渠道能力表**逐字一致**（后端按请求分辨率精确匹配）：
  生视频渠道 `MiniMax-H3` 的能力表就是 `["480P","768P"]`，所以档位键用大写 P。
- 写入走的是应用自己的归一化与校验（与后台「保存渠道配置」同一段代码），写入前用
  `node:sqlite` 单列 `UPDATE`，并有三层守卫（渠道数/清单/模态路由不变、既有字段取值不变、
  生视频价格等于预期值）；原值备份在服务器 `/tmp/policy-before.json`。

⚠️ 这些是**标准零售价**，文档原话「账户实际价格以控制台适用的分组及折扣为准」。
所以它只是 `COMPUTED`（估值）的兜底，**不是结算依据**；逐笔结算以 `REPORTED` 为准
（来源优先级 `REPORTED > COMPUTED > ESTIMATED > UNKNOWN`）。

## 五、验证证据（2026-09-15）

发布：release `20260915T033122Z` / commit `35bf362`，服务 `active`、`NRestarts=0`、
五个公网入口全 200。

真机验证（用生产渠道配置 + 生产密钥，经应用自己的适配器真打一次上游）：

```bash
# 服务器上（脚本在 .tmp/，不进仓库 —— 它会真花钱，绝不能放进 scripts/ 被冒烟跑到）
export PATH=/srv/ai-kids-platform/runtime/node/bin:$PATH
set -a; . /etc/ai-kids-platform/production.env; set +a
node /tmp/probe-upstream-usage.mjs      # 一次图片生成，打印上游原始信封 + 我们读到的值
node /tmp/probe-wallet-currency.mjs     # 免费：确认钱包币种写法
```

实测结果：

- 提交 → 轮询 → 终态 `data.usage = {amount: 0.040112, currency: "¥"}`（状态值是大写 `SUCCESS`）。
- 定位：`zhenzhen-image-g-v2-lowprice` + `1k` ≈ **¥0.040112/张**（比 Seedream 的 ¥0.23~0.54 便宜一个量级）。
- 钱包：`amount=79.935414`、`used_amount=310.064586`、`display_type="CUSTOM"`。

`/api/usage/wallet/` 的 `used_amount` 可以做**总账校验**：平台累计 `REPORTED` 成本的增量
对上钱包 `used_amount` 的增量，差额能立刻暴露漏记。没有模型维度、粗，但免费且可靠。

## 六、边界与遗留

- **没有账期账单接口**：所以「官方账单自动对账」那套适配器（`openai-costs` / `anthropic-usage` /
  `generic-http`）对这个上游用不上；`generic-http` 顶多能接钱包余额，但余额是聚合值、没有模型维度，
  对不出「账期 × 模型」。逐笔实扣才是正解，已经接上。
- **文本没有 per-call 实扣**：`/v1/chat/completions` 是同步接口，只回 token 用量。文本成本要靠
  合同单价折算（`COMPUTED`），而文本渠道目前没配价。
- **小于 1 分的金额会被四舍五入吃掉**：实测单张图 ¥0.040112 → 4 分。逐笔误差 < 0.01 分，可忽略；
  但若将来出现大量亚分调用，需要重新考虑分以下的精度。
- **`usage.amount` 为 0 视为上游上报的 0**（文档说失败退款为 0，而失败任务在更早的分支就抛错了，
  正常不会走到这里）。如果上游对失败任务也回 0 而不是报错，需要在 `cost_source` 上另加区分。
- **MiniMax-H3 的视频实扣尚未真机验证**（只验证了图片这条路）；视频轮询路径已由 `p90` 用
   `task.usage` 形状覆盖。要真机验证需跑一次视频生成（480P 5 秒 ≈ ¥0.75）。
