## 比对方法（这一步的"可信"全靠它）

```text
① **先在线上库取一致性快照**：`VACUUM INTO '/tmp/snapshot.db'`（事务内读，不受并发写影响）。
   为什么必须这样：线上平台一直在写，直接拿活库导出、过几分钟再比对，必然对不上
   —— 我第一版就是这么误报的（audit_logs 4901 vs 4839、sessions 477 vs 476，
   看着像"搬丢了 62 行"，其实是快照时间点不同）。
② 从**快照**导出数据、灌进 MySQL，再拿**同一个快照**做比对基准。
③ 逐表比行数（89 张全比）；关键表**逐行比内容摘要**。
④ 摘要里两边的值必须**归一到同一种表示**再比：SQLite 侧整数是真 number、
   MySQL 侧经 XML 拿回来是字符串 —— 不归一就会出现"内容不一致"的假警报。
⑤ MySQL 侧用 **`--xml`** 输出（数据里有制表符/换行，TSV 会切坏），
   并且**必须识别 `xsi:nil="true"`**（否则 NULL 被读成空字符串，又是一类假警报）。
```

## 这一路真踩到的 5 个坑（都修了，都值得记住）

```text
① **类型选择必须基于真实数据长度**。第一版按"有没有默认值"拍脑袋定，结果 `metadata`
   （JSON 远超 255 字符）和 `canvas_snapshot`（实测最长 4122 字符）都成了 VARCHAR(255)
   —— **会静默截断**。改了之后又给长度加了上限，**第二次错**：4 个列被判成 VARCHAR(16383)，
   而它们真实有 7 万～15 万字符（audit_logs.before_data 152148、platform_config_change_logs
   的 old/new_value 82493、platform_settings.ai_provider_policy 71059）→ 超限一律 MEDIUMTEXT。
   **并且写了一道独立检查**：逐列比对"VARCHAR(n) 的 n 是否 ≥ 该列真实最长数据"，
   现在 999 个 VARCHAR 列 **0 个会截断**。这道检查抓出了上面那 4 列。

② **MySQL 单行固定宽度上限 65535 字节**（不算 TEXT/BLOB）。utf8mb4 下每个 VARCHAR(n) 占 n×4，
   一张有十几个宽 JSON 列的表就爆：course_lessons(88308)、student_projects(71636)、
   vibecoding_submissions(66228) 直接 ERROR 1118。修法是**按表算总宽度，超了就把非索引列降级成
   MEDIUMTEXT**（TEXT 系在行里只占一个指针），降级了哪几列要**报出来**。

③ **线上 DDL 里有一处漏了逗号**（generation_jobs 的 project_id 外键后面）：
     `… ON DELETE CASCADE\n  FOREIGN KEY (retry_of_job_id) …`
   **SQLite 容忍**（表一直在跑），**MySQL 直接报语法错**。
   ⚠️ 修法**不能用全局正则补逗号** —— 会把**列定义里的 CHECK** 也误伤
   （`status TEXT … DEFAULT 'X' CHECK (…)` 前面被插逗号，列定义就破了）。
   正解：只在"这一部分**本身以表级约束关键字开头**"时才拆；而且
   `CONSTRAINT <名字> CHECK (…)` **本身是一个整体**，里面的 CHECK 不能当"下一个约束"拆
   （线上 course_series 就是行首逗号 + 命名约束的写法，踩了两次才定位到）。

④ **索引列不能一律 VARCHAR(255)**：MySQL 单条索引键上限 3072 字节，
   utf8mb4 下 4 列 × 255 字符 = 4080 → `ERROR 1071 Specified key was too long`。
   修法：索引列也**按真实数据长度**定尺寸（下限 64）—— id 这类列真实只有 25 字符，
   VARCHAR(64) 完全够，键长一下就下来了。

⑤ **`CONCAT()` 不能直接进函数索引**：`ERROR 3757 Cannot create a functional index on an
   expression that returns a BLOB or TEXT`（CONCAT 返回 TEXT）。
   修法：包一层 `MD5(CONCAT(…))` —— 返回 32 字符，既躲开类型限制也躲开键长上限。
   （实测确认 RDS 上 MD5 可以用于函数索引。）
```

## 那 20 个"部分索引"的解法（一条业务约束都没丢）

见 `deploy/production/migrate/13-partial-indexes-mysql.sql`。三类：

```text
A. 本来就不是 UNIQUE 的（5 条）→ 普通索引即可（多索引几行 NULL 无害）
B. UNIQUE 且条件只有 `… IS NOT NULL`（6 条）→ **普通 UNIQUE 就等价**：
   SQL 的唯一索引把多个 NULL 当互不相同的值，"只对非 NULL 唯一"正是默认行为
C. UNIQUE 且条件含业务判断（9 条）→ 函数索引 `UNIQUE KEY ((IF(条件, MD5(拼接键), NULL)))`
   —— 不满足条件时为 NULL，语义与 SQLite 的部分唯一索引**完全一致**，
   实现为隐藏虚拟列，不改表结构、不影响 SELECT *

⚠️ 其中一条容易写错：organizations.org_code 的条件是「非 NULL **且非空串**」，
   不能简单写成 UNIQUE(org_code) —— 那样多个空串会互相冲突，而原来允许。
```

## 阶段 1 是什么（提前说清，那才是主体）

```text
阶段 0 只证明了"数据能原样搬进 MySQL"。**应用还完全没接** —— 它现在仍然用
node:sqlite 的**同步** API（q/rows/row/count/one/transaction 六个函数，约 1000 处调用点、
52 个文件）。接 RDS 意味着这六个函数变成返回 Promise、那 1000 处加 await、
调用链上的函数变 async —— 这是整个工程的主体，以天/周计。
还有一批跟着走：约 130 个守卫脚本（很多自己建临时 SQLite 库跑流程）、migrate-*.mjs、
以及每日备份/恢复演练那套（现在是 PRAGMA + 拷文件的 SQLite 玩法）。

阶段 0 的价值：到了阶段 1，schema 与数据这一层已经**确定可行且已验证**，
剩下的都是代码改造 —— 而不是"改完才发现数据搬不过去"。
```
