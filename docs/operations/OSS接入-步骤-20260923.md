# OSS 接入（2026-09-23）—— 设计、步骤、回滚

> **状态：已完成并验证**（2026-09-23 晚）。密钥已配、连通性验收 8 项全过、275 个历史对象已回填、
> `FILE_STORAGE=oss` 已打开。真实链路实测：公网下载 142,759 字节的文件，**实收字节数与 sha256
> 与本地原文件完全一致**。

> 目标（来自迁移文档 §三 的第 1 步）：**把上传/媒体的读写改成 OSS**，私有素材走签名 URL。
> 真实收益有二：① 这台机的**公网出口只有 5 Mbps**，媒体全从它出去会拖慢所有用户；
> ② 学生私有素材不该有公网地址（现在靠平台自己的授权口，改成签名地址更干净）。

## 设计（为什么这么做）

```text
【一】零依赖手写 OSS 客户端（apps/server/src/services/objectStorage.js）
  这是**刚上线**的生产，多一个依赖就多一份 lockfile 与构建面；而我们要的只有四个动作
  （放、签发 URL、取到本地、删）。V1 签名规则公开稳定（HMAC-SHA1 + 固定拼法），手写更好审计。

  ⚠️ **两个端点分清**是省钱提速的关键：
    OSS_ENDPOINT          公网端点 → 给**浏览器**签发的 URL 用它
    OSS_INTERNAL_ENDPOINT 内网端点 → **服务器自己**读写用它（同地域 ECS 走内网：免流量费、更快）
  没配内网端点就退回公网，不会坏。

【二】每行自己回答"我在哪儿"（apps/server/src/services/fileStorage.js）
  判据放在 `file_assets.metadata.storageBackend` —— 表里本来就有 metadata JSON 列，
  **不用改 schema**；**没有这个字段的（全部历史数据）一律当本地盘**。
  所以：打开开关不会让老数据"搬家"，回滚也只是把标记去掉。

【三】开关是两段，缺一不可（fail-closed）
  ① env 里有 FILE_STORAGE=oss  ② bucket/AK/SK/端点都齐
  任何一段不满足就退回本地盘 —— 绝不允许"半开"（上传写进 OSS 一半、读的时候找不到）。
  这一条被守卫 p136 钉住了。

【四】读的时候怎么发字节
  · OSS 行 → 平台**302 到带签名的临时地址**（15 分钟），字节由 OSS 直接服务，不经过我们
    （授权判断在这之前已经做完，签名地址只是"取件凭证"）
  · 本地行 → 照旧流式下发（Range 支持原样保留）

【五】课件预览的特别处理
  Office 转 PDF 用的 LibreOffice **只认本地文件**，所以 OSS 上的课件预览会先
  `getObjectToFile` 取到 `uploads/.oss-preview-cache/<fileId>` 再转换（同一份只下一次）。
```

## 回滚（三档，都很快）

```text
· 只回滚"新上传"：把 FILE_STORAGE 改回 local → 重启。新上传回本地盘，历史行不受影响。
· 回滚"某一行"：把那一行 metadata.storageBackend 去掉 → 它立刻按本地盘读（本地文件还在）。
· 全量回滚：FILE_STORAGE=local + 批量去掉 metadata 里的 storageBackend 标记。
  ⚠️ 如果跑过 --prune-local，本地文件已经删了，那就得先把对象从 OSS 拉回来再回滚。
```

### ⚠️ 两条 OSS 的真实行为（别再照直觉改）

```text
① **不能在签名 URL 里覆盖 content-type** —— 会直接 400：
   `InvalidRequest: Can not override response header on content-type`
   （对象上传时已带 Content-Type 就不许再覆盖）。我们上传时本来就把 mime 写对了，
   所以浏览器拿到的类型本来就是对的 —— 根本不需要覆盖。**这一条差点让 275 个文件全下载不了**：
   代码改了但忘了重建，线上跑的还是旧版，302 出去的地址带 response-content-type → 400。
   教训：**改了代码一定要重建 + 用真实链路验一次**（"302 存在"不等于"302 能用"）。

② **`inline` 会被无视** —— 请求 `inline` 回给你的仍是 `attachment`；
   只有 `attachment; filename=…` 这类会原样生效。
   对我们没有影响：走这条重定向的只有**下载**（要的就是 attachment + 文件名），
   而**预览**走的是"先把对象取到本地再发"（fileAssets.js 里 materializeObject），不经过签名 URL。
```

## 第二步：公开内容（广场媒体 + 客户端安装包）搬 OSS

```text
为什么是这两样：它们是吃满这台 5 Mbps 出口的**大头**。
  · 广场媒体 1.79G，每个页面都要取图
  · 客户端安装包 392M —— 5 Mbps 下一个用户要下 10 分钟；
    而且客户端修好之后会有一波**集中下载**，不搬的话那波会把整台机出口堵死

量出来的范围：广场媒体 832 个文件 / 1705 MB，安装包 6 个文件 / 373 MB，合计约 2.08 GB。

【关键设计：为什么**不用改数据库、也不用改客户端**】
  内容对外仍然是 https://aicyld.com/media/… 与 …/downloads/…（库里存的也是这个），
  只是 **nginx 对这两条路径 302 到 OSS**。三条依据：
    ① 浏览器会跟随 302 → 由 OSS 直接把字节发出去，不经过我们那 5 Mbps；
    ② 客户端更新用的是 `fetch`（默认跟随跳转）；
    ③ 客户端那道「更新地址必须是平台域名、路径必须是 /downloads/」的校验
       **只作用在初始地址上**（读过 LingdongUpdater.ts 的 allowedUpdateUrl 确认），
       302 出去之后它照样下载，并继续校验 size/sha256。
  → 所以数据库一行不用改（不像换域名那次要重写 485 行），客户端一行也不用改。

【安全边界（红线）】
  只对 `public-media/*` 与 `downloads/*` 两个前缀开匿名只读，**绝不开**放上传所在的私有前缀
  （课件、学生素材都在下面）。脚本最后会**实测**：公开前缀匿名读 200、私有前缀仍然 403 ——
  后者不过就说明边界破了，必须立刻回滚策略。

【步骤】
  ① 用户在控制台给 bucket 加一条授权策略（子账号没有改策略的权限，这是对的）：
     OSS 控制台 → Bucket 列表 → 点进 bucket → 左侧「权限管理 → Bucket 授权策略」→ 编辑 → 粘脚本打印的 JSON
  ② node deploy/production/migrate/11-publish-public-assets-to-oss.mjs --policy   # 只验策略
  ③ node deploy/production/migrate/11-publish-public-assets-to-oss.mjs            # 真传（幂等，按大小跳过）
  ④ 改 nginx：/media/ 与 /downloads/ 由 alias 改 302 到 OSS（带短的 Cache-Control，让浏览器缓存跳转）
  ⑤ 验收：图片、安装包都能下；私有课件的签名下载不受影响

【回滚】把 nginx 的 302 改回 alias（本地文件一直在），策略删掉即可 —— 两步都很快。
```
