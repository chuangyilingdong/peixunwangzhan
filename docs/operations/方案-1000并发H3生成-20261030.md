# 1000 路并行 MiniMax-H3 生成 · 可行性与实施方案（2026-10-30）

## 〇、结论先说

**目标口径**：1000 个 H3 任务同时处于 `RUNNING`（同一天/同一节课集中提交），不是“1000 个学生在线但只有少数人生成”。

**上游生成：有条件可行。** 用户确认 MiniMax 侧不限并发；但仍要验证账号的**提交 QPS、轮询 QPS、单账号任务数/费用配额**——不限并发 ≠ 不限 QPS/不限预算。

**平台侧按现状：不可行，且不是 worker 数的问题。**

当前平台单机实测：

```text
CPU 4 核 / 内存 7.4GB / 磁盘 14GB 空闲
H3 单条：20–22MB，生成 7分50秒–9分25秒
服务器入向：单流 1.31MB/s；8 流并发聚合仍约 1.28MB/s（≈10Mbps）
同一文件从开发机单流：2.67MB/s（说明上游 CDN 不慢，瓶颈在服务器入口）
```

1000 条 H3 的结果是 **20GB**。按服务器 1.3MB/s 入向，光把结果拉回来就要：

```text
20GB ÷ 1.3MB/s ≈ 15,400 秒 ≈ 4.3 小时
```

也就是：**上游 1000 路 8 分钟生成完，平台还要 4 小时才能把结果收完**。课堂当场用不了。要在 8–9 分钟内收完，需要 ≥42MB/s（≈336Mbps）的入向吞吐，当前 5Mbps EIP 差两个数量级。

**同时还有两个硬限制：**

- 归档当前是 `Buffer.from(await response.arrayBuffer())`，每条 20MB 全进内存；1000 路 = **20GB 内存**，7.4GB 机器直接 OOM。必须改成流式写 OSS。
- 当前是单 Node 进程 + 单机 4 核；1000 路轮询、DB 查询、归档、前端 200 QPS 轮询都压在同一进程/同一 RDS 连接池（10）上，不可行。必须拆 worker、做持久队列与多进程/多实例。

**一句话：1000 路上游可以开，但平台必须先解决“结果怎么进来”和“任务怎么持久调度”，否则 1000 路只会把 20GB 堵在 10Mbps 入口。**

## 一、现状基线（2026-10-30 实测）

### 1.1 服务器

| 项 | 实测/现状 |
| --- | --- |
| CPU / 内存 | 4 vCPU / 7.4GB（可用约 6.5GB） |
| 磁盘 | 40GB，已用 24GB，空闲 14GB |
| 服务 | 单 systemd 进程 `learning-platform-production` |
| DB | MySQL 8 RDS，应用连接池 10/进程 |
| 文件存储 | `FILE_STORAGE=oss`，H3 产物 `metadata.storageBackend=oss` |
| 学生取件 | `/api/student/file-assets/<id>/download` 302 到 OSS 签名地址（不占服务器出口） |
| 公网 | 文档口径 5Mbps 峰值；实测入向约 10–14Mbps |

### 1.2 生成链路

- 单条 H3：20–22MB，7分50秒–9分25秒；
- 2026-10-30 8 个学生 16:42 同时提交，平台单 worker 串行，最后一条 17:48 才完成，等待 65 分钟；
- 已上线 8 路 worker 作为止血（release `20261030T095319Z`），但 8 路处理 1000 条仍需约 **17.7 小时**；
- 当前归档：整段视频读进内存再 `persistSecureUpload`；1000 路不可行；
- 当前队列：进程内数组 + 单进程；进程重启只靠启动时回收，不适合多实例。

### 1.3 网络实测

| 测试 | 结果 |
| --- | --- |
| 服务器 → 上游 H3 结果（单流 20MB） | 1.31MB/s，15.2s |
| 服务器 → 同一 URL，8 路并发各 4MB | 32MB / 25s，聚合约 1.28MB/s |
| 开发机 → 同一 URL（单流 4MB） | 2.67MB/s |
| 服务器 → 清华镜像 20MB | 1.11MB/s |
| 服务器 → npmmirror 4MB | 1.71MB/s |

结论：**上游 CDN 对开发机能到 2.67MB/s；服务器侧无论单流还是 8 流都只有 ~1.3MB/s，瓶颈在服务器入口/EIP，而不是上游。** 是“每 IP/每 EIP 总入口”还是“服务器线路”需要再用一台高带宽/香港实例验证，但当前这台机器不具备 1000 路结果回传能力。

## 二、逐维度评估

### 2.1 上游（MiniMax / seedance 渠道）

| 维度 | 评估 |
| --- | --- |
| 1000 并发任务 | 用户确认不限并发，可提交；需确认账号任务数上限 |
| 提交 QPS | 1000 条一次提交，若 QPS 限 10 则 100s 发完，可接受；需限流 |
| 轮询 QPS | 1000 任务 × 每 5s 一次 = 200 RPS；对上游可能过高。建议 10–30s + 抖动（33–100 RPS），或 webhook/批量查询 |
| 结果地址 | 当前是 `rh-hk-images.xiaoyaoyou.com` 的公网 CDN 地址；开发机 2.67MB/s，服务器 1.31MB/s |
| 费用 | 1000 条 H3 的费用必须先算清；平台当前是“观测账本”，没有硬预算拦截 |
| 失败/重试 | 1000 条按 1% 失败也是 10 条；需要幂等提交（task_id 对账）与有限重试 |

### 2.2 计算 / worker

| 维度 | 评估 |
| --- | --- |
| 单进程 | 4 vCPU/7.4GB；1000 路轮询/DB/归档不可能放在一个 Node 进程 |
| 建议 | 4–8 个 worker 进程（同机）或 2–4 个 worker 实例；每进程 125–250 并发（I/O 密集，需压测） |
| 内存 | 流式归档后每路约 <1–2MB；1000 路约 1–2GB，4–8 进程总和可控；**不流式则 20GB，直接否决** |
| CPU | 4 vCPU 要同时跑 API + worker；建议 API/worker 分进程，worker 按 CPU 核数分配 |
| 部署 | 多进程后 `interruptOrphanedJobs` 不能启动时把所有 RUNNING 收掉，必须改成租约/实例级归属 |

### 2.3 队列 / 调度 / DB

| 维度 | 评估 |
| --- | --- |
| 当前 | 进程内数组；单进程；无租约续期；重启只靠启动回收 |
| 1000 路 | 必须持久队列：`generation_jobs` 已是持久表，可直接做队列 |
| 认领 | MySQL 8 `SELECT ... FOR UPDATE SKIP LOCKED` 或 Redis/SQS；每任务原子 `QUEUED→RUNNING`（已加 `claimed.changes`） |
| 租约 | 增加 `worker_id + lease_expires_at`，worker 心跳续租；崩溃后到期回收，不靠“启动时全杀” |
| 索引 | 增加 `(status, created_at)`，避免 1000 条时全表扫 |
| 连接 | 每进程池 10；4–8 进程 40–80 连接；RDS 需确认上限；更高并发用 RDS Proxy/连接复用 |
| 公平 | 按班级/机构轮转与配额，避免一个班占满 1000 路 |

### 2.4 结果回传 / 归档（**第一瓶颈**）

| 方案 | 评估 |
| --- | --- |
| A. 上游直接写我们 OSS | **最优**：20GB 不经过 ECS 入口；需确认 seedance/MiniMax 是否支持 output bucket/webhook；若能，1000 路只需提交/轮询/落库 |
| B. 香港/高带宽归档实例 | 在靠近 `rh-hk` 的区域起 1Gbps 实例，20GB 约 3 分钟；或 10–30 个多 IP 实例聚合（若上游按 IP 限速）；需测上游单 IP 上限 |
| C. 当前 ECS + 升 EIP | 若瓶颈是 EIP，升到 100Mbps/1Gbps 可解；需阿里云确认带宽与费用；20GB/100Mbps≈27min，1Gbps≈3min |
| D. 上游 URL 先给学生播，异步归档 | 学生直接从上游 CDN 取；但 URL 可能过期/不可控，且学生侧 1000 并发下载对上游是另一回事；只能作为过渡 |
| E. 降低产物大小 | 480P/5s 已经约 20MB；压到 10MB 仍需 10GB，4.3h→2.1h，不解决根本 |

**结论：不解决 A/B/C，1000 路并行没有课堂意义。**

### 2.5 存储 / OSS / 学生取件

| 维度 | 评估 |
| --- | --- |
| 单批容量 | 1000 × 20MB = 20GB；OSS 存储足够，成本可控 |
| 本地盘 | 14GB 空闲；不能把 20GB 临时文件落本地；必须流式直传 OSS |
| 学生下载 | 已 302 到 OSS，不占服务器 5Mbps；1000 学生取件由 OSS/CDN 承担 |
| 签名/权限 | 保持 PRIVATE + 签名 URL；不要为了快把 bucket 公开 |
| 生命周期 | 生成视频建议设置 OSS 生命周期/归档策略，避免长期堆积 |

### 2.6 API / 前端

| 维度 | 评估 |
| --- | --- |
| 1000 学生在线 | 每人 5s 轮询 = 200 RPS；单进程 + RDS 连接池 10 风险高 |
| 建议 | 15–30s + 抖动（33–67 RPS），或 SSE/WebSocket 推完成事件；显示排队位置/ETA |
| 画布保存 | 1000 人自动保存会叠加；已有 1.2s 防抖，仍需压测 |
| 结果补齐 | 现有画布 effect 会在重开 DRAFT 项目时按 box_id 补挂；1000 路要保证服务端/前端都能补 |
| 静态资源 | 官网/画布 JS 走 CDN/nginx，不占生成链路 |

### 2.7 可靠性 / 可观测性

| 维度 | 评估 |
| --- | --- |
| 任务丢失 | 持久队列 + 租约 + 原子认领；重启不丢 |
| 上游已受理但本地失败 | 已有 `compute_attempts.task_id` 对账；1000 路要跑对账定时器并限速 |
| 重复提交 | 原子认领 + 幂等键；避免双扣费 |
| 监控 | 队列深度、活跃 worker、每阶段 P50/P95、上游 429/5xx、OSS 错误、DB 池、内存/带宽 |
| 熔断 | 上游连续 429/5xx 时降速/暂停新任务，避免 1000 条一起失败 |
| 部署 | 蓝绿/滚动；worker 优雅退出，任务回队列 |

### 2.8 成本 / 业务

| 维度 | 评估 |
| --- | --- |
| 生成费 | 1000 条 H3 的费用是首要决策；平台当前无硬拦截 |
| 存储/流量 | 20GB OSS + 20GB 学生取件流量；相对生成费通常较小 |
| 带宽/归档 | 高带宽实例或 EIP 升级有成本；按批次/小时计 |
| 配额 | 必须按机构/班级/课包做并发和预算上限；否则一次 1000 路可能超预算 |
| 体验 | 1000 路同时提交，即使全部并行，单条仍 8–9 分钟；必须显示 ETA，不能让学生以为丢了 |

## 三、目标架构（1000 路）

```text
学生/API
  │  POST /ai/generations/async（只做预检 + 入队，不做重活）
  ▼
generation_jobs（MySQL，QUEUED）
  │  多 worker 进程/实例：SELECT ... FOR UPDATE SKIP LOCKED
  ▼
worker fleet（4–8 进程/实例，每进程 125–250 并发）
  ├─ provider.submit（限流 + 幂等键）
  ├─ provider.poll（10–30s 抖动；有 webhook 优先）
  ├─ 结果流式写入 OSS（或 provider 直接写 OSS）
  └─ 更新 media_assets + job 状态 + usage
  ▼
media_assets（OSS，PRIVATE，签名 URL）
  │  SSE/WebSocket 或 15–30s 带抖动轮询
  ▼
学生画布（按 box_id 补挂；重开项目也能补）
```

关键点：

1. **API 与 worker 分离**：API 只入队，避免 1000 个生成请求把 API 打满；
2. **持久队列 + 租约**：worker 崩溃/重启任务回队列，不丢、不重复提交；
3. **流式归档**：禁止 20MB Buffer/条；优先 provider 直接写 OSS；
4. **结果交付**：OSS 302 + SSE/退避轮询；
5. **公平与配额**：按班级/机构限流、排队、预算。

## 四、实施方案（分阶段）

### Phase 0（已完成，止血）

- 8 路 worker；1000 条仍需 ~17.7 小时，只适用于当前小班；
- 原子认领已加，避免重复提交。

### Phase 1：100–200 并行（先证明链路）

目标：在不换机器的前提下，把“流式归档 + 持久队列 + 多进程 worker + 前端退避”跑通。

1. **流式归档**
   - 新增 `archiveGeneratedAssetStream`：上游 `response.body` → OSS multipart/流式写；
   - 只在首块做 MIME/魔数校验，大小上限 64MB；不落 20GB 本地临时盘；
   - 失败保留上游 URL + metadata.reason，不判生成失败（与现口径一致）。
2. **DB 队列 + 多进程**
   - `generation_jobs` 增加 `lease_expires_at`、`priority`、`class_session_id`（如缺）；
   - `SELECT ... FOR UPDATE SKIP LOCKED` 认领；worker 心跳续租；
   - 4 个 worker 进程（或 1 个 worker 服务 4 实例），每进程 50 并发；
   - 启动不再“全杀 RUNNING”，改为只回收过期租约；worker_id 实例级。
3. **上游限流**
   - 提交令牌桶（如 10 QPS）；轮询 10–30s + 抖动；
   - 连续 429/5xx 熔断降速。
4. **前端**
   - 轮询 15–30s + 抖动；显示排队位置/ETA；重开项目自动补挂。
5. **验收**
   - 100 条 mock 任务（8 分钟、20MB 假文件）压测：无 OOM、无重复、全部终态；
   - 20 条真实 H3：P95 提交/完成时间、上游错误、OSS 流式归档；
   - API/DB/内存/带宽指标达标。

### Phase 2：500–1000 并行（解决结果回传）

先做**结果回传方案选型**（按顺序）：

1. 找 provider 确认：能否把产物直接写到我们的 OSS（output bucket / webhook / 回传地址）；能做则最优，20GB 不经过 ECS；
2. 若不能：起香港/高带宽归档实例（1Gbps）或 10–30 个多 IP 实例，实测上游单 IP 上限与聚合吞吐；
3. 若仍不行：评估“上游 URL 先播 + 异步归档”的过渡方案（URL 过期风险要写清楚）。

同时：

- 4–8 个 worker 进程/实例，每进程 125–250 并发（按压测调）；
- DB 连接池/RDS Proxy；队列深度自动扩缩；
- SSE/WebSocket 完成推送；按班级公平队列 + 配额；
- 1000 条 mock 压测 → 100/500/1000 条真实 H3（需预算批准）；
- 验收：1000 条全部终态、无重复上游提交、20GB OSS 可播、P95 等待可接受、成本可控。

### Phase 3：10k

- 队列迁 Redis/SQS/Kafka；worker 多实例/多可用区；API 水平扩展；
- OSS/CDN 交付；按机构/班级配额与优先级；
- 压测 10k，按结果扩容与预算。

## 六、必须由业务/上游确认的点

1. **上游是否支持把结果直接写我们 OSS / webhook 回调**？这决定 1000 路是否能在课堂内完成；
2. 上游 **提交 QPS、轮询 QPS、单账号并发任务数、失败重试政策**；
3. 1000 条 H3 的**单价与总预算**；是否需要按班级限额；
4. 1000 是“同时提交”还是“同一节课陆续提交”？两者的容量/ETA 不同；
5. 能否接受“排队 + ETA”，还是必须 8–9 分钟内全部出片（后者需要高带宽归档/直接 OSS）。

## 七、建议的下一步（按顺序）

1. 找 provider 要 **OSS 直写/webhook + QPS/配额** 的明确答复；
2. 用一台香港/高带宽实例实测：单 IP 聚合吞吐、20GB 归档耗时；
3. 先做 Phase 1（流式 + DB 队列 + 4 进程 + 100 并发压测），这是所有方案的地基；
4. Phase 2 选型确定后再申请带宽/实例预算，做 1000 路真实验收。

> 现有 8 路 worker 只是止血；1000 路的核心不是“把 8 改成 1000”，而是把结果回传从 5–10Mbps 的单机入口上搬走，并把任务调度做成持久、多进程、可扩缩的 worker 服务。
