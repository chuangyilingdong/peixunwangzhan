# 修复：客户端安装包没走 OSS，每次下载都在吃服务器出口（2026-11-01）

## 现象

EIP 改成「150Mbps 按流量计费」之后，出方向开始按 GB 计费。查出口敞口时发现：

```text
GET /downloads/lingdong-client-0.2.10-win-x64.exe  → 200（无跳转）
GET /downloads/lingdong-client-0.2.10-mac-arm64.dmg → 200（无跳转）
```

`200 且没有 302` 意味着由 nginx 从本机磁盘发（`X-Accel-Redirect`），
**每个学生下载一次 143.9MB / 177.5MB 都在走服务器出口**。

## 根因

`/downloads/**` 的设计本来就是「OSS 上有就 302、没有才回本地」（`routes/publicAssets.js`）。
管理端上传接口（`routes/admin/clientInstallerUpload.js`）也确实会在发布时把包推 OSS ——
但推失败**不算发布失败**（只在响应里回 `ossSynced:false`），于是 0.2.10 这两个包
成了"本地有、OSS 没有"的状态，而没有任何人发现。

生产日志已轮转，查不到当时的失败原因。

## 处理

新增 `deploy/production/backfill-downloads-to-oss.mjs`：

- 只传**清单里引用的**那几个包（清单之外的旧版本不该有公开下载地址 ——
  nginx 里还专门 404 了几条老包路径，传上去等于把它们又放出来）；
- 已经在 OSS 上且大小一致的跳过（可反复跑）；
- 默认干跑，`--apply` 才真传。

执行结果：

```text
lingdong-client-0.2.10-mac-arm64.dmg（177.5MB）✓ 446ms
lingdong-client-0.2.10-win-x64.exe（143.9MB）✓ 370ms
汇总：已传 2 个（321.4MB）· 跳过 0 · 失败 0
```

> 走的是 OSS **内网端点**，321MB 不到 1 秒。

传完重启了一次服务，清掉进程里「OSS 上有没有」的 10 分钟探测缓存（重启前确认在途生成任务 = 0）。

## 验证

```text
/downloads/lingdong-client-0.2.10-win-x64.exe   → 302 → oss-cn-guangzhou.aliyuncs.com
/downloads/lingdong-client-0.2.10-mac-arm64.dmg → 302 → oss-cn-guangzhou.aliyuncs.com
/downloads/manifest.json                        → 200（本地，设计如此：必须每次读最新）
跟随跳转取 1MB                                   → 206，落地是 PE32 可执行文件（内容正确）
```

## 以后每次发客户端都要看一眼

上传接口推 OSS 失败是**静默**的。所以每次发版后跑一次：

```bash
for f in <清单里的文件名>; do
  curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" https://aicyld.com/downloads/$f
done
# 期望：302 + oss-...aliyuncs.com；出现 200 就是没推上去
```

或者直接重跑补传脚本（幂等）：

```bash
node deploy/production/backfill-downloads-to-oss.mjs --apply --env-file /etc/ai-kids-platform/production.env
```

## 残留

- 本地 `/srv/ai-kids-platform/downloads/` 还有 6.5GB 历史安装包，现在只作为兜底存在
  （OSS 探测失败时 nginx 才会发本地那份）。磁盘 13GB 空闲，暂不需要清理；
  真要清请注意别删清单引用的那两个。
- `manifest.json` 必须留在本地，别搬到 OSS。

## 补记：blockmap（2026-11-02）

### 现象

上线后第二天，安装包已经走 OSS 了，但日志里还有一条持续的 404：

```text
111.55.205.33 "GET /downloads/lingdong-client-0.2.11-win-x64.exe.blockmap" 404  UA=electron-builder
```

### 是什么

`.blockmap` 是 **electron-builder 生成的差分更新索引**。客户端更新时先取它，
用它算出"这次只需下哪几块"；**没有它就只能退回全量下载** ——
每个学生每次更新多下 144-178MB（在 OSS 账单上）。

注意：请求来自**打包那台机器**（UA=electron-builder），不是学生端 ——
说明文件在打客户端那边生成过，只是没传上来（`lingdong-client` 这个包一直没有 blockmap，
而 `junshi-desktop` 那批包里是有的）。

### 平台侧改了什么

1. `parseBlockmapName()`（`services/clientUpdateManifest.js`）：认
   `lingdong-client-<版本>-<平台>.exe|dmg.blockmap`，校验版本号，不合规返回 null；
2. 上传路由（`routes/admin/clientInstallerUpload.js`）加一支：走同一条**流式**落盘 + 推 OSS，
   但**不写清单**（它不是安装包，不参与版本判定）；额度单给 64MB（不是安装包的 600MB）；
3. 补传脚本顺带把安装包旁边的 `.blockmap` 一起推到 OSS；
4. `p146` 补 5 条断言（能传、字节落盘、**不改清单**、坏名字 400）。

> ⚠️ **绝不在服务端自己生成 blockmap**：分块格式必须与 electron-builder 那端完全一致，
> 猜一个会让差分更新算出错误的补丁 —— 比 404 更糟。

### 顺带修掉的一个测试 bug

`p146` 里「⑥ 三端同版本」那段引用了 `x64Digest`，而声明它的第 ⑦ 段排在**后面**，
运行时抛 `Cannot access 'x64Digest' before initialization` —— 整条守卫在第 32 条断言处中断，
后面十几条根本没跑。已把那段挪到 ⑦ 之后（它本来就是断言"三端都发完之后"的状态）。
修完 **40 条断言全过**。

### 还需要客户端这边配合一步

平台现在**能收** blockmap 了，但文件要从打包机传上来：

```bash
# 与安装包同一个接口，name 带上 .blockmap 后缀
curl -X POST "https://aicyld.com/api/admin/client-update/upload?name=lingdong-client-0.2.11-win-x64.exe.blockmap" \
  -H "Authorization: Bearer <管理员 token>" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @lingdong-client-0.2.11-win-x64.exe.blockmap
```

或者把文件发给平台侧，用补传脚本推（`backfill-downloads-to-oss.mjs` 已经会把同目录的
`.blockmap` 一起补）。

在传上去之前，更新器会一直退回全量下载 —— 功能不受影响，只是多花流量。
