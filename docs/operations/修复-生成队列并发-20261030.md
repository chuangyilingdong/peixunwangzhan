# 修复 · 生成队列串行，8 个学生同时生成 H3 排成一小时（2026-10-30）

## 现象

多个学生账号同时生成 MiniMax-H3，等了很久；部分学生觉得「结果丢了 / 没生成出来」。

## 现场证据（生产库 `generation_jobs`）

- 当天 9 条 MiniMax-H3 全部 `SUCCEEDED`，每条 1 个视频素材；
- 其中 8 条在 16:42–16:43 提交，实际 `started_at` 依次是：

```text
16:42:35 → 16:50:24 → 16:59:23 → 17:07:04
17:16:29 → 17:24:07 → 17:31:56 → 17:39:46
最后一条 17:48:15 完成
```

- 每条 H3 本身耗时 **7 分 50 秒 ~ 9 分 25 秒**；
- 因为串行，最后一位从提交到完成等了约 **65 分钟**；
- 8 条学生结果里 **7 条已挂回画布**（项目快照含对应 file_id）；
- 1 条结果（`generation_47cd357f084145ebb505` → `project_cda344cc06d34e3ea339`，
  `file_2404390ab1ca43e6952e`）在 17:39:46 完成，但学生最后一次保存是 17:24:42，
  提前离开了页面，所以画布快照里还没挂上。项目是 `DRAFT`，**重新打开项目会自动补挂**；
- 当天另有 11 条 `zhenzhen-image-g-v2.5-lowprice` 失败，是上游内容审核/12 小时冷却，
  **不是 H3**，与本次并发问题无关。

## 根因

`apps/server/src/routes/aiGeneration.js` 里：

```js
const asyncGenerationQueue = [];
let asyncGenerationWorkerRunning = false;
```

`drainAsyncGenerationQueue()` 用一个布尔保证**全进程只有一个 worker**，所有生成任务
（不分模态、不分用户）排成一条队。上游 MiniMax 账号实际不限并发，平台侧把它串行化了。

## 修复

- 新增 `AI_GENERATION_CONCURRENCY`（默认 **8**，上限 16）：`asyncGenerationActive` 计数，
  `while` 派发最多 N 个 `processAsyncGeneration`；
- 多 worker 下 `QUEUED → RUNNING` 必须原子认领：

```sql
UPDATE generation_jobs
SET status='RUNNING', started_at=?, worker_id=?, next_attempt_at=NULL
WHERE id=? AND status='QUEUED'
```

  只有 `claimed.changes` 非 0 的 worker 继续；重复入队/重试定时器不会让同一任务向上游提交两次；
- 启动日志打印 `[生成队列] 并发 8 路`；
- `.env.example` 增加 `AI_GENERATION_CONCURRENCY=8`。

## 发布与验证

- release：`20261030T095319Z`（源码 `0ceeb430`），39/39 自检通过，health 200；
- 发布前确认没有 `QUEUED/RUNNING` 的在途任务，未打断学生生成；
- 启动日志实际输出：`[生成队列] 并发 8 路（AI_GENERATION_CONCURRENCY 可覆盖，默认 8）`；
- 下次多个学生同时生成时，应能看到多条 RUNNING 同时存在；单条 H3 仍是 8-9 分钟（上游速度），
  但不再排队一小时。

## 调整与边界

- 班级人数超过 8 时，把 `AI_GENERATION_CONCURRENCY` 调到 16（或按服务器带宽/磁盘评估）；
  每条 H3 视频约 20-22MB，8 路同时归档约 160MB，当前磁盘 14G 空闲；
- 学生提前离开导致结果未挂画布的：重开 DRAFT 项目，前端会按 `box_id` 自动补；
- 该 worker 池是**单进程内**的；当前生产是单 systemd 进程。若以后改 PM2 cluster，
  需要把 `interruptOrphanedJobs` 的 worker 归属逻辑一起改成实例级，否则多个进程会互相回收任务。
