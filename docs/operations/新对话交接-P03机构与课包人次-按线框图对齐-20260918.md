### 必须新做的（这是主要工作量）

1. **机构多三个字段**（图2/图3/图5/图8 都要）：
   **机构简称**、**机构编码**（图7/图8 显示 `KB003`/`ORG0001`）、**所属区域**（图5/图8 显示"北京市·海淀区"）。
   现状：`organizations` 表**没有这三列**（已核对 `schema.js:56-68` 的建表 + 无相关 ALTER）。
   → 加列（`ALTER TABLE ... ADD COLUMN`，与仓库既有做法一致）+ 写进创建/编辑接口 + 回显。
   ⚠️ 机构编码若要"可读且稳定"，得定生成规则（如 `ORG` + 序号补零），并考虑**存量机构回填**。
2. **禁用机构要"必填原因"**（图4）：现在 `audit(...)` 里只记 `{action, status, actor}`（`organizations.js:272`）
   **没有原因**。→ `POST /:id/status` 接受 `reason`（必填、上限 500，与线框图一致），落审计；
   恢复/冻结等其它动作是否也必填原因，按线框图只有 disable 有 → **只对 disable 强制**，其它可选。
3. **平台侧「调整某机构某课包的人次」接口**（图7）：**没有**。
   现状只有"教师席位调整"（`seat-adjustments`）与"机构端把课包分给学生"。
   → 新增 `POST /api/admin/organizations/:id/course-quotas/:seriesId/adjust`：
   `{delta: ±N, reason: 必填}` → 改 `course_assignments.quota_total`；
   **校验：调整后 `quota_total` 不得小于 `quota_used`**（图7 的警示条就是这个，正是 `seat-adjustments`
   里"教师上限不能低于现有人数"的同款规则）+ 审计。
   注意与**许可三账**的关系：`license_purchase_batches` 记的是"平台卖给机构的批次"，
   而这里是"给机构开/调额度"——**两者要不要联动**（开额度是否生成一条批次）必须先定，
   否则平台账与机构账会对不上（见 `真实三账对照-20260914.md` 的口径）。
4. **人次变更记录（P03-04）—— 需要一张新流水表**：现在**完全没有**（已 grep 确认无
   `quota_change*` / `quota_ledger*` 之类的表）。
   线框图要求 5 种变更类型 + **变更前/后总人次** + 变更值 + 操作人 + 原因：
   | 线框图的类型 | 触发点 | 变更前/后总人次从哪来 |
   |---|---|---|
   | 初始开通 | 平台给机构开课包（建 assignment） | 0 → 初始人次 |
   | 增加人次 / 减少人次 | 上面第 3 条的新接口 | 调整前后各一次读取 |
   | 授权消耗（-1） | 机构端把课包分给学生（`POST /api/org/course-grants`） | 总人次**不变**，变的是已分配（图8 的 `变更前总人次=321 → 变更后=320` 说明它把"剩余"当成了总人次口径 —— ⚠️ **这点要跟用户确认**，见第五节） |
   | 授权取消返还（+1） | 平台撤销学生授权（`POST /api/admin/course-grants/:id/revoke`） | 同上 |
   → 新表 `course_quota_changes`（系列 × 机构 × 类型 × 变更值 × 变更前后总人次 × 操作人 × 原因 × 时间）
   + 在上述 4~5 个写入点各插一条 + 列表接口（按课包/类型/时间范围筛、分页）。
   ⚠️ 这也正是**上一轮 002-07「人次变更流水」被推迟的原因**（当时没有前后值可存）——
   线框图现在明确要它，所以这次要做，并且**要从现在开始记**（历史数据补不出来）。

## 四、与既有口径的关系（别走岔）

- 机构端的「授权消耗 / 授权取消返还」事实已经在 `student_course_grants` + `license_revenue_events` 里，
  P03-04 的流水**不要**去改这两处的语义，只做"把发生的事记成一笔可读流水"。
- **取消授权只有平台端有权限**（用户口径，已固化）：所以图8 的「授权取消返还」操作人一定是平台账号 ——
  与机构端 002-05「学生授权记录」里那条口径一致。
- 许可三账（`真实三账对照-20260914.md`）里的"批次/收入事件/分摊"是**财务账**；
  本页的"人次"是**库存账**。两者**可以不一致**，但界面上必须说清是哪一个口径（否则又是一轮对不上账）。

## 五、开工前必须先跟用户确认的两件事

1. **图8 的"变更前/后总人次"到底是哪个数？**
   线框图里 `授权消耗 -1` 那行写的是 `321 → 320`，而"总人次"按我们现有口径是 `quota_total`（授权消耗**不动它**，
   动的是 `quota_used`）→ 所以线框图那一列看着像**剩余人次**（或"可用余额"）。
   → 要么这一列改叫**剩余人次**，要么我们按"总人次 − 已分配"来记 —— **得让用户拍一下**，否则表建好就记错。
2. **平台给机构"开额度 / 调额度"要不要自动生成许可批次？**
   若生成，则"人次库存"与"许可三账"同源；若不生成，则两者会各自演化（机构买的批次 ≠ 平台开的额度），
   财务对账时又得解释一遍。建议：**开额度时选填关联批次号**，默认不生成，但把关系留出字段。
