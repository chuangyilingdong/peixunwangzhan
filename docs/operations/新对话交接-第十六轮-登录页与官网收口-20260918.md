## 三、不许破的口径

**第十五轮那五条全部仍然有效**（①平台侧只有"授权次数"没有"算力额度" ②额度一律不拦人、学生端看不到
③内部成本口径不上公开面、验收有反向断言 ④取消授权只有平台端有权限 ⑤上游账户余额只有平台端能看）。
这一轮又长出几条**工程口径**，同样是"踩过之后才写下来的"：

1. **官网文案优先改 CMS**（键：`HOME / INTRO / FAQ / HANDBOOK / BRAND`，后台「官网内容」页）。
   改代码里的 `CMS_FALLBACK` 时要**与 CMS 当前内容对齐**，否则接口慢/挂时会露出不一样的文案
   （本轮"强刷闪旧内容"就是这么来的）。接口回来前**不渲染文案**（`ready = !cms.loading`）。
2. **首页与登录页的按钮是一套 specular 组件**：hero 两个 CTA + 黑底首页顶栏三个入口。
   ⚠️ 只在**黑底**上用（光效是"白线在暗面上扫"，浅底等于看不见）；浅底内页用原来的实心/描边胶囊。
   它渲染的是 `<button>`，导航走 `onClick + navigate`（右键新标签打开不可用）。
3. **字号不许只按 vw 写**：vw 与文字所在盒子的宽度无关，盒一变窄就折行（本轮品牌主张折成三行）。
   要用**容器查询单位 cqw**（`.login-copy` 已设 `container-type:inline-size`）或按字数内联算
   （首页 `.hp-title` 是后者）。同理，`nowrap` 之前必须确保尺寸放得下。
4. **装饰层不许伸到盒子边缘**：环境光斑曾被网格栏（`overflow:hidden`）裁出一条硬边（用户报"有明显的
   边框痕迹"）。做法：不外扩 + 加渐隐遮罩（`mask-image`）。**验证手法**：把视频临时藏掉看整页是否纯黑零边界。
5. **`overflow:hidden` 仍可被程序化滚动**：焦点滚入视野会把整页横向滚（本轮 224px）。要禁止就用
   `overflow-x: clip`。
6. **改守卫断言前先看它在查什么**：本轮有 4 处断言因口径变更失效（`p6` 官网导航标签、`p75`/`p87`
   退役的 `estimatedCostFen`、`verify-production-entrypoints` 的登录文案与"预约演示"）。改的时候要
   注明 `口径变更，不是测试漂移`，并**顺手看它是否已变成空转**（比如查的词已不存在 = 断言失效）。

## 六、守卫与验证怎么用（这一轮更新过的部分）

- **跑守卫用的 node**：`C:/Program Files/nodejs/node`（v24）。**`pnpm` 也必须用它** —— 默认 PATH 的 node 是
  v16，pnpm 会直接报 `requires at least Node.js v22.13`。做法：
  `export PATH="/c/Users/Administrator/.vibe-coding/node:$PATH"`。
- **快**：`node scripts/p70-pages-render.mjs`（三端 **88** 页，含三端登录页；改前端必跑）。
- **全量**：`node .tmp/smoke-run.mjs`（123 个）。⚠️ 本轮给它加了一条：**失败时把子进程输出落到
  `.tmp/smoke-fail-<name>.log`** —— 以前只剩一个秒数，每次都要靠单跑复现去猜原因；这一轮靠它一次定位到
  `schema.js` 的迁移。**但 runner 本身在 .tmp（未受版本控制），建议一并移进 scripts/。**
- **p111 很慢**（约 2 分钟、28 张截图）：它是机构/教师端的真浏览器端到端，改机构端/教师端必跑；
  只改官网跑它没意义。
- **浏览器验收必须是"真浏览器 + 真站点"**：这一轮所有"只有生产才犯"的问题都是这么抓到的。
  生产 CSP 很紧（`script-src 'self'`，没有 `font-src`），外链字体/脚本一律会被拒收。

## 七、这一轮踩过的坑（都值钱，别重复）

1. **bash 里内嵌 `node -e "…"` 改文件会把 `${name}`、反引号当展开/命令替换** —— 我为此两次写坏文件
   （55 个守卫文件里写进了字面量 `${name}`；README 里代码片段被替换成空字符串）。
   **纪律：批量改文件用 Write 写出来的脚本文件（不经 bash 转义）+ 先 dry-run + 先只改一个文件验证，再铺开。**
2. **"偶发守卫红项"不是机器负载**：真根因是 `schema.js` 的启动迁移没有 `busy_timeout`；
   `busy_timeout` 还治不了「延迟事务升级死锁」，所以写事务要用 `BEGIN IMMEDIATE`。
   （我为此先误判成负载、又误扫了 127 处守卫连接，最后靠**失败日志的堆栈**才定性。）
3. **一个"残留"往往有第二个来源**：强刷闪旧内容 = `index.html` 骨架屏（静态 HTML 里的旧文案）
   + CMS 兜底文案，两头都要治。**骨架屏尤其容易漏** —— 它不在任何组件里，只有强刷才看得见。
4. **改文案/组件后要检查"断言是否还在真的断言"**：本轮 `websiteNavRejected` 查的「预约演示」
   已从代码里消失 → 断言变成永远通过（空转），换成只属于官网导航的「灵动学习」才重新有效。
5. **装饰性出血会带来真 bug**：光斑/装饰线伸到容器外 → ①被裁出硬边（视觉）②让容器可被程序化滚动（交互）。
6. **部署脚本的自检是有效的**：本轮它拒绝过一次切换，别绕过它。

## 九、补做（同一天，官网上线之后）

### A. 新增 `scripts/p115-website-ui-check.mjs`（官网首页 + 登录页的真浏览器守卫）

这一轮那四类"只有人眼能发现"的问题，现在都是可复跑的断言：

- **横向程序化滚动**：不查 CSS 写了什么，而是把页面上**每个可聚焦元素真 focus 一遍**，
  再扫全文档有没有哪个容器 `scrollLeft > 0`；另外查 `.site / .hp / .website-login / .login-page /
  .login-intro` 有没有**横向溢出** —— 溢出是"因"（装饰伸到盒子边缘），`overflow-x: clip` 只压住了症状。
- **品牌主张恒定两行**：**7 档宽度**（1600 / 1440 / 1280 / 1120 / 960 / 820 / 420）逐个量
  `height ÷ line-height` 的行数与 `scrollWidth - clientWidth` 的溢出差。
- **光斑硬边**：官网这侧断言 `.login-intro::before` 的 computed `display === 'none'`。
  ⚠️ 两处要说清：官网隐藏它的**真实原因是"视频上再叠一层紫光会出色差"**，不是硬边；
  硬边那个修法是共享 CSS 里的 `mask-image`，**是给平台端/机构端用的，目前没有守卫**（见 D）。
- **强刷闪旧文案**：三处来源一起验 —— ①接口正常；②接口**定向延迟 1800ms**（断言首帧**不出任何文案**，

### G. ⚠️ 「偶发守卫红项」**没有根治** —— 这次把它的全貌摸清了（**下一轮最该做的一件事**）

这次全量跑第三遍时又出现一条红项：`p14-list-pagination` 10 秒失败，日志是
**`database is locked`，崩在 `schema.js:12`**（就是 `PRAGMA journal_mode = WAL` 那一句），
随后服务起不来 → 守卫超时。单独复跑 p14 **通过** —— 正是 §七.2 描述过的那个"偶发、每轮换一个、单跑又全过"。

于是这次把它当真问题追了一遍，先写了个最小复现（`.tmp/verify-startup-race.mjs`：
**同一条库路径同时起 4 个进程 import schema.js**，跑 8 轮 = 32 次启动），结论如下：

| 实测（32 次并发启动） | 失败模式 |
|---|---|
| 修之前 | `database is locked` ／ `duplicate column name: compute_snapshot` |
| 修了两个具体点之后 | `database is locked` ／ `UNIQUE constraint failed: platform_alert_thresholds.alert_type`（0~4 次/32，波动） |

**修了两处（都是真 bug，但都不是根治）**：

1. **`busy_timeout` 原来排在 `journal_mode = WAL` 之后** —— 而 WAL 那句本身就要抢写锁，
   等于**最危险的第一句在裸奔**（`schema.js:12` 的堆栈就是它）。§七.2 当时只修了迁移语句，漏了第一句。
   现在顺序改成 `busy_timeout → journal_mode → 其余`（注释里写明顺序不能动）。
2. **`if (列不存在) ALTER` 是 TOCTOU**：两个进程都判"不存在"、都去 ALTER，后到的拿
   `duplicate column name` 并**崩在启动路径上**。新增了 `addColumnIfMissing()`：幂等 + **只吞
   `duplicate column name` 这一种错**（⚠️ 别写成 `catch {}`，那会把真失败吞掉；`student_seats`
   那处还要用返回值区分"是不是我加的"，因为它的回填**只能在真新增列时跑一次**）。
   改完 `duplicate column name` 这一类没再出现。

**没修掉的（下一轮该做的）**：`database is locked` 与 `UNIQUE constraint failed` 都还在。
根本问题不是少一个 pragma，而是 **`schema.js` 在 import 时跑全量迁移（上百条 ALTER + 若干条补种 INSERT），
多个进程同时起来就各自跑一遍**。加超时只能把窗口收窄、不能消除；`UNIQUE` 那条更说明连"先查后插"的
补种逻辑也在并发下会撞。
**建议的正解**：给启动迁移加一把**跨进程锁**（例如在固定路径上取一个独占锁文件，或先
`BEGIN EXCLUSIVE` 一把专门的锁表），**只让一个进程迁移**，其余等待并在拿到锁后确认"已经迁移过了"就跳过。
这属于基础设施改动，不要顺手做 —— 它会影响三端 + 生产启动路径，值得单独一轮 + 单独验收。

**影响面（为什么可以带着它发布）**：生产是 `systemctl restart` 单个服务，**同一时刻只有一个进程在迁移**，
所以线上受影响很小；真正被它折磨的是**本地全量守卫**（几十个进程各自 spawn 服务 + 自己写库）。
留个可复跑的尺子：`node .tmp/verify-startup-race.mjs`（建议下一轮和 `p115`/live-check 一起移进 `scripts/`）。

> 完整结论就是上面这张表 —— 它是一个**类**，不是一条。
