## 五、本轮（09-24 下午）修的那个 bug：**毒连接**（与夹具改造无关，但它一直在坑验收）

```text
症状：SQLite 快速套件这次跑出 **11/12** —— p119-runtime-upload-submit 被判「120s 超时失败」。
      单独跑它是**过的**（23 条断言全过），只是**跑了 5 分 07 秒**。
      ⚠️ 同一份代码：09-24 12:30 跑是 8.8 秒（.tmp/acceptance-after-revert.json 里留着一行记录），
         12:45 就 307 秒 —— "偶发"两个字就是这么来的。

定位（一步步量出来的，别跳）：
      ① 给 p119 的每条 check 加计时 → 慢的**只有一条**：「画布课堂：/status 也不认它」= 304.8 秒
      ② 那一条紧跟在**两个超大包**（17MB / 30MB，测上传上限）之后
      ③ 最小复现：POST 30MB → 紧接着连打 /health —— **第一个 0.0 秒回、第二个挂 60 秒没回来**

根因：服务端读 body 是**读到一半就回话**的（readJson / readBodyBuffer 一超限就抛；读 body 之前
      的内存闸 UPLOAD_BUSY 更狠，压根没读），但响应**还写着 `connection: keep-alive`** ——
      这条连接上还堵着十几 MB 没写完的字节。客户端（undici）把它放回**连接池**，
      下一个被分到它的请求就挂住，直到 TCP 层放弃（实测 304 秒）。
      这也解释了 p119 里那句老注释「偶发在连接层失败（Windows 上实测 fetch failed）」：
      当时只当抖动、加了一次重试，**真凶没找到**。
      （不只影响验收：真实客户端复用这条连接一样会挂，所以这是服务端该修的。）

修法（apps/server/src/index.js，一处）：请求体没读完就回话时，响应带 `connection: close`。
      判据用 `req.complete === false`，**不列举错误码** —— 列举法会漏掉下一个没想到的拒绝分支
      （这个仓库已经吃过好几次「只想到①、被②绊倒」的亏）。实测语义（Node 22 探针验过，不是猜的）：
      正常读完 / GET / DELETE / 空 body 都是 true，只有"没读完"是 false。

效果：p119 从 **307 秒 → 2.25 秒**；快速套件 12/12 → **13/13**（26 秒）。
      顺带把 `rds-p2-fixture-codemod.mjs` 归进 HARNESS：它是**工具**（默认试运行），
      上一轮被当成一个测试跑了 —— 清单从 150 变 149 是这个原因，不是行为变了。

新钉子：`scripts/p138-oversized-body-keepalive.mjs`（已进 CI 的 FAST 精选，占 2.7 秒）钉三件事：
      · 超限拒绝**仍然说中文**（PAYLOAD_TOO_LARGE）—— 别为了关连接把原因吞了；
      · 拒绝之后紧接着的 3 个请求必须秒回（**连打三次**：毒连接要被复用上才发作，打一次测不出来）；
      · 反向也钉住：正常请求仍然 keep-alive（别一刀切把整站改成关连接）。
      验过它**真会红**：把修复临时撤掉 → 第①条立刻失败（实际 `keep-alive` ≠ 期望 `close`）；恢复后全绿。
```

### 两个线上 bug（都是"不报错、只是看不见"）

```text
① OSS 对象键**双重前缀**（修的是"生成成功但图片不显示"的一大半）：
   写进库的是**带前缀的完整键**（putObject 返回 key = 前缀 + 相对键），而读路径（signedUrl /
   headObject / getObjectToFile / deleteObject）每个都又过了一次 withPrefix →
   键变成 `lingdong/lingdong/2026/09/xxx.png` → OSS 404。
   症状：下载接口照常 302（nginx 日志里只看得见那个 302），404 发生在 OSS 那边；
   画布那边 blob 取不到就静默显示空框。生产实测：281 个 OSS 行里 275 个是回填的相对键（正常）、
   **6 个是新上传的完整键（全部读不到）**，而且此后每次新上传都会坏。
   修法：withPrefix 幂等（`=== 前缀` 或 `前缀/` 开头就原样返回）。修完实测 8/8 素材可读，
   那张学生图 302 过去是 200 + `image/png` 1406401 字节（941x1672）。

② **bucket 没有 CORS，且生产密钥无权改**（这是"不显示"的另一半，也是**仍然存在的约束**）：
   `OPTIONS` 预检 403、GET 不带任何 `Access-Control-*` 头；用生产密钥读 CORS 配置直接被拒
   （`oss:GetBucketCors` → AccessDenied，"The bucket you access does not belong to you"，
   桶属于另一个账号）。nginx 配置里那句注释早就写了这件事（"OSS 不返回 ACAO，除非给 bucket 配 CORS"），
   但**画布是用 fetch 取素材的**（CORS 模式）→ 读不到响应体 → 拿不到 blob → 框体空白。
   修法（不依赖 bucket 配置）：`useDisplayUrl` 解析不出东西时**退回原始 /api 地址**，
   让 <img>/<video>/<audio> 自己去取 —— 子资源加载不吃 CORS，认证走登录种下的 `platform_token`
   cookie（服务端 readToken 认它；客户端那台机器上确实是用网页登录过的，日志里有 POST /api/auth/login 200）。
   ⭐ 长期正解仍是给 bucket 配上 CORS（允许 https://aicyld.com，GET/HEAD）：那样 blob 那条路也能通，
   而且 `fetchDataUrl`（沙箱 iframe 里要 data: 的场景）才不会继续受限。
   **✅ 2026-09-24 下午已经配上了**（用户给那个 RAM 用户补了 `oss:GetBucketCors` / `oss:PutBucketCors`
   之后，由我用签名请求 `PUT /?cors` 写入；桶属主账号 = 1280578137306348，子用户 aild@…）：
     来源 https://aicyld.com、方法 GET/HEAD、AllowedHeader `*`、Expose ETag/Content-Length、
     MaxAge 600、**ResponseVary true**（返回 Vary: Origin）
   实测（配完之后）：预检 `OPTIONS` → **200** + `Access-Control-Allow-Origin: https://aicyld.com`
   + `Access-Control-Allow-Methods: GET, HEAD`；跨域取那张学生图 → **200 / image/png / 1406401 字节**
   + `Access-Control-Allow-Credentials: true` + `Vary: Origin`。⇒ 画布的 blob 取图这条路现在是通的，
   §七① 那条"退回原始地址"的兜底**继续留着当安全网**（解析成功走 blob、失败走原始地址，两条都行）。
   ⚠️ 两个实测细节：**OSS 的 CORS 配置写入后有传播延迟**（`PUT` 回 200 后立刻回读仍是
   `NoSuchCORSConfiguration`，等几秒再读才对 —— 别以为没写进去就去反复写）；
   **来源不要写 `*`**：取图是带 credentials 的，浏览器要求 ACAO 回具体来源 + ACAC: true。
```
