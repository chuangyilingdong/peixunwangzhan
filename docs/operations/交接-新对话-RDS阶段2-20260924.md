## 四、最值得记住的几条（都是实测出来的）

```text
1. **"验证装置"自己也会骗人**（这一轮又栽两次）：
   · p9-r04 打印了 passed 却被判"超时失败" → mysql2 连接池握着事件循环（idleTimeout 不足以放行，
     必须显式关池；unref 太危险：查询在途时事件循环可能空掉 → 静默丢语句）
   · MySQL 侧突然全红 → 夹具自己连了一个**还没建的库名**（Unknown database）
   **先确认测量工具是对的，再相信它给出的数字。**

2. **同一个根因有好几张脸**：schema.js 的导入期代码 ①建表 ②插默认行 ③回填 —— 只想到①，
   被②绊倒（表现是"AI 能力全被平台关掉"，看着像业务 bug，其实是数据缺行）。

3. **只有"可证明等价"才配做翻译**：json_extract 一开始也被塞进翻译层，实测直接语法错
   （正则补不了配对的右括号）→ 撤掉，改成调用点用 jsonText()。
   而且**翻译层写完必须拿真实的失败输入再打一次** —— 有条规则因为文件里被写进了一个字面退格符
   （\x08 而不是 \b）而**静默不生效**（不报错，只是不生效）。

4. **危险的是"静默出错"那一类**：json_extract 在 MySQL 返回带引号的 JSON、NOW_SQL 的毫秒位数不同
   （会让字符串比较排序错）、`Number(asyncFn())` = NaN（漏 await 的夹具）—— 都不报错，只会悄悄算错。

5. **拿真数据跑才能发现真问题**：`ORDER BY … DESC NULLS LAST`（MySQL 没这个语法）正好卡在
   **广场浏览**那条查询上；种子数据 + 那 12 个脚本覆盖不到它 —— 一打真数据就 500。
```
