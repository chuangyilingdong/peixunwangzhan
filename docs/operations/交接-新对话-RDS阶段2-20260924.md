## 五、本轮（09-24 下午）修的那个 bug：**毒连接**（与夹具改造无关，但它一直在坑验收）

```text
症状：SQLite 快速套件这次跑出 **11/12** —— p119-runtime-upload-submit 被判「120s 超时失败」。
      单独跑它是**过的**（23 条断言全过），只是**跑了 5 分 07 秒**。
      ⚠️ 同一份代码：09-24 12:30 跑是 8.8 秒（.tmp/acceptance-after-revert.json 里留着一行记录），
         12:45 就 307 秒 —— "偶发"两个字就是这么来的。

定位（一步步量出来的，别跳）：
      ① 给 p119 的每条 check 加计时 → 慢的**只有一条**：「画布课堂：/status 也不认它」= 304.8 秒
      ② 那一条紧跟在**两个超大包**（17MB / 30MB，测上传上限）之后
      ③ 最小复现：POST 30MB → 紧接着连打 /health —— **第一个 0.0 秒回、第二个挂 60 秒没回来**

根因：服务端读 body 是**读到一半就回话**的（readJson / readBodyBuffer 一超限就抛；读 body 之前
      的内存闸 UPLOAD_BUSY 更狠，压根没读），但响应**还写着 `connection: keep-alive`** ——
      这条连接上还堵着十几 MB 没写完的字节。客户端（undici）把它放回**连接池**，
      下一个被分到它的请求就挂住，直到 TCP 层放弃（实测 304 秒）。
      这也解释了 p119 里那句老注释「偶发在连接层失败（Windows 上实测 fetch failed）」：
      当时只当抖动、加了一次重试，**真凶没找到**。
      （不只影响验收：真实客户端复用这条连接一样会挂，所以这是服务端该修的。）

修法（apps/server/src/index.js，一处）：请求体没读完就回话时，响应带 `connection: close`。
      判据用 `req.complete === false`，**不列举错误码** —— 列举法会漏掉下一个没想到的拒绝分支
      （这个仓库已经吃过好几次「只想到①、被②绊倒」的亏）。实测语义（Node 22 探针验过，不是猜的）：
      正常读完 / GET / DELETE / 空 body 都是 true，只有"没读完"是 false。

效果：p119 从 **307 秒 → 2.25 秒**；快速套件 12/12 → **13/13**（26 秒）。
      顺带把 `rds-p2-fixture-codemod.mjs` 归进 HARNESS：它是**工具**（默认试运行），
      上一轮被当成一个测试跑了 —— 清单从 150 变 149 是这个原因，不是行为变了。
```

### 25.1 课件预览不再吃那 5 Mbps

搬之前的链路（每一步都是生产实测出来的）：

```text

       → 而且每次都重写一遍源文件 → mtime 变新 → 转换缓存当场作废 → **每次预览都重转一遍**
```

搬之后（`prepareFilePreview(ctx, file, { ossOffload: true })`，只开给机构端的教学素材预览）：

| 形态 | 现在怎么走 |
| --- | --- |

| 作品文件（`<iframe>` 打开的那几处） | 原样：本机流式发，**不许跳**（跨域 iframe 会被 `default-src 'self'` 挡成白屏） |

### 26.1 PPT 原生渲染（`.pptx` 不再转 PDF）

**做法**：前端 `pptx-preview` 在浏览器里解析 OOXML、把每张幻灯片画成 DOM。

**取原始文件、不做转换**，OSS 行 302 到对象自己的签名地址（106MB 的课件也从 OSS 直取）。
鉴权与 `/preview` 一字不差，且**只认 .pptx**：`.ppt`（97-2003 二进制）解析不了，照旧转 PDF。

界面按 WPS/PowerPoint 的版式：**左缩略图栏 + 右侧一屏一张**；缩略图是解析好的幻灯片 DOM

`pptx-preview` 按需加载（独立 chunk，gzip 430KB），只有真打开 PPT 才下。

**验收数据**（本机真浏览器，16 张真课件）：
`第 1 / 共 14 张`、左栏 14 张缩略图全部画出、翻页后 `.on` 跟着走、全屏后
`head/rail/toolbar` 三处 `display:none` 且幻灯片满宽 1444px；106MB 那份**解析 0.9 秒**（15 张）。

**⚠️ 一条口径变了（必须记住）**：原生渲染要求浏览器拿到 `.pptx`，所以「原始文件不下发」
**不再成立**。界面文案已改成"不提供下载入口"，代码注释也写明了。同理，`.ppt` 与 docx/xlsx 仍走

后台「客户端更新」页新增**上传并发布**（`apps/admin/src/pages/ClientUpdate.jsx`）。

```text
浏览器（XHR，能看进度）──POST 原始字节──▶ /api/admin/client-update/upload?name=<安装包名>
   ↑ 必须 XHR：377MB 在 5 Mbps 上要十分钟，fetch 拿不到上传进度
服务端（routes/admin/clientInstallerUpload.js）：
   ① 权限 = ADMIN_AUDIT（与「客户端更新」配置同档）
   ② **流式落盘**（req → 临时文件，边写边算 sha256，有背压）→ 同目录 rename 定稿
      为什么不能走通用上传管线：那条把整份 body 读进内存（硬顶 200MB，这台机以前被打穿过）
   ③ 原子写 manifest.json（版本/文件名/字节数/sha256 四样齐全，并保留后台配的策略字段）= **触发更新**
      客户端每次启动都带 ?t= 拉 /downloads/manifest.json?，它看到新版本就自己下
   ④ 顺手流式推 OSS（`putObjectFromFile`）→ /downloads/<名字> 302 到 OSS 客户端才下得动
nginx：`location = /api/admin/client-update/upload` 单开一条（client_max_body_size 800m +
      proxy_request_buffering off —— 开着的话 nginx 会先把 377MB 落盘再转发）
```

文件名按**客户端的契约**先拦：`lingdong-client-<版本>-win-x64.exe`（Mac 是 `-mac-arm64.dmg`），
不合规直接 400 —— 名字不对的包传上来客户端也永远装不上。

### 26.4 发送次数虚高（客户端报的那个）

现场：客户端 `sends = {limit:8, used:8}` 把学生锁死，而 DSH 自己的会话投影是 2 轮。
根因：判据数的是"历史里像学生发的 user 消息条数"，而 0.1.7 注入的上下文块比 09-19 那版多，
老判据只认两种形态，认不出的全被当成学生按的发送。

修法**三条一起**（都在 `services/vibecodingLessonSettings.js`）：
1. **补判据**：时间快照 / compaction 检查点 / compaction 请求 / 切模型通知 / 重复工具调用提醒 /
   运行时上下文清零态 / 起标题请求（原来"有意不排"的那个，有了夹取之后它会变成永久虚高）。
2. **夹取（治本）**：同一请求里真人只可能 +1 → `seen = min(observed, seenBefore + 1)`。
   这一条对**还没见过的新注入形态免疫**，也是对学生的保护。
3. **工具轮不推计数**：末尾不是"像学生发的那条"就一点都不推 —— 用户的"任务还在跑就 8/8"就是这条没管住。
   另外认不出来的注入会打一行 `[发送计数]` 告警（内容前 80 字），下次出新形态照日志补。

生产上被抬高的记录已归零：`session_students.vibecoding_sends` 里 09-24 起那 3 条（8 / 6 / 5，
都是测试账号）→ 0；09-23 及更早的 5 条（1~3，0.1.6 那版客户端的）保留没动。
⚠️ 这类计数是单调最大值：**虚高的数不会自己降下来**，以后修完口径要顺手看一眼有没有锁住的学生。

### 26.5 给客户端的（用户问的「需要客户端配合的你告诉我」）

* **安装包上传/发布**：客户端**不用改**。它启动时读 `/downloads/manifest.json`（带 `?t=` 绕缓存），
  按 `version` / `channel` / `enabled` / `files['win-x64']` 判断要不要更新 —— 后台这一套写的正是这些字段，
  连 `sha256` / `size` 都是服务端算好后写进去的，与它们的 `LingdongUpdater` 校验口径一致。
* **Mac 包**：updater 目前只认 win32+x64（`updateTarget()`），所以 mac 用户走官网手动下载 —— 要自动更新得客户端那边补 mac 分支。

| 指标 | 换视频前 | 换视频后 |
| --- | --- | --- |
| 首屏总下载 | **2510 KB** | **1594 KB**（-37%） |
| 其中视频 | 1817 KB（hero-animal） | **894 KB**（hero-rabbit） |
| 视频可达可播 | readyState 1（还没下完） | readyState 3 |
| `load` | 1.1 s | 1.0 s |

  这是这个文件里已经踩过一次的坑（CSP 那段注释）。

### 27.5 深挖：首页那 6MB 图片（当天下午补的第 4 件事）

把「流畅度」当真查下去，发现首屏以下真正的胖子**不是视频，是 CMS 配图**：

```text

那 6.2MB 图片 = 4 张 CMS 配图，直接引了**上传原图**（PROMO_COVER）：

   file_52b10ece64ef4708859a  微信图片_2026….png    2.53MB  2758×1412
   file_78a2886f8b9147ff98a1  926b6581-….png        0.37MB  1671×976
   file_a84e84bb3d1542deacec  77e95e8b-….png        0.08MB  1560×639
```

**修法：给下载口加「按宽度取」**（`/api/public/file-assets/:id/download?w=1200`）——
302 到 OSS 时带上 `x-oss-process=image/resize,w_1200/format,webp/quality,q_80`，

* 只在「**图片** + 带 `w`」时生效；下载口其余情况一律照旧（还是原件）。
* ⚠️ `x-oss-process` 是 OSS 的**子资源，必须进签名**（`objectStorage.signedUrl` 的 `imageProcess`）——
  漏签的表现是 **403**（看着像权限问题），所以 p136 专门钉了"带与不带它、签名必须不同"。
* 宽度夹在 64~2000；非法值 `imageProcessFor` 返回 null，调用方退回原图。
* 顺手把 HOME 那 4 处 CMS 配图改成 `?w=1200`（**内容也改了**，备份在服务器
  `/root/website-content-backup/HOME-{draft,published}-<时间戳>.json`；后台里随时可改回去）。

## 二十九、2026-09-26：「机构一点授权就报『购买批次余额不足，无法确认收入』」

> 用户报障原文：「为什么这个机构账号授权这个学生会出这个报错」（截图：机构端「课包库存与学生授权」，
> 顶部红条 **购买批次余额不足，无法确认收入**；课包显示「已用 0 / 6 次 · 剩 6 次」，学员「可授权」）。

### 29.1 根因：两条口径在「把课发给学生」这一步撞上了

```text
平台后台「机构与课包人次 → 调整授权次数」    ← 这条路径**按设计不生成许可批次**
        ↓ 授权单 quota_total 变成 6                     （源码原话：「财务账不受影响，用户未要求联动」）
机构端「课包库存与学生授权」看到「剩 6 次」   ← 读的是 quota_total - quota_used
        ↓ 点「授权给学员」
appendLicenseGrantRevenue → nextFifoUnit()   ← 这一步**要求有批次**做 FIFO 收入分配
        ↓ 一条批次都没有
LICENSE_PURCHASE_BALANCE_EXHAUSTED：购买批次余额不足，无法确认收入
```

生产上**三个授权单**都有这个缺口（说明不是一次性的）：培扬 0/6、灵动未来科技 5/10、银河少年创客中心 1/51。
后两家还是"部分覆盖"——批次有一点、但不够授权单上的次数。

### 29.2 修法：在「真要发给学生」那一刻补齐缺口

## 三十一、2026-09-26 收盘前：三端「带关键字搜索」在 MySQL 上必 500（SQLite 容忍）

> 这一条是**交接前跑全量套件时顺手挖出来的生产故障**，不是谁报的 —— 顺手看一眼 journalctl 就看见了。

### 31.1 现象与根因

生产日志 3 小时里 **48 行** `ER_PARSE_ERROR`，SQL 是这种形状：

```sql
... AND (work.title LIKE ? ESCAPE '\' OR student.display_name LIKE ? ESCAPE '\' ...)
```

MySQL 默认把反斜杠当转义符 → `'\'` 被读成**没结束的字符串** → 整条 SQL 语法错误。
SQLite 不把反斜杠当转义符（`'\'` 就是"一个反斜杠"）→ 本地全量套件**一路绿**。
经典"SQLite 容忍、MySQL 严格"，而且踩中面很大：**三端所有带关键字的搜索**
（平台端作品库 / 用量报表 `p13`、机构端作品检索、学生端「我的作品」检索，以及 admin/helpers 那一族列表筛选）。

### 31.2 修法

* `apps/server/src/lib.js` 新增两个 helper：
  * `likeEscapeClause()` —— 按方言选写法（**MySQL `ESCAPE '\\'`（SQL 文本两个反斜杠）/
    SQLite `ESCAPE '\'`（一个）**，别"顺手统一"）；
  * `likeKeyword(search)` —— 把用户输入里的 `% _ \` 转义掉再用 `%` 包起来。
* 7 处调用点全部改用它（orgAdmin ×4、admin/helpers ×3、student ×2）。
* 守卫 `p143`（MySQL 严格/SQLite 容忍 的静态网）加第 ③ 条：
  **生产代码里不许出现手写的 `LIKE … ESCAPE`**，只能通过 helper；顺带钉住 `likeKeyword` 会转义 `% _`。
* 验证：本机 MySQL 容器 + 真服务，7 条带关键字的搜索请求（含 `%25`、`a_b%25c` 这种转义路径）
  **全部 200**（`.tmp/verify-search-mysql.mjs` 那次跑法，脚本已随本轮删掉；要复现就用那 7 个 URL）。

⚠️ 这条也是"**MySQL 侧那套套件必须跑**"的又一例证：SQLite 侧永远看不见它。

## 三十三、2026-09-26 晚：画布课堂「当前作品状态不允许重新提交」—— 作品**已发布**了

> 用户原话：「提交新增的生图结果，遇到报错。（之前先生文→提交→生图片1→提交是正常的）画布课堂为什么会出现这个报错。」

### 33.1 根因：不是这次改坏了，是这台作品**已经发布到作品广场**

审计流水（生产，按时间）：

```text
15:27:19  STUDENT      PROJECT_SUBMIT  round 1 (resubmission=false)   → 作品创建（PENDING）
15:30:01  STUDENT      PROJECT_SUBMIT  round 2 (resubmission=true)    → 正常（PENDING→PENDING 合法）
15:31:44  SUPER_ADMIN  PLATFORM_WORK_PLAZA_PUBLISH  PENDING → PUBLISHED   ← 平台端「发布到官网」
15:34:21–15:56:47  STUDENT ×6  DOMAIN_INVALID_TRANSITION（INVALID_WORK_TRANSITION）
                                  = 「当前作品状态不允许重新提交」
```

所以"前两次正常、这次不行"的原因很清楚：**前两轮提交时作品还是 PENDING**（增量提交允许 PENDING→PENDING）；
15:31 平台端把它**发布到作品广场**之后，状态机里 `PUBLISHED → PENDING` **不是合法转换**
（`PENDING / APPROVED / REJECTED / UNPUBLISHED` 都可以），于是学生再提交就被挡。
要接着提交的**正规路径是先下架**：`PUBLISHED → UNPUBLISHED`（作品管理里「下架」）→ 之后 `UNPUBLISHED → PENDING` 放行。

### 33.2 为什么学生只能干瞪眼（两处界面/话术的洞）

* **按钮判据只看"有没有新产出"**，不看作品状态 —— 学生看到一个亮着的按钮，点下去只有一句
  「当前作品状态不允许重新提交」，既没说为什么，也没说下一步找谁做什么（生产上他连着点了 6 次）。
* 那句 message 对所有"转不过去"的状态一视同仁 —— 而这里的下一步是明确的：**先下架**。

### 33.3 修法（不动业务规则，只把"为什么"和"下一步"说清）

* `packages/shared/src/canvasWorkspace.jsx`：提交按钮的禁用条件加上 **`workStatus === 'PUBLISHED'`**
  （判据来自项目载荷里一直带着的 `workStatus`，不需要新接口），并给出 `WORK_PUBLISHED_LOCK_MESSAGE`
  ——「这份作品已经发布到作品广场，不能再重新提交了。想接着补充内容：请老师或平台先在作品管理里把它
  「下架」，下架后这里就能继续提交。」⚠️ 这句判断要排在"有没有新产出"**前面**（否则有产出但已发布时
  会先说"先做完再说"，把人绕进去）。
* `apps/server/src/routes/student.js`：那条 409 的 message **按状态分档**，PUBLISHED 这一档带上"下架"
  的指引 —— 页面可能是发布前打开的（载荷里的 workStatus 还没刷新），这时它是学生唯一能看到的东西。
* `p139`（画布增量提交守卫）加 **⓪′ 源码口径**与 **④′ 真接口**：
  已发布 → 409 `INVALID_WORK_TRANSITION` 且 message 里要有「已发布」「下架」、被拒时**不留半条脏数据**、
  **下架之后同一份产出就能继续提交**（把"给学生指的那条路"也钉住，不只钉住挡人那半句）。
  验收：p139 SQLite ✓ / MySQL ✓；SQLite 快速 16/16；发布 release **20260926T081032Z**、自检 38/38、五入口 200。
  线上核对：服务端 `student.js` 有那条分档话术、官网（学生）包 `index-CcRgOvgh.js` 里有新文案。

### 33.4 留给用户决策的一件事（没动，等口径）

### 33.5 用户定的口径（2026-09-26 晚，已实现）：**课堂还在进行中的作品，先不进平台后台**
