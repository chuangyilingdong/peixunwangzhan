## 一、决定性发现：入向 10Mbps 是计费规则，不是机器上限

### 1.1 复测（2026-11-01，本次）

同一杆秤、两次测，确认是**共享上限**而不是"上游 CDN 按 IP 限速"：

```text
阿里云镜像，单个 12MB 文件，单流        → 1,343,419 B/s  (1.34MB/s ≈ 10.7Mbps)
同一文件 8 路并发各跑 30s，聚合 36.76MB → 1,225,000 B/s  (1.22MB/s ≈ 9.8Mbps)
```

8 路并发聚合等于单流 —— 如果是 CDN 按连接限速，8 路应该接近 8 倍。
所以瓶颈在**服务器这一侧的入口**，与上游无关。

### 1.2 为什么正好是 10Mbps

阿里云 ECS 公网带宽有一条固定规则：

| 购买的出方向带宽 | 实际获得的入方向带宽 |
| --- | --- |
| **≤ 10 Mbit/s** | **固定 10 Mbit/s** |
| **> 10 Mbit/s** | **等于出方向带宽** |

- 你买的是**出方向**（收费的那一半）；
- **入方向不收费**，但上限由出方向决定；
- 当前出网带宽按文档记录是 5Mbps → 入方向被固定成 10Mbps。

实测 9.8–10.7Mbps，与规则完全吻合。

### 1.3 这条发现推翻了什么

原方案的容量账：

```text
20GB ÷ 1.3MB/s ≈ 4.3 小时   ← 前提是"入向只能 1.3MB/s"
```

按规则重算（只改计费档位，不动代码、不换机器、不买第二台）：

| 出方向带宽档位 | 入方向获得 | 20GB 归档耗时 |
| --- | --- | --- |
| 现在（≤10Mbps） | 10Mbps | ≈ 4.3 小时 |
| 50Mbps | 50Mbps | ≈ 53 分钟 |
| 100Mbps | 100Mbps | ≈ 27 分钟 |
| 200Mbps（按固定带宽上限） | 200Mbps | ≈ 13 分钟 |

**也就是说「4.3 小时」到「13 分钟」之间，差的是一行计费设置，不是一次架构改造。**

### 1.4 成本方向：很可能更便宜

- 入方向流量**不收费**：那 20GB 拉回来本身是 0 元；
- 服务器出方向流量很小：视频/图片取件早就 302 给 OSS，不占服务器出口；
- 所以把计费方式从「按固定带宽」切到「**按使用流量**」、把峰值拉到 100Mbps，
  付出的只是"实际出向用了多少 GB"，而不是"提前买 100Mbps"。

按广州区常见单价量级估算：出向 50GB/月 ≈ 几十元，比现在 5Mbps 固定带宽（百元级）更低或相当，
而**入向从 10Mbps 变成 100Mbps**。

> ⚠️ 我读不到当前实际购买的带宽值（机器上没装 aliyun CLI，DescribeInstanceAttribute 拿不到），
> 只有实测的 10Mbps 上限这一条硬证据。**改之前请在控制台确认当前计费方式与出网带宽**，
> 并核对切换是否会影响已有 EIP / 包年包月打折。

### 1.5 需要你做的（我做不了）

阿里云控制台 → ECS/EIP → 带宽计费方式 → 切换为「按使用流量」→ 峰值带宽拉到 100Mbps。
切换后建议立刻复测：

```bash
ssh ai-kids-prod
# 期望从 ~1.3MB/s 变成 ~12MB/s
curl -s -o /dev/null -w "%{speed_download} B/s\n" \
  https://mirrors.aliyun.com/debian/dists/bookworm/main/binary-amd64/Packages.gz
```

## 二、带宽修好后，剩下的才是代码问题

带宽解决的是"20GB 能多快进来"。下面这几条不解决，**带宽再大也会自己把自己堵死**。

### 2.1 归档整段读进内存（一定会 OOM，不是"可能"）

`apps/server/src/services/generatedAssetArchive.js:74`：

```js
buffer = Buffer.from(await response.arrayBuffer());
```

一条 H3 = 20-22MB。**1000 条并行 = 20GB 内存**，机器 7.4GB。

好消息：**流式上传的轮子已经有了**，不用新写。
`apps/server/src/services/objectStorage.js:235` 的 `putObjectFromFile()` 就是
`createReadStream` + `duplex:'half'` + 显式 `Content-Length`，注释里写明 2026-09-25 在真桶上验过。

所以缺的只有中间那一段：**把响应体流式落到临时文件**，而不是读成 Buffer。

#### 具体改法

```text
fetch(url)
  → response.body (ReadableStream)
  → 边写临时文件边做三件事：
      ① 首块嗅探 MIME（现有 sniffMime 只需要前 4KB）
      ② 累计字节数，超过 64MB 立刻 abort
      ③ 增量 sha256（createHash 的 update 支持分段喂）
  → putObjectFromFile()  ← 已存在，直接复用
  → 删临时文件
```

#### 一个必须绕开的坑

`storeGeneratedAsset()`（`apps/server/src/routes/fileAssets.js:468`）会调
`persistSecureUpload()`，而后者**签名就要求 Buffer**：

```js
export async function persistSecureUpload({ fileName, mimeType, buffer, scan = null })
  // ...
  if (!Buffer.isBuffer(buffer)) throw ...
  const scanResult = scan || await scanWithConfiguredScanner(buffer);
  checksum: createHash('sha256').update(buffer).digest('hex')
```

生成产物不该走"用户上传"这条（不需要 clamscan，也不需要 `FILE_UPLOAD_MAX_BYTES`）。
建议新增 `storeGeneratedAssetFromFile()`：参数收 `{ tempPath, size, mimeType, checksum, ... }`，
落库逻辑照抄 `storeGeneratedAsset` 的 INSERT，只是存储那一步换成 `putObjectFromFile`。

#### 磁盘账（不紧张）

临时文件按**并发归档数**算，不是按任务总数：
8 路 × 64MB 上限 = 512MB；16 路 = 1GB。当前空闲 14GB，够。
**关键是别把临时文件目录放在系统盘且忘了失败清理** —— 需要一个"启动时清理
`/var/tmp/generated-archive/*` 里超过 1 小时的文件"的兜底。

### 2.2 归档堵在任务完成路径上（架构问题，不只是性能）

现在的顺序（`aiGeneration.js:1184-1188`）：

```js
const archivedAssets = await archiveGeneratedAssets(assetPayloads, {...});  // 同步下载 20MB
await settleSuccessfulJob({ ..., assetPayloads: archivedAssets, ... });     // 然后才结算
```

意思就是：**任务"完成"的定义里包含了"20MB 已经存进 OSS"**。
单条看起来只是多等 15 秒，但 1000 条并行时，这 20GB 全部挤在"任务还没完成"这个状态里。

#### 建议：拆成两个状态

```text
SUCCEEDED           上游出片了，库里先记 upstream URL + archive_state='PENDING'
  ↓ 独立的归档队列（低优先级、限并发）
ARCHIVED            字节进 OSS，asset_url 改写成稳定地址
```

好处：
- 生成完成立刻可结算、可通知学生，**课堂不再等 20GB**；
- 归档可以摊到课后几小时，也可以按"学生真打开过"优先；
- 归档队列的并发 = 带宽 ÷ 单文件大小，是唯一需要精确限流的地方。

风险（原文档已验证过，必须兜住）：**上游 URL 会过期**（历史上 21 条里 7 条已 403）。
所以 `archive_state='PENDING'` 必须带 `archive_deadline`：
超过 30 分钟未被归档的，**强制提到队首**，不管有没有人看。

### 2.3 队列没有模态隔离（图片被拖 43-61 分钟的直接原因）

`drainAsyncGenerationQueue()`（`aiGeneration.js:1195`）是一个全局计数器：

```js
while (asyncGenerationActive < ASYNC_GENERATION_CONCURRENCY && asyncGenerationQueue.length)
```

`ASYNC_GENERATION_CONCURRENCY` 默认 8，**不分模态**。8 条视频各占 8-9 分钟，8 个槽全占满，
新来的图片/文本只能等。

#### 改法 A：按模态分桶 + 预留槽位（改动最小）

```text
light 池（TEXT / IMAGE / MUSIC）：永远至少保留 2 个槽
heavy 池（VIDEO）：上限 = 总并发 - 2
空闲槽位：谁先来谁用，但 light 排队优先
```

8 路时 = 视频最多 6 路，图片/文本永远有 2 路可走。
图片 50 秒就能出，不会再有 43 分钟的等待。

#### 改法 B（更对，但要多写一点）：按"资源类型"限流，而不是按"任务数"限流

这一点值得单独说，因为原方案也掉进去了：

> **H3 生成一条占 9 分钟，但那 9 分钟里它几乎不占 CPU、不占内存 —— 它在等上游。**

所以"8 路并发"限制的其实是**内存里的等待者数量**，而这个成本极低（每路几 MB）。
真正稀缺的资源只有两个：**归档带宽**和**API/DB 连接**。

结论：**视频的并发上限不该是 8，也不该是 1000，而是由"同时归档的字节数"反推出来**。
带宽到 100Mbps 后，单条 20MB 约 1.6 秒传完，同时归档 16 路也不会打满；
那么视频并发可以直接开到 100+，让 1000 个任务在 10 分钟内全部提交到上游。

### 2.4 上传闸：`FILE_UPLOAD_MAX_CONCURRENT=3` 被两个作用域共用了

`apps/server/src/services/uploadLimits.js:31`：

```js
if ((active.get(userKey) || 0) >= cfg.maxConcurrent
 || (active.get(orgKey)  || 0) >= cfg.maxConcurrent)
```

**同一个 `maxConcurrent` 同时卡"个人"和"机构"**。所以一个机构里，同时上传最多 3 个。
1000 个同机构学生同时交作品 → 997 个直接拿 `UPLOAD_CONCURRENCY_LIMIT`。

代码注释自己写了这个闸的用途是"**别让一个客户端同时占一堆上传连接**" ——
那是**个人**维度的事。机构维度用同一个 3 是误伤。

#### 改法：拆成两个可配值

```env
FILE_UPLOAD_MAX_CONCURRENT=3          # 个人，保持
FILE_UPLOAD_ORG_MAX_CONCURRENT=100    # 机构，新增
```

#### 但更该先修的是这个：每次上传跑两次全表聚合

同一个文件 `currentBytes()`：

```js
SELECT COALESCE(SUM(file_size),0) FROM file_assets WHERE owner_org_id=? AND storage_kind='INTERNAL_PROXY' AND status!='REMOVED'
```

**每次上传都要跑两条**（个人一条、机构一条）。1000 人同时上传 = 2000 次 `file_assets` 聚合。
这张表会随时间一直长（已有 2GB/20GB 配额口径），这个查询会越来越慢。

换句话说：**就算把 3 改成 100，DB 也会先被打挂。**
建议：机构维度改成"缓存值 + 增量维护"（上传成功 +N，删除 -N，启动/每小时校准一次），
或者至少只在上传**成功后**校验一次，而不是每次 reserve 都算。

### 2.5 `generation_jobs` 缺关键索引

`packages/database/src/schema.js` 只建了：

```sql
idx_generation_jobs_project_created (project_id, created_at DESC)
idx_generation_jobs_org_created     (org_id, created_at DESC)
```

而队列要跑的是：

```sql
SELECT id FROM generation_jobs WHERE status='QUEUED' AND next_attempt_at <= ? ORDER BY created_at
```

**没有 `(status, created_at)` 索引** → 全表扫。
现在只有几万行不明显，1000 路并发 + 每分钟多次扫描时会成为热点。

#### 改法

```sql
CREATE INDEX idx_generation_jobs_status_created ON generation_jobs(status, created_at);
-- 如果要做 SKIP LOCKED 认领，再加一条
CREATE INDEX idx_generation_jobs_queue ON generation_jobs(status, next_attempt_at, created_at);
```

⚠️ 生产 RDS 侧要手工 ALTER（仓库惯例见 schema.js 顶部注释）。

### 2.6 多进程下 `interruptOrphanedJobs` 会互相残杀

`aiGeneration.js:536`：启动时把所有 `RUNNING` 且 `worker_id != 本进程` 的任务判失败。

单进程没问题。**一旦改多进程（这条路必须要走），进程 B 启动会把进程 A 正在跑的 1000 条全部杀掉。**

原文档提到了这点，但低估了顺序：**必须先做租约（lease），再上多进程**，
否则第一次滚动发布就是一次 1000 条集体失败。

正确顺序：

```text
① 加 lease_expires_at + 心跳续租
② 回收逻辑改成"只收过期租约"，不再按 worker_id 判
③ 然后才允许跑第二个 worker 进程
```

## 三、修正后的瓶颈排序（按"必须先做"）

| 顺序 | 事项 | 谁做 | 成本 | 不做的后果 |
| --- | --- | --- | --- | --- |
| 1 | **改 EIP 计费/带宽档位到 100Mbps** | 你（控制台） | 大概率更便宜 | 20GB 永远要 4.3h |
| 2 | 归档流式化 + 临时文件 | 代码 | 小 | 1000 路必 OOM |
| 3 | 上传闸拆个人/机构 + 去掉全表聚合 | 代码 | 小 | 千人大班上传全 429 / DB 热点 |
| 4 | 队列按模态隔离（预留 2 槽） | 代码 | 小 | 图片又被拖 40 分钟 |
| 5 | `generation_jobs(status, created_at)` 索引 | 你/运维 | 极小 | 队列扫描变热点 |
| 6 | 归档与"任务完成"解耦 | 代码 | 中 | 课堂等 20GB |
| 7 | DB 队列 + lease + SKIP LOCKED + 多进程 | 代码 | 大 | 上不了 1000 路 |

**1、2、3、4、5 做完，就已经能支撑"一个班 100-200 人同时生成"** ——
这大概率是近期真实的需求量级，而 6、7 才是冲 1000。

## 五、上游产物 URL 有效期：已实测（2026-11-01）

### 5.1 方法

生产库 `file_assets.metadata.upstreamUrl` 里存着归档时的**原始上游地址**（328 条，最早 2026-09-05）。
把这些地址按生成时间排序逐个 `HEAD` 探活，看"多大年龄的地址还活着"。

脚本已落地：[scripts/probe-upstream-artifact-ttl.sh](../scripts/probe-upstream-artifact-ttl.sh)。

### 5.2 结果

| 上游域名 | 样本 | 可用 | 真实失效(403/404) | 样本年龄 |
| --- | --- | --- | --- | --- |
| `media.seedance.nz`（**H3 当前上游**） | 51 | 51 | **0** | 7–81 小时 |
| `rh-hk-images.xiaoyaoyou.com` | 9 | 9 | 0 | 50–53 小时 |
| 腾讯 COS（港澳 / 北京） | 65 | 30 | 35 | 202–962 小时 |
| `getapib.org`（早期图片） | 187 | 34 | 153 | 202–962 小时 |

**结论：H3 当前上游 `media.seedance.nz` 在 81 小时内 0 失效。**
**下界 81 小时（3.4 天）是硬证据；上界还没测到**，因为没有比 81 小时更老的 seedance 样本。

### 5.3 两个必须纠正的误判

**① 「7 天拐点」是假象。**
一开始按年龄分桶得到"1-3 天 98% 存活、7-10 天 53%、10 天以上 0%"，
看起来像 TTL = 7 天。但按域名拆开才发现：**10 天以上的样本全部来自旧 provider**
（getapib.org / 腾讯 COS），seedance 最早的样本才 81 小时。
真实原因是 **provider 换过一代**，不是"时间到了就失效"。
把两个 provider 混在一个年龄桶里统计，结论会完全错。

**② `000` 不是失效。**
第一次跑 328 条时有 2 条返回 `000`（curl 连不上），一度被算进"死亡"。
重跑后这两条都 200 —— 是网络瞬断。
脚本里对 `000` 重试 3 次、仍失败才记 `UNREACHABLE`，且**不计入存活率分母**。

### 5.4 对方案的影响

原文档留的这个悬念直接决定 2.2 能不能做，现在有答案了：

| 假设 TTL | 20GB 归档必须多快收完 | 需要的入向带宽 |
| --- | --- | --- |
| 1 小时 | 一节课内 | ≈45Mbps |
| 24 小时 | 当天内 | ≈1.9Mbps |
| **≥81 小时（实测下界）** | **可以摊到 3 天** | **≈0.8Mbps** |

**也就是说：按目前证据，20GB 完全不需要在课堂上收。**
2.2 的「生成完成」与「已归档」解耦不只是可行，而且**带宽升级的紧迫性大幅下降** ——
100Mbps 仍然值得改（它对单条 H3 的归档延迟、以及突发批量有直接好处），
但**它不再是"能不能上课"的前置条件**。

于是 `archive_deadline` 的取值建议从原设想的 30 分钟放宽到：

```text
普通任务：事务提交时顺手入归档队列，低优先级
强制提升：年龄 > 24 小时仍未归档 → 提到队首（留 3 倍安全余量对 81 小时下界）
```

### 5.5 还差什么

81 小时只是**下界**，不是 TTL。要拿到准确值只有一个办法：**记录"首次失效时刻"**。

```bash
# 生产机上，每天 04:17 跑一次，持续 2 周以上
17 4 * * * bash /srv/ai-kids-platform/source/scripts/probe-upstream-artifact-ttl.sh \
  --days 30 --csv /var/log/ai-kids-platform/upstream-ttl.csv \
  >> /var/log/ai-kids-platform/upstream-ttl.log 2>&1
```

累积后对每个地址取「第一次非 200 的探测时刻 − 生成时刻」，P50/P95 就是真实 TTL 分布。

⚠️ 挂 cron 属于生产变更，**没有擅自装**。要装的话说一声，或者你手动加。
在装之前，手动跑一次 `--days 30` 就能复核本文档的结论。

## 六、实施步骤（按依赖排序，2026-11-01 梳理）

### 6.0 目标形态

```text
学生提交
  ▼
generation_jobs（QUEUED）
  ▼  多 worker 认领（上限由"归档带宽"反推，不再写死 8）
上游生成（8-9 分钟，纯 I/O 等待，不占 CPU）
  ▼
结算 → 立刻建 file_assets 占位行（storage_key 为空，metadata.archive=PENDING）
       ↓ 对外地址此刻就固定了，以后不变
学生画布拿到 /api/student/file-assets/<id>/download
  ▼
独立归档队列（限并发，低优先级）
  ├─ 流式落临时文件 → putObjectFromFile（内网，不占公网出口）
  └─ 回填 storage_key → 同一个地址从此 302 到 OSS
```

**核心设计：对外地址在"结算那一刻"就固定，字节后到。**
依据是 `fileAssets.js:241 prepareFileDownload()` 已经支持 `__fileResponse + status:302 + redirectUrl`，
所以"PENDING 时 302 到上游、归档后 302 到 OSS"是加一个分支，不是改协议。
这样前端、画布快照、已分享的作品全都不用动。

### 阶段 A：止血（小改，独立，当天可上）

| # | 做什么 | 改哪里 | 验收 |
| --- | --- | --- | --- |
| A1 | 轻模态（TEXT/IMAGE/MUSIC）永久预留 2 个槽，视频上限 = 总并发 − 2 | `aiGeneration.js:1195 drainAsyncGenerationQueue()` | 图片排队从 40min+ 降到 <2min |
| A2 | 上传闸拆成个人 / 机构两个值 | `uploadLimits.js:28 reserveUpload()` | 同机构 10 人并发上传不再 429 |
| A3 | 去掉每次上传的两条全表 `SUM(file_size)` | `uploadLimits.js:27 currentBytes()` | 并发上传时 DB 无聚合热点 |

> A2/A3 必须一起做。只改 A2 会把压力从"闸"转移到 DB —— `file_assets` 只会越来越大。

### 阶段 B：归档不占内存、不堵完成路径（主菜）

| # | 做什么 | 关键点 |
| --- | --- | --- |
| B1 | 流式归档：`response.body` → 临时文件 → `putObjectFromFile` | 新函数 `storeGeneratedAssetFromFile`，绕开 `persistSecureUpload`（它强制要 Buffer + clamscan）。**sha256 增量算，MIME 只看首块**。临时目录必须有启动清理 |
| B2 | 结算时建占位行，`storage_key` 留空 + `archive.state=PENDING` | 下载路由加分支：有 storage_key → 走现有 OSS 302；没有但有 PENDING 上游地址 → 302 到上游，**并把这个任务提到归档队首** |
| B3 | 独立归档队列（限并发）+ `archive_deadline` 24h 强制提升 | 依据第五节实测：seedance ≥81h 0 失效，24h 是 3 倍安全余量 |

**验收**：1000 条 20MB 假产物压测 —— RSS 峰值 <1.5GB、磁盘临时文件不超 1GB、全部终态、
**任务完成时间不再包含归档耗时**（这是最关键的一条指标）。

### 阶段 C：放大并发

| # | 做什么 | 说明 |
| --- | --- | --- |
| C1 | 加索引 `(status, next_attempt_at, created_at)` | 生产 RDS 手工 ALTER（仓库惯例） |
| C2 | 上游提交令牌桶 + 轮询抖动 | 1000 条 × 5s 轮询 = 200 RPS，多数上游会拒 |
| C3 | 把 `AI_GENERATION_CONCURRENCY` 从 8 调大 | 真正的闸移到归档队列；生成侧是 I/O 等待，可以开很大 |

**验收**：200 条任务压测，无重复提交、P95 完成时间、上游 429 率。
