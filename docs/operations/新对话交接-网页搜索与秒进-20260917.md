## 二、本轮做完的：网页搜索走网关（Anthropic 协议透传）

**症状**：学生用搜索，报 `DeepSeek search has no API key for "DEEPSEEK_API_KEY"`。

**原设想是错的，这点先记住**：那个插件调的**不是搜索接口**，而是 **Anthropic 协议的
`/messages`**（插件源码 `const endpoint = \`${options.baseURL}/messages\``，搜索是模型一跳里的
服务端工具 `web_search_20250305`）。所以做的不是「加一个搜索端点」，而是**一条 Anthropic 透传**。
插件自己的注释也写明：它复用 `DEEPSEEK_API_KEY`，但**不复用** chat 的 base。

**做法**（`apps/server/src/routes/runtimeSearchGateway.js`：

```text
学生环境  --x-api-key / authorization: Bearer <运行时密钥>-->  /api/gateway/v1/search/messages
                                                              ↓ 验签 + 过门禁（与聊天同一个实现）
                                                              ↓ 换成渠道真密钥
                                                              →  <上游>/anthropic/v1/messages
                                                              ↓ 原样回吐 + 落账
```

- **身份/门禁/记账与聊天那条路共用同一套实现**（`verifyRuntimeKey` / `assertRuntimeClassroomActive`
  / `recordAiUsage` 都是复用，不是各写一份 —— 那种迟早走偏）。
- **协议不翻译**（Anthropic 进、Anthropic 出），只动两处必须由我们决定的：
  `model`（换成我们渠道解析出来的名字，绝不原样发上游）与 `tools`（只留 `web_search*` 类服务端
  工具，`max_uses` 夹到 10 —— 否则这个端点就是一台「能点上游任何服务端能力」的机器）。
- **端点按渠道实际形态推导**（`searchUpstreamEndpoint`）：算力网关 → 网关的 `/v1/messages`；
  渠道 `protocol=ANTHROPIC` → 用它自己的 endpoint；其余 → **同源主机**的 `/anthropic/v1/messages`。
- **宿主脚本**注入 `DEEPSEEK_SEARCH_BASE_URL=<网关>/search`、`DEEPSEEK_API_KEY=<运行时密钥>`。
- ⚠️ **复用判定也认 `DEEPSEEK_SEARCH_BASE_URL`**（`environment_key_usable` 里）：它在这次改动之前
  起的环境里根本不存在，不看这一条就会复用出一个「AI 能用、一搜索就报 no API key」的半坏环境，
  而且学生没有任何提示。代价是一次性冷启动十几秒。

**已实测的关键事实**（不用再猜）：

- DeepSeek 的 Anthropic 入口认**我们渠道现有的那把密钥**（`channel-mtp9razp`），不需要新申请；
  实测返回真实 `web_search_tool_result`（10 条结果）。
- **模型名**：插件默认发 `deepseek-v4-flash`，我们渠道的模型叫 `deepseek-flash` —— 两个上游都认。
  但网关仍按老规矩把「调用方报的名字」解析成渠道自己的模型（`deepseek-v4-flash → deepseek-flash`），
  留档在 `usage_records.pricing_snapshot.modelResolution` 里。**规矩不能因为「这次恰好认」就破**。
- 一次搜索的账（实测）：input 2782 / output 459 tokens，按合同单价折算 0.9236 分，
  `compute_attempts.cost_source=COMPUTED`、`webSearch.requests=1`。

**怎么验的**（这是唯一能证明它活着的方法，别只看守卫绿）：

```bash
# ① 端点在不带密钥时是 Anthropic 形状的 401（不是 404、不是平台信封）
curl -s -X POST -H "content-type: application/json" -d '{}' \
  https://iicili.cyou/api/gateway/v1/search/messages
# ② /tmp/verify-search.mjs：签真密钥 + 照插件源码发请求 → 200 + 10 条真实结果
# ③ /tmp/probe-student-search.mjs：以**学生用户**身份、用 dsh 进程里的那两个变量发一次
#    （runuser 要带 timeout，我第一版没带，挂了 400 秒才被 timeout 杀掉）
```

## 三、同一轮的第二个 bug（**用户现场报的**）：网关请求体 2MB 的墙

**症状**：学生让 agent 做个游戏，agent 连着读了自己 8-12 张截图（UI 上是一串「读取图片 · /tmp/xxx.png」），
然后整轮失败：`400 {"code":"PAYLOAD_TOO_LARGE","message":"请求体过大"}`，**活干到一半停住**。

**根因**：分发层对所有非 multipart 的 POST 一律 `readJson(req, '2mb')` —— **`/api/gateway/` 也不例外**。
可 dsh 每轮把整段对话重发一次，而 agent 干活时图片会不断进历史。两个关键数：

```text
真实截图：185-288KB 一张（base64 后约 350KB）  →  12 张 ≈ 3.7MB  →  越过 2MB
token 账本：那一轮只有 25k tokens             →  图片按**字节**很大、按 **token** 很小
nginx 给的上限：client_max_body_size 30m       →  连 413 都轮不到 nginx 报，是我们在应用层掐的
```

**改法两处**：

1. `/api/gateway/` 的 JSON 上限单独放宽到 **24MB**（`RUNTIME_GATEWAY_BODY_LIMIT` 可调），
   普通接口仍守 2MB —— 不是把全局放开。24MB 相对实测体量（12 张 ≈3.7MB）留了约 65 张的余量。
   ⚠️ 它必须**小于** nginx 的 `client_max_body_size`（30m）：大了就轮不到我们说话，
   小也轮不到我们报错（nginx 直接 413，学生看到一句没头没尾的错）。
2. 历史图片按**字节**封顶（12M 字符，约 34 张截图）。这是**安全阀，不是常态**：常规会话碰不到。
   超了就从最新往回留，更早的换成一句话并**告诉模型图在工作区里、需要时重读**
   （这些图本来就是 agent 自己从工作区读的，所以省略不丢信息，只是多一次读文件）；
   消息本身与 `tool_call_id` 都不动 —— 工具配对不能因为省略图片而散掉。

**另外补了证据**：这类失败以前在日志里**一声不响**（4xx 不打印），修完顺手让
「请求体过大」留下路径、实际用的上限与 nginx 收到的 content-length。

**怎么验的**：`/tmp/verify-bigbody.mjs` —— 拿学生环境里**真实的 12 张截图**拼成历史（3.26MB，
正是之前撞墙的体量）发到生产网关 → **HTTP 200**，而且模型真看懂了（答出「6 张是游戏画面、
6 张是菜单/暂停/通关/死亡结算」，连文件名都对上了）。账本记 8061/365 tokens。

**⚠️ 下一轮要注意的一件事**：这堵墙只是被推远了，没有消失。dsh 每轮重发全量历史，
图片会一直攒。真到 24MB 那天，日志里会有 `[API] 请求体过大被拒`（带路径与 content-length），
那时有两条路：再放宽（同时抬 nginx）或**在客户端侧就不让它攒**（dsh 是第三方的，只能靠配置/形态）。

## 四、⚠️「秒进」：我量了一下，卡住的不是代码，是**内存**

上一份交接说要「先问清用户要的形态」。先看数（2026-09-17 实测）：

```text
机器：总内存 1607MB，available 844MB，CPU 2 核；swap 2047MB 里已用 421MB
平台自己：约 320MB
一个学生环境（dsh 进程）：RSS 445MB（文档记的稳态 470-490MB）
冷启动：约 17 秒（dsh 进程自身启动时间，代码改不了）
```

**推论（这条是硬的）**：这台机器**同时只装得下 1–2 个**学生环境。
所以「点下去那一刻环境已经在跑」的秒进，**在这台机器上对任何真实班级都不可能** ——
我上一版的预热方案被否掉，很可能就是撞在这一条上：预热 3 个就已经把内存吃满了
（`REQUIRED_MB=600` 的容量闸门会直接拒绝开第 3 个盒子），学生体验到的仍是「排队 / 开不出来」。
**不是预热思路错，是这台机器装不下。**

所以下一轮要先问用户的是**形态**，二选一（都要花钱或花工期，没有第三条便宜路）：

| | 做法 | 成本 | 能做到什么程度 |
|---|---|---|---|
| A | **加内存**（6 人班约需 4GB，30 人班约需 16GB：学生数 × 445MB + 平台 320MB + 冷启动峰值余量），开课时预热全班 | 机器钱 | 真正的秒进：「点下去就在跑」 |
| B | **不换机器**：把「环境」拆成轻运行时（先给一个不吃 445MB 的东西，按需再升级到大能力） | 工期，改动大 | 秒进 + 省内存，但要重做运行时形态 |

用户此前的两条约束仍然是重做的输入：
① 「肯定是根据他输入的提示词发送之后，才决定要不要调用更大的能力」（按需）—— 这条更贴 B；
② 「不配 DNS」—— 端口池已放到 400（18201-18600），不需要 DNS，只是安全组要放行这一段（用户侧操作）。
③ 用户明确**不要**「替 dsh 决定用什么能力」的干涉；能力决策全归 dsh。

## 五、本轮踩的坑（5 条，都值得记）

1. **守卫里 `AI_PROVIDER_SECRET_FILE` 必须早于「任何平台源码」被加载**：`providerSecret.js` 的文件
   路径是**模块加载时**读的（`const file = process.env...`），而 ESM 的静态 `import` 会被提升到所有
   语句之前 —— 于是静态引 `runtimeGateway.js`（它现在也引 providerSecret）会先把这个模块用**默认路径**
   打开并缓存住，症状是「密钥读不出来、路由报渠道没配密钥」。修法：平台源码一律用**动态 import**，
   并在其之前把 env 设好。（p97 能静态引是因为它用到的 `secret()` 是**调用时**读 env 的。）
2. **我又漏提交了**：改了 `deploy/` 下两个宿主脚本，但 `git add` 只写了三个 server 文件，于是
   「已推送」之后服务器上 pull 下来的还是旧脚本（症状：`grep DEEPSEEK_SEARCH_BASE_URL` 数为 0，
   而我差点以为 pull 没生效）。**提交后 `git show --stat --oneline HEAD` 看一眼文件清单**。
3. **`runuser` 包一层没有 timeout 就会挂住**：以学生用户跑探针时，第一版包装脚本没加超时，
   挂了 400 秒被外层 `timeout` 杀掉，害我误以为「环境没起来」。跑跨用户探针一律加 `timeout`。
4. **冷启动会换端口**：复用不成立时脚本重新在端口池里挑（旧 conf 还在 → 18201 被算占用 → 拿 18202），
   然后覆盖同一个 `dshs-*.conf`。所以「端口变了」是正常现象，不是配置写坏。
5. **新端点会静默继承分发层那个 2MB 的请求体上限**：`index.js` 里 `readJson(req, '2mb')` 是**全局默认**，
   加新端点时没有任何东西会提醒你。判断方法很土但有效：想一下「这个端点最坏会收到多大」——
   凡是**会带图**、或者**客户端每轮重发全量历史**的（dsh 就是），必然超。
   现在按路径分流（`jsonBodyLimitFor`），以后加这类端点记得用上。

## 六、还欠着的（按优先级）

1. **「秒进」形态**（第四节）—— 要先问用户，别擅自开工。
2. **多机放置**：平台仍只认一个宿主（一个 broker socket），加机器用不上第 2 台。
   设计在 `docs/architecture/多学生并发-扩容设计.md`。⚠️ 上一条（加内存）与本条是同一件事的两面：
   换规格更大的单机也是「扩容」，只是省掉多机调度。
3. **文件安全扫描口径**（老问题，未定）：生产 clamscan 每次加载 108MB 库、峰值 618MB，
   机器 1607MB —— 会把上传拖进 swap。建议「把扫描从提交挪到发布」。
4. **`/candidates` 的 N+1**（课堂「添加学员」）：一次返回本机构全部学员、每人 3-4 条 SQL、无分页无 search。
5. 学生看不到自己未发布的作品；dsh 的工作区预选没做；生产库里有 3 条验收记录（标题带「可删」）。
6. **搜索这块的两个小尾巴**（都不影响现在能用）：① 学生若在 dsh 设置里改掉 `web-search-deepseek`
   的 Endpoint，搜索会绕过我们的网关（那是 dsh 自己的设置面，属于「学生可改的面」这一类问题，
   要单独定口径）；② 流式搜索被显式拒绝（`RUNTIME_SEARCH_STREAM_UNSUPPORTED`）——
   插件是 `accept: application/json` 非流式，所以现在不需要；将来要支持得把回吐改成真流式 + 边流边记账。

## 七、口径对照（**别把这些当 bug 改回去**）

| 现象 | 为什么 |
|---|---|
| 搜索**不翻译协议**，但会换 `model`、会摘掉非 web_search 的工具 | 「不翻译」指的是不做 Anthropic↔OpenAI 转换；模型名与工具白名单是**必须由我们决定**的两处 |
| `/api/gateway/` 的请求体上限（24MB）比普通接口（2MB）大得多 | 网关那条会带图、且 dsh 每轮重发全量历史；2MB 是分发层的全局默认值，不是为它定的 |
| agent 读了很多截图后，历史里更早的图变成了一句「已省略，需要时重读文件」 | 图片字节预算的安全阀（12M 字符）。图是 agent 自己从工作区读的，重读即可；消息与 `tool_call_id` 都没动 |
| 搜索的响应是一次性读完再回吐（不是流式转发） | 用量必须从响应体里读出来才能落账；插件本来就是非流式的 |
| `DEEPSEEK_API_KEY` 这个名字出现在学生环境里 | 它是**运行时密钥**（短时、绑课堂），不是渠道真密钥；插件源码把这个变量名写死了 |
| 复用判定多了一条「搜索网关变量对不对」 | 判据是「进程活着 ≠ 它手里那套是齐的」，与密钥那条同源 |
| 冷启动后端口从 18201 变成 18202 | 旧 conf 还在，端口池扫描把它算作占用；conf 文件名由「课堂+学生」推导，所以是覆盖不是新增 |
| 静默/报错都不出现的「卡住」 | 本项目最主要的 bug 类型：**不报错、只表现为卡住**。修的时候顺手补「失败要说清楚」 |
| 登录名只允许英文数字、同机构同角色不能重名、授权跟合同日期走 | 第五轮用户口径（详见 `产品口径调整-20260916.md`） |
