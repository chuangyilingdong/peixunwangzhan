# 给客户端：关于「运行时密钥已过期」（2026-10-14）

> 你们给的四条建议我们逐条对过了。**结论：平台侧已经改掉 3 条（1 / 3 / 4），第 2 条（NTP）当场实测是好的。**
> 另外我们把"客户端到底有没有被我们拒"这件事**从日志里查清了**，见下面第一节——这条对我们两边都有用。

## 一、我们先查了"到底是谁拒的"（现场证据）

用生产 nginx 访问日志 + 平台日志对了一遍（14/Oct）：

| 时刻（+0800） | 请求 | 结果 |
| --- | --- | --- |
| 06:26:22 ~ 06:29:18 | `GET /api/student/runtime/client-context`（同一条 IP，每 ~5 秒一次） | **全部 200**（每次都拿到新 key） |
| **06:34:27** | `POST /api/gateway/v1/chat/completions`（UA `ZCode/0.2.7`） | **401**（响应体 104 字节 = `RUNTIME_KEY_EXPIRED`） |
| **06:37:51** | 同上 | **401**（同上） |

两点结论：

1. **是平台拒的**（不是客户端本地判的）——响应码/体积与 `RUNTIME_KEY_EXPIRED` 的报文一致；
2. 但**不是"平台给的 key 是旧的"**：那几分钟里你们 UI 侧的轮询全是 200、拿到的都是**现签的新 key**。
   被拒的是**发到网关的那一把**——也就是说，调用侧（Agent 进程）手里那把 key 不是刚从 `client-context`
   拿到的那把，而是更早的一次（TTL 到期了）。这与你们第 3 条（"极端长课堂"）描述的形态一致。

> 顺手补一条对两边都有用的：以前网关**不记录**拒签，我们只能翻 nginx 才知道"被拒过、被拒了几次"。
> 现在平台侧会打一行 `[gateway] 运行时密钥被拒：已过期 N 分钟 · 学生 x / 课堂 y`，下次这类问题一眼可查。

## 二、你们四条建议的逐条答复

| # | 你们的建议 | 平台侧现状 / 已做的动作 |
| --- | --- | --- |
| 1 | `client-context` 每次都签发新 key + 保持 `no-store` | ✅ **"每次现签"本来就是这样**（每次请求都调用签发，`exp = now + TTL`）。❌ **`no-store` 原来没有**（实测响应头里一个 `cache-control` 都没有）→ **已改**：平台所有 API 的 JSON 响应默认 `cache-control: no-store`（2026-10-14 上线）|
| 2 | 服务器保持 NTP 时钟同步 | ✅ **实测是好的**：`System clock synchronized: yes`、`NTP service: active`（chrony 在跑）、无时间跳变记录；服务器时间与阿里云站点、与我们本机均在 1–3 秒内 |
| 3 | 6 小时 TTL 放宽到 12/24 小时 | ✅ **已取 12 小时**（原来 6 小时）。取 12 而不是 24：真正的安全边界不在 TTL 上——**每一次调用都会重过课堂门禁**（课堂仍在进行 + 学生在名单里），密钥里没有的东西一律不认 |
| 4 | 轮换 `RUNTIME_GATEWAY_SECRET` 时留过渡窗口 | ✅ **已加**：新环境变量 **`RUNTIME_GATEWAY_SECRET_OLD`** —— 装上"上一把"之后，轮换前签出的 key **仍然认**（只用于验签，签发永远用当前那把）；过渡结束把它删掉重启即可立刻收口 |

## 三、需要客户端配合的一条（我们做不了的那半）

**请让"发往网关的那一条路"也吃到新 key**：`client-context` 每 5 秒都在下发新 key（已确认），
但被拒的那两条说明**调用侧用的是旧 key**。建议二选一（或都做）：

1. 每轮任务开始前（或会话每次启动）重新取一次 `client-context` 并把 `gateway.key` 换成新的；
2. 网关返回 `RUNTIME_KEY_EXPIRED`（或任何 401）时，**自动重取一次 client-context 再重试一次**——
   现在 TTL 是 12 小时，配合这一条，长课堂基本不会再撞上。

## 四、可以拿去复现/自测的口径

- `client-context` 响应头：`cache-control: no-store`（且没有 `etag`/`expires`）；
- `gateway.key` 解出来（`rt1.<base64url payload>.<mac>`）的 `exp − now ≈ 12 小时`；
- 过期 key → `401 {"error":{"code":"RUNTIME_KEY_EXPIRED","message":"运行时密钥已过期"}}`；
- 轮换过渡期内：旧 secret 签的 key → 不再 401；其它任意 secret 签的 → 仍然 `RUNTIME_KEY_INVALID`。
