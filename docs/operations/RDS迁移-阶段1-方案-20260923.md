## 二、为什么**不能**做成"半同步半异步"的渐进过渡

一个很自然的想法是：给数据层加一套 async 孪生（`arow/arows/aq/...`），今天让它们**同步地**包住老的
同步实现（`async function arow(){ return row(); }`），这样就能一个文件一个文件地改，应用全程可用。

**这条路是错的，而且错得很隐蔽**：

```text
SQLite 是**单连接 + BEGIN IMMEDIATE** 的事务。改了之后的代码在事务里 await 一下就会**让出事件循环**，
于是**别的请求会挤进同一个事务里** —— 它们的数据访问会被算进这个事务，
提交/回滚的边界全乱。表现是"偶尔有几条数据莫名其妙地被一起回滚/一起提交"，
而且**没有任何报错**。
```

所以：**数据层的签名变更必须与全部调用点在同一次变更里完成**（一个分支、一个原子提交）。
这也意味着放弃"过渡期双跑"，改用**分支 + 完成后一次性切换 + 快照回滚**。

## 三、关键机制：让"漏写 await"当场炸，而不是静默

漏 await 是最危险的一种错（`node --check` 抓不到、运行时不报错、表现为各种莫名其妙的业务错）。
两道防线：

```text
① **静态**：scripts/p137-async-db-await.mjs
   报告"还有多少处没 await"（进度尺），改造完用 --gate 当门禁。
   已跑：起点 1203 处。

② **运行时**（改造时一起加）：数据层返回的不是裸 Promise，而是一个 **Proxy** ——
   除 then/catch/finally 以外，**访问任何属性都直接抛错**，错误信息就是"你漏了 await（SQL: …）"。
   这样任何漏 await 的地方在**被跑到的那一刻**就会大声报错，
   而不是"拿 Promise 当数据用"（`if (user)` 恒真、`user.id` 是 undefined、`[...rows]` 空数组）。
   ⚠️ 这条是整个改造能不能**验证**的关键：没有它，漏 await 只能靠通读代码发现。
```

## 四、执行顺序（每一步都可验证）

```text
1. 建分支（不动生产）                     ← 现在
2. 数据层加异步 API（aq/arows/arow/acount/aone/atransaction），并装上上面那个 Proxy
3. 逐文件加 await / 把函数变 async（用 p137 当进度尺；每改完一批跑 node --check + import 冒烟）
   · 3 处同步 forEach 改成 for...of
   · ~70 处 transaction(fn) 改成 await atransaction(async () => {...})
4. **跑起来才算数**：在一台 staging（同一台机、另起端口 + 数据库副本）上起应用，
   用真实前端把四条主流程走一遍（教师开课 / 学生进课堂 / 上传素材 / 广场浏览），
   看有没有"漏 await"的抛错 —— 这是唯一能证明 1203 处都对的手段。
5. 切 mysql2（真异步驱动）→ 此时业务代码**一行都不用再改**
6. 灰度：先只切 staging → 桌面客户端与网页都验 → 再切生产
   回滚：release 回退（SQLite 那份数据一直是活的，切回即可）
```

## 五、我要先说清的风险

```text
· 这是**以天/周计**的改造，不是一次动作。1203 处 × (加 await + 改 async + 处理级联) 都要过脑，
  "批量正则替换"在这里**不安全** —— 因为把函数改成 async 之后，**它的调用者**也得 await，
  而调用者不是数据访问调用、静态检查抓不到（这正是第 3 步要逐个过、第 4 步要真跑起来的原因）。
· 现有自动回归网薄（CI 只跑 3 个脚本），所以第 4 步的"真跑一遍"不能省。
· 阶段 0 已经把这件改造的**数据面**风险消掉了（schema 与数据都验证过），
  剩下的风险全在**代码改造**上 —— 而那是可以逐批判定、可以回滚的。
```

## 六、也别忘了：RDS 里现在已经有一份**验证过的数据**

阶段 0 之后，RDS 上已经是一份逐表比对过、与生产一致的副本。即使阶段 1 拖得久，
这件事本身的价值也在：**机器之外有一份可查询、可做报表、可回滚的数据库**。
要不要在阶段 1 期间再加一个"每小时同步一次"的定时任务（保持 RDS 与生产同步），
可以在开始阶段 1 前定。
