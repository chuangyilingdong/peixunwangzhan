## 二、改造可以**增量做**（这一节我先写错了，实测后更正）

> ⚠️ **2026-09-23 晚补记：这一节的"实测"只测了宏任务，结论不完整。**
> `await` 让出的是**微任务队列** —— 进程里另一个异步任务（后台 worker / 定时器）只要此刻有排队的续体，
> 就会在"BEGIN 与 COMMIT 之间"跑 SQL（实测症状：`cannot start a transaction within a transaction`，
> 以及"别人的 INSERT 混进我的事务跟着一起回滚"）。现已由 `schema.js` 里的**全局执行队列**挡住。
> **"可以增量做"这个结论保留，但它现在依赖那把锁，而不是依赖"await 不让出事件循环"。**
> 详见完成文档 §二.①。

我最初判断"必须一次性改完、不能一个文件一个文件地改"，理由是：

```text
SQLite 是单连接 + BEGIN IMMEDIATE。事务里 await 会让出事件循环 →
别的请求会挤进同一个事务 → 提交/回滚边界全乱，而且没有任何报错。
```

**这个判断是错的。** 实测（`await` 一个**已 resolve** 的 Promise 之后，`setImmediate` 里的回调有没有插进来）：

```text
await 已 resolve 的 Promise 之后，别的请求是否插进来过：**否**
```

原因：`await` 一个已 resolve 的 Promise 只把后续排进**微任务队列**，而 Node 会在处理下一个
**宏任务**（另一个请求的 I/O 回调）之前把微任务**排空**。转换期的异步层正是"同步实现的外壳"
（`arow` 底下就是同步的 `row`，没有任何真实 I/O）→ **不会发生交错** ✓

**所以改造可以一个文件一个文件地做，应用全程可用、每批都能独立验证、随时能停。**
（这也把"以天计的连续改造"变成了"可以分批交付"。）

**但有一条真正的交界**：等把实现换成 mysql2（真异步驱动）时，`await` 一次真实网络往返**会**让出
事件循环 → 那时事务必须用**专用连接**。做法：用 `AsyncLocalStorage` 记录"当前事务的连接"，
让模块级的 `aq/arow/...` 自动路由过去 —— **这样那 70 处事务调用点一行都不用改**。
（这一步属于"切换那一刻"，不属于改造本身。）

## 三、关键机制：让"漏写 await"当场炸，而不是静默

> ⚠️ **2026-09-23 晚补记：下面这条只对了一半。** Proxy 抓得到**属性访问**（`user.id`）、
> **JSON 序列化**、**迭代**（`[...rows]`）；**抓不到** `if (leaked)` / `!leaked` / `x && y`
> —— JS 的 ToBoolean 对对象**没有可拦截的钩子**（Proxy 的 `get` 不会触发），恒为真。
> 兜住这一类的是**静态门禁**（"调用 async 函数却没 await 的调用点 = 0"），不是运行时检测器。

漏 await 是最危险的一种错（`node --check` 抓不到、运行时不报错、表现为各种莫名其妙的业务错）。
两道防线：

```text
① **静态**：scripts/p137-async-db-await.mjs
   报告"还有多少处没 await"（进度尺），改造完用 --gate 当门禁。
   已跑：起点 1203 处。

② **运行时**（改造时一起加）：数据层返回的不是裸 Promise，而是一个 **Proxy** ——
   除 then/catch/finally 以外，**访问任何属性都直接抛错**，错误信息就是"你漏了 await（SQL: …）"。
   这样任何漏 await 的地方在**被跑到的那一刻**就会大声报错，
   而不是"拿 Promise 当数据用"（`if (user)` 恒真、`user.id` 是 undefined、`[...rows]` 空数组）。
   ⚠️ 这条是整个改造能不能**验证**的关键：没有它，漏 await 只能靠通读代码发现。
```

## 四、执行顺序（**增量交付**，每一步都可验证）

```text
1. ✅ 数据层加异步 API（aq/arows/arow/aone/acount/atransaction）+ 运行时的"漏 await"检测器
      （已上线，纯新增、dormant：构建 38 通过 / 0 失败、五入口 200）
2. **逐文件改造**（可以一批一批来、每批都能单独验证并随发布上线）：
   · 把该文件里的 row/rows/q/one/count 换成 arow/arows/aq/aone/acount，并加 await
   · 把包裹它们的函数改成 async（顺着调用链往上，直到已经在 async 里的处理函数）
   · 3 处同步 forEach 改成 for...of
   · ~70 处 transaction(fn) → await atransaction(async () => {...})
   · 每改完一批：`node --check` + import 冒烟 + `p137` 看进度（起点 1203，目标是 0）
   ⚠️ 转换期**应用全程可用**（异步层是"同步实现的外壳"、和同步层共用同一个 SQLite 连接，
      不会出现"一半写 A 库、一半读 B 库"）
3. **跑起来才算数**：staging 起应用，用真实前端走四条主流程（教师开课 / 学生进课堂 /
   上传素材 / 广场浏览），看有没有"漏 await"的抛错 —— 这是唯一能证明 1203 处都对的手段
4. 切 mysql2（真异步驱动）+ `AsyncLocalStorage` 记录事务连接 →
   业务代码**一行都不用再改**；回滚 = release 回退（SQLite 那份数据一直是活的）
5. 灰度：先 staging → 客户端与网页都验 → 再切生产
```


## 五、我要先说清的风险

```text
· 这是**以天/周计**的改造，不是一次动作。1203 处 × (加 await + 改 async + 处理级联) 都要过脑，
  "批量正则替换"在这里**不安全** —— 因为把函数改成 async 之后，**它的调用者**也得 await，
  而调用者不是数据访问调用、静态检查抓不到（这正是第 3 步要逐个过、第 4 步要真跑起来的原因）。
· 现有自动回归网薄（CI 只跑 3 个脚本），所以第 4 步的"真跑一遍"不能省。
· 阶段 0 已经把这件改造的**数据面**风险消掉了（schema 与数据都验证过），
  剩下的风险全在**代码改造**上 —— 而那是可以逐批判定、可以回滚的。
```
