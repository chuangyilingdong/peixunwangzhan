## 一、要解决的问题

| # | 问题 | 现状 |
| --- | --- | --- |
| 1 | 发送次数误计 | 平台从对话历史里"猜"哪条 user 消息是学生按的。dsh 的压缩摘要、运行时上下文、技能指令、工具图片回填都会伪装成 user 消息，每出新形态就要补一条规则（`INJECTED_PREFIXES` 已经补了十几条）。2026-11-01 现场：学生本地只按了 **2** 次，库里记到 **9**，封顶成 7，课堂在 12:10 被 429 锁死 |
| 2 | 没有全局提示词 | 平台无法给所有 VibeCoding 会话加一段统一约束 |

客户端已配合：每次真实发送派生出的**所有**模型请求都会带 `x-zcode-send-id`（turnId）。
同一个用户发送产生的工具轮 / 压缩 / 起标题 / 子代理 / SSE 重试 / 断线重连复用同一个值；
用户下一次点发送才产生新值；没有 turnId 的后台请求不会伪造这个头。

## 二、平台改了什么

### 2.1 判据：从"猜历史"改成"数 sendId"

| 文件 | 改动 |
| --- | --- |
| `packages/database/src/schema.js` | 新增 `session_vibecoding_sends`（**主键就是幂等键**：`session_id, student_id, send_id`）；`platform_settings` 补两列 |
| `apps/server/src/services/vibecodingSendLedger.js` | **新增**：`recordSendId`（`INSERT OR IGNORE`）/ `countSendIds` |
| `apps/server/src/services/vibecodingLessonSettings.js` | 按请求头分流：有 sendId 走台账，没有走原启发式；两条路按"这场课堂有没有台账行"隔离 |
| `apps/server/src/routes/runtimeGateway.js` | 读 `x-zcode-send-id`，传给 `enforceVibecodingSendLimit` |

**幂等的关键**：先 `INSERT OR IGNORE`，再看行数 —— **不是**先查后写。
同一条请求并发到 8 路（SSE 重连 + 工具轮）时，只有数据库主键能裁决谁是真的第一次。
`aq()` 在 MySQL 驱动下会把 `INSERT OR IGNORE` 翻成 `INSERT IGNORE` 并回 `changes`
（`packages/database/src/mysql.js:120`）。

**兼容列**：`session_students.vibecoding_sends` 仍然跟着台账同步（只增不减），
因为老师端/报表还在读它。但它**不再是事实源**。

**旧客户端**：不带 sendId 的请求继续走原启发式（p118 原有 33 条断言全保留）。
只要这场课堂已有台账行，旧路径就直接按台账值判定、不再自己加数 —— 避免同一次发送被记两遍。

### 2.2 全局提示词

| 文件 | 改动 |
| --- | --- |
| `apps/server/src/services/vibecodingGlobalPrompt.js` | **新增**：读写、32 KiB 校验、敏感形态拦截、下发载荷 |
| `apps/server/src/routes/admin/platformSettings.js` | **新增**：`GET/PUT /api/admin/vibecoding-prompt`（带审计） |
| `apps/server/src/routes/adminOrg.js` | 注册分发 |
| `apps/server/src/lib.js` | 权限映射：`/api/admin/vibecoding-prompt` → `ADMIN_BILLING` |
| `apps/server/src/routes/studentRuntime.js` | `client-context` 两个分支都下发 `globalSystemPrompt` / `globalSystemPromptRevision` |
| `apps/admin/src/components/VibecodingPromptPanel.jsx` | **新增**：后台编辑面板（实时字节计数） |
| `apps/admin/src/pages/ModelCompute.jsx`、`src/main.jsx` | 第四个页签「全局提示词」→ `/compute/prompt` |

四条硬约束（全部在服务层兜住）：

1. **正文 ≤ 32 KiB UTF-8**，超了**整段作废**（不是截断）—— 契约要求"不出现半截提示词"；
2. **空 = 不启用**：两个字段整块不下发；
3. **revision 只用于诊断**，不进模型上下文；
4. **不放敏感信息**：服务端拒收 `sk-…`、阿里云 AccessKey、私钥头、身份证号、手机号这几类形态。

## 三、验证

`scripts/p118-vibecoding-send-limit.mjs` 扩到 **42 条断言**（原 33 条 + 新增 9 条），
在生产机的 Node 24 上、对打了补丁的源码树跑：

```text
{"name":"p118-vibecoding-send-limit","pass":true,"checks":42,"failed":[]}
```

新增断言直接对应客户端的验收清单：

| 客户端验收 | 平台断言 |
| --- | --- |
| 同一个 sendId 连续 100 次，计数只加 1 | ⑦ 连打 100 次，台账 = 1 |
| 同一 sendId 的并发请求不重复加次 | ⑦ 并发 8 路，台账 = 1 |
| 新 sendId 加 1 | ⑦ t1/t2/t3 各 +1，工具轮不重复 |
| 第 7 次成功后 used=7/remaining=0 | ⑦ 用 limit=3 等价验证 |
| 第 8 次返回 429 `SEND_QUOTA_EXCEEDED` | ⑦ 第 N+1 个返回 429，且不新增 usage_records |
| 旧客户端缺少 sendId 时不因工具轮增加计数 | ⑦ 老客户端在已有台账的课堂里不加数 |
| 下发后 client-context 带正文 | ⑧ 保存后原样下发 |
| 改正文/revision 后是新内容 | ⑧ 第二版生效 |
| 清空后不再带旧提示词 | ⑧ 字段整块消失 |
| 超 32 KiB 不出现半截提示词 | ⑧ 拒收且库里保留上一版 |

## 四、上线步骤

### 4.1 生产 DDL（RDS，手工）

```sql
CREATE TABLE IF NOT EXISTS session_vibecoding_sends (
  session_id   VARCHAR(64)  NOT NULL,
  student_id   VARCHAR(64)  NOT NULL,
  send_id      VARCHAR(128) NOT NULL,
  first_seen_at VARCHAR(40) NOT NULL,   -- 与全库一致：时间是 ISO 字符串，不是 DATETIME
  PRIMARY KEY (session_id, student_id, send_id)
);

ALTER TABLE platform_settings ADD COLUMN vibecoding_global_prompt TEXT NULL;
ALTER TABLE platform_settings ADD COLUMN vibecoding_global_prompt_revision VARCHAR(64) NULL;
```

> `first_seen_at` 用 VARCHAR(40) 而不是 DATETIME：全库其它时间列都是 mediumtext 存 ISO 串，
> 混合类型会让 `ORDER BY` / 比较出问题。

### 4.2 发布

代码与 admin 前端一起发一次（`build-production.sh` 会构建 admin）。**必须先 DDL 再发**，
否则网关第一次读 `session_vibecoding_sends` 会报表不存在。

### 4.3 数据校正：`csession_a5330d4b4c7e4bba8eff`

**依据**：整场 146 次 TEXT 请求里只有一个 ≥60 秒的空档（11:53:03 → 11:55:38，156 秒），
把时间线切成两段；客户端本地记录也是 2。所以真实发送次数 = **2**（库里是 9）。

```sql
-- 以现场为准执行；-- 前面两行是核对，确认后跑 UPDATE/INSERT
SELECT s.id, s.status, ss.vibecoding_sends
FROM class_sessions s JOIN session_students ss ON ss.session_id=s.id
JOIN users u ON u.id=ss.student_id
WHERE s.id='csession_a5330d4b4c7e4bba8eff' AND u.login='xueshengpeixun1-1';

UPDATE session_students SET vibecoding_sends=2, updated_at=UTC_TIMESTAMP()
WHERE session_id='csession_a5330d4b4c7e4bba8eff'
  AND student_id=(SELECT id FROM users WHERE login='xueshengpeixun1-1');

-- 台账补两行"历史校正"记录，让事实源与兼容列一致。
-- 用可自解释的 send_id 前缀，将来看到这两行就知道是人工校正的，不是客户端发的。
INSERT IGNORE INTO session_vibecoding_sends(session_id, student_id, send_id, first_seen_at) VALUES
  ('csession_a5330d4b4c7e4bba8eff', (SELECT id FROM users WHERE login='xueshengpeixun1-1'), 'legacy_correction:1', UTC_TIMESTAMP()),
  ('csession_a5330d4b4c7e4bba8eff', (SELECT id FROM users WHERE login='xueshengpeixun1-1'), 'legacy_correction:2', UTC_TIMESTAMP());
```

> 为什么要写台账那两行：`vibecodingSendUsage()` 是"台账有行就以台账为准"。
> 只改兼容列的话，学生下次用新客户端再来一次，台账从 0 开始、显示反而变成 1。

### 4.4 回滚

代码回滚到上一 release 即可（旧代码不看新表/新列，DDL 可以留着不动）。
数据校正**只影响这一场已结束（ENDED）的课堂**，不需要回滚。
